## Context

LLM用語要約は `LlmSummaryService` → `LlmSummaryPipeline` → `LlmClient.generate` の構造で、Ollama利用時は `OllamaClient` が `POST /api/generate`（`stream: false`）を発行する。現状のリクエストボディは `model` / `prompt` / `stream` のみで、生成パラメータは一切指定していない。

実測（gemma4:e4b、7ファイルヒット、9コール、コールドスタート）:

| 項目 | ベースライン | `think: false` 付与時 |
|---|---|---|
| 合計 | 128.4秒 | 34.0秒 |
| トークン生成 | 113.2秒 (88%) | 17.3秒 (51%) |
| プロンプト評価 | 9.7秒 | 11.7秒 |
| モデルロード | 5.0秒 | 4.7秒 |
| 生成トークン数/コール | 366〜1437 | 43〜167 |

thinking対応モデルはOllamaがデフォルトで思考トークンを生成し（`response` には含まれない）、これが生成時間の大半を占めていた。返答本文は52〜400文字に対し生成トークンは最大1437個。

## Goals / Non-Goals

**Goals:**

- thinking対応モデル使用時の用語解析時間を大幅短縮する（実測3.8倍）
- 出力トークン数に上限を設け、异常に長い出力による時間の暴走を防ぐ
- 旧Ollamaバージョン・thinking非対応モデルでも従来どおり動作する（劣化なし）

**Non-Goals:**

- OpenAI互換クライアントへの `max_tokens` / reasoning系パラメータ追加（プロバイダ依存のため別変更で検討）
- 呼び出しの並列化・ファイル統合・`keep_alive` 変更（残ボトルネックへの対策は別変更）
- thinking ON/OFF を切り替える設定UI（要望が出たら追加）
- タイムアウト・キャンセル（既知の負債 D-075、別軸）

## Decisions

### D1: `generate` のボディに `think: false` を無条件付与

`OllamaClient.generate` のリクエストボディに `'think': false` を常に含める。モデルのcapabilityを事前照会して分岐する案（`/api/show` でthinking対応か確認）は、追加のHTTP往復と状態管理を要する割に得るものがない。現行Ollamaはthinking非対応モデル（qwen2.5等）に `think: false` を送ってもエラーにならないことを検証済み。

### D2: 旧バージョン互換フォールバック（`think` 起因のエラー時に1回だけ再送）

古いOllamaは `think` パラメータ自体を知らない（未知フィールドは無視される）が、中間バージョンで thinking 非対応モデルへの `think` 指定を 400 で拒否する挙動が存在しうる。`generate` がエラーステータスを返し、かつエラー本文に `think` を含む場合に限り、`think` を除いたボディで1回だけ再送する。フォールバック発動後は同一クライアントインスタンスでは以後 `think` を送らない（毎コール2回送信になるのを防ぐ）。

代替案（フォールバックなし・エラーをそのまま表示）は、ユーザーのOllamaバージョンを制御できない配布アプリでは後方互換の後退となるため不採用。

### D3: `options.num_predict = 1024` を上限として付与

fact抽出・最終要約の正常出力は実測で最大400トークン程度（thinking込みベースラインでも返答本文は短い）。1024は正常出力の2倍以上の余裕を持ちつつ、思考の混入や繰り返し暴走（数千トークン）を確実に打ち切る値。値はコード内定数（`OllamaClient` の static const）とし、設定UIは設けない。

上限到達で切り詰められたJSONは既存のデコードフォールバック（生テキスト利用）または `LlmResponseFormatException` の経路に乗り、既存の堅牢性挙動を変えない。

### D4: `releaseResources` は対象外

アンロード要求（`keep_alive: 0`）は生成を行わないため、`think` / `num_predict` を付与しない。

### D5: `fact_cache` の `prompt_version` は据え置き

プロンプト文面は変更しないため、既存キャッシュのfactsは引き続き有効。thinking有無で抽出結果の文面は変わりうるが、意味的品質は同等（実測で確認）であり、全ユーザーのキャッシュを無効化してまで再抽出させる価値はない。

## Risks / Trade-offs

- [thinking無効化による品質低下の可能性] → 実測では最終要約の品質は同等（人手確認）。fact抽出はコンテキストからの列挙タスクであり深い推論を要さない。問題が報告されたら設定トグルを別変更で追加
- [`num_predict: 1024` が正当な長出力を切り詰める] → 実測最大の2倍以上の余裕を確保。切り詰め時も既存のフォールバック/例外経路で安全に処理される
- [未知のOllamaバージョンで `think` がエラーになる] → D2のフォールバックで1回だけ再送し、以後は送らない
- [エラー本文の文字列判定（`think` 含有）が脆い] → 誤検知しても影響は「`think` なしで再送する」だけで、結果は従来挙動と同じ（安全側に倒れる）
