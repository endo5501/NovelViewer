## Context

動機は proposal.md の「Why」を参照。

設計を形づくっている既存の構造は次の2点である。

**1. 話数上限フィルタは「上限以下でヒットのあるファイル」だけを残す。** `LlmSummaryService` は `searchWithContext` でフォルダ全体を検索したのち `_filterResultsByUpperBound` で話数が上限以下のファイルに絞る。ヒットの無いファイルはそもそも検索結果に現れないため、上限を初出話数 `F` に置くと残る証拠は初出話数のファイル群だけになる。これは「初出ページを閲覧中にネタバレなし解析を実行する」と同じ状態であり、**新モードは既存パイプラインの特殊ケースとして表現できる**。

**2. 本文と語を突き合わせる箇所が3つあり、1つだけルビの扱いが違う。** マーク描画（`mark_matcher.dart`）と履歴からのジャンプ（`first_line_containing.dart`）はルビタグを取り除いてから突き合わせるが、証拠収集に使う `searchWithContext` は生テキストに対して素朴な部分一致を行う。`ruby-text-rendering` の「Search highlight with ruby text」要件が描画側でルビ base を検索対象として扱う前提を置いていることからも、判定側が浮いている。

## Goals / Non-Goals

**Goals:**

- 新モードをプレゼンテーション層の追加だけで実現する（データ層に変更を加えない）
- 一致判定の不一致を解消し、副産物として既存2モードが初出ページを拾えるようにする
- 一致判定の実装を1つに保つ

**Non-Goals:**

- Ctrl+F の検索機能をルビ対応にすること（判定とハイライトの両方をセグメント跨ぎにする必要があり、規模が別）
- LLMに渡す証拠テキストの整形（ルビは情報を持つため生のまま渡す）
- 既存のファクトキャッシュの一括失効
- 初出ページに説明が無い語への対策

## Decisions

### D1. 新モードは `AnalysisScope` の追加と上限解決だけで実現する

`AnalysisScope` に1値（初出スコープ）を追加し、`runWithScope` で初出話数を解決して既存の `run()` / `generateSummary()` にそのまま渡す。`LlmSummaryService` / `LlmSummaryPipeline` / `FactCacheRepository` / `LlmSummaryRepository` / DBスキーマ / 履歴UI / ホバーポップアップの表示ロジックは変更しない。

スナップショットは `(word, F)` で保存され、履歴パネルには `F話時点` として並び、ホバー時のスナップショット選択則 `max{Sᵢ | Sᵢ ≤ C}` にも自然に乗る。

**代替案: `generateSummary` に証拠ファイル集合を渡せるようにする。** 「初出 + 現在ページ」のような複数ファイルの組み合わせに拡張できるが、Service のシグネチャと話数キーの意味を変えることになる。初出ページのみで割り切る方針（proposal.md 参照）では不要な一般化なので採らない。

### D2. ルビ除去は `searchWithContext` の一致判定にのみ適用し、返す文字列は生のまま

判定対象のテキストからは読み（`<rt>…</rt>`）、代替括弧（`<rp>…</rp>`）、および `<ruby>` / `</ruby>` と `<rb>` / `</rb>` のタグを取り除く。base は残る。除去するタグ集合は `parseRubyText` が認識するものと一致させる（理由は D5 参照）。返す行番号・文脈テキスト・拡張文脈は生の本文のまま変更しない。

証拠を生のまま渡すのは、小説においてルビが単なる読みではなく付加的な情報（別名、二重の意味、内心の声など）を担うためである。剥がすと語の意味自体が落ちる。

この変更が封じ込められていることの根拠: `SearchMatch` は `lineNumber` / `contextText` / `extendedContext` のみを持ち**列オフセットを持たない**。したがって「どの行を採用するか」の判定だけを変えても、下流に渡る値の構造は変わらない。

**代替案: 証拠テキストもルビ除去する。** トークンを節約でき、オンデバイスモデルの狭いコンテキスト窓では効く。しかし上記の情報損失に加え、既存のキャッシュ済みファクトとの整合のために `prompt_version` の更新が必要になる。得るものに対して代償が大きい。

### D3. `TextSearchService.search` は変更しない

`search` と `searchWithContext` は呼び出し元が完全に分離している（`search` は `searchResultsProvider` = Ctrl+F の検索UI、`searchWithContext` は `LlmSummaryService`）。したがって判定の変更を LLM 経路だけに限定できる。

UI 側も変えない理由は2つある。検索結果パネルは生の行をそのまま表示するため、ルビ除去でヒットした行はクエリが連続して見えない形で並ぶ。また本文中のハイライトは `ruby-text-rendering` の要件どおりセグメント単位で base を突き合わせるため、境界をまたぐクエリはハイライトできない。判定だけを変えると「一覧には出るがジャンプしてもハイライトされない」という新しい不整合が生まれる。

2つのメソッドは本体がほぼ同一で判定だけが分かれることになるため、**なぜ一方だけが剥がすのかをコードのコメントに残す**。これがないと次に読む者が不具合として扱う。

### D4. 初出話数は `searchWithContext` の結果から求め、専用の検索APIを作らない

`runWithScope` は `searchWithContext(directory, word)` を呼び、結果のファイルのうち有効話数（数値接頭辞、無ければフォルダ内の辞書順ランク）が最小のものを取る。

**代替案: 話数昇順に走り最初のヒットで打ち切る軽量APIを追加する。** 読むファイル数は減るが、**一致判定の2つ目の実装**になる。両者がずれた瞬間、初出として解決したファイルで Service が何も見つけられず、目に見えて存在する語に対して「情報を抽出できなかった」失敗が出る。フォルダ全読み1回の追加コストは、LLM呼び出し2回に対して誤差であり、判定の一貫性を構造的に保証できるほうが価値が高い。

なお Service 側も同じ検索を再度行うため、1回の簡易解析でフォルダ全読みが2回発生する。これは既存のネタバレなし解析にも同程度存在する既存の非効率であり、本変更では扱わない。

### D5. ネタバレの上限クランプを実装しない

「簡易解析はネタバレなし解析の読む範囲を超えない」という不変条件（specs/llm-summary-context-menu-trigger 参照）は、D2 の結果として**導出される**。ユーザーが選択できるのは現在ページに表示されている語であり、判定が表示形と同じ規則でルビを取り除くなら現在ページ自身が必ずマッチする。したがって語を含むファイルの最小話数は現在ページの話数以下になる。

**代替案: 初出の探索を「話数 ≤ 現在ページ」に限って最小を取る。** 判定がずれていても上限を守れるが、それは原因（判定の不一致）を放置して症状に蓋をする形になり、解析の精度は一切改善しない。D2 を行うなら不要な機構である。

ただしこの依存関係は記録しておく価値がある。**一致判定が表示形と食い違うことは、結果の質の問題であるだけでなくネタバレの問題でもある。** 判定が現在ページを取りこぼせば、簡易解析は未読ページを唯一の証拠に選びうる。

**実際にこれは一度壊れた。** 最初の実装では除去パターンが `<rb>` / `</rb>` を含んでおらず、`parseRubyText` が `<rb>` の内容を表示上の base として扱う一方で、除去後のテキストにはタグが残っていた。青空文庫の HTML は `<ruby><rb>…</rb><rp>…</rp><rt>…</rt><rp>…</rp></ruby>` という完全形を使い、`AozoraSite` はこのアプリの正式なアダプタで、ダウンロード時にルビは `outerHtml` のまま保存される。つまり青空文庫由来の小説では常態であり、初出ページを取りこぼして未読ページに上限が飛ぶ経路が実在した。

したがって**除去対象のタグ集合は `parseRubyText` が認識するものと一致していなければならない**。これは不変条件の前提そのものなので、ヘルパのコメントに明記し、ヘルパ・証拠検索・上限解決の3階層でテストで固定した。

### D6. `prompt_version` は上げない

ルビ対応で証拠が増えるファイルは2種類に分かれる。

- **該当箇所がすべてルビ分断だったファイル** — 従来は `matches.isEmpty` で `SearchResult` が返らず、`_FileWork` に入らず、ハッシュも取られず、キャッシュ行が存在しない。修正後は新規のミスとして正しく抽出される。**無効化不要**。本変更の精度上の主張（作者がルビを振った初出ページ）を支えるのはこのケースであり、無償で解決する。
- **素の出現とルビ分断の出現が混在するファイル** — 行が存在し `content_hash` も `prompt_version` も一致するため再利用され、ファクトが不完全なまま残る（間違いではない）。

後者のために `prompt_version` を上げると、全既存ユーザーの全語・全ファイルのキャッシュが失効し、狭いケースのために全再抽出を課すことになる。上げない。

**この不完全さがどこまで治癒するかは、当初の記述より狭い。** 失効は `generateSummary` の再解析検出を通じてのみ起き、その条件は3つとも満たされる必要がある。

1. **同一の上限**にスナップショットが既存であること（`s.coveredUpToEpisode == coveredUpToEpisode`）。別の上限で解析しても何も失効しない。
2. 失効はそのモデルの行に限られる（`modelId`）。
3. 失効は `updated_at <= lastSuccessfulRun` の行に限られる。

3つ目が最も効く。キャッシュ行の書き込みは失敗の**手前**で行われるため、**保存前に失敗した解析が書いた行は最後の成功スナップショットより新しくなり、失効を免れる**。ハッシュもプロンプト版も変わらないので、それらは同一上限での再解析後もキャッシュヒットし続ける。

加えて、失効が起きた場合でも再抽出されるのは**その時点で一致し、かつ上限内のファイル**だけであり、全ファイルが即座に作り直されるわけではない。

したがって「一度再解析すれば直る」は保証ではない。確実に作り直したい読者には、その語の要約を削除する経路がある（`fact_cache` はカスケードで消える）。それでも `prompt_version` を上げない判断は変えない: 上げる代償は全既存ユーザーの全語・全ファイルであり、対象は素とルビ分断が混在するファイルという狭いケースのままである。

### D7. ルビ除去ヘルパを共有化する

`mark_matcher.dart` と `first_line_containing.dart` に同一の除去パターンが重複しており、`searchWithContext` が3箇所目になる。`lib/shared/` に1つ切り出して3箇所から使う。

当初は「挙動を変えない純粋な移動」と位置づけていたが、**D5 の `<rb>` 修正によりそうではなくなった**。パターンに `<rb>` / `</rb>` を加えたことで、マーク描画と履歴からのジャンプも `<rb>` 付きの語を扱えるようになった。どちらも改善だが、共有化が挙動に影響しないという前提は成り立たないので、両者にも `<rb>` のテストを追加した。

共有化しておいたこと自体は結果的に効いた。3経路が同じ盲点を持っていたため、1箇所の修正で3つとも直っている。

### D8. 3つの解析メニュー項目は1グループとして扱う

既存の2項目は同じ条件（解析が利用可能か）でゲートされており、テストも `vertical_context_menu_test.dart` の「omits **both** analysis entries when their labels are absent」、`dictionary_context_menu_test.dart` の「omits both optional groups when neither callback is given」とグループ単位の挙動を固定している。グループ内の個別独立性を主張するテストは無い。新項目も同じグループに合流させ、「3つとも出るか1つも出ないか」とする。辞書項目は従来どおり独立に省略可能。

### D9. ホバーポップアップの簡易解析項目には話数と `(上書き)` を出さない

既存2項目は話数と、既存スナップショットがある場合の `(上書き)` を表示する。簡易解析でこれを出すにはメニュー構築時に初出検索が必要になり、**ドロップダウンを開くだけでフォルダ全読みが走る**（しかも非同期）。このモードの性格は「何話時点かはどうでもいいから概要をくれ」なので、ラベルに話数が無いのは不自然ではない。

上書き自体は他の項目と同様に確認なしで進む。表示しないのは予告だけである。

### D10. 解析対象の小説は要求時に一度だけ決め、`run` に渡す

`runWithScope` は上限解決のためにフォルダ全体を検索し、それを await する。`run` は従来、自身で `summaryNovelFolderProvider` を読み直していた（await を跨ぐ自分自身の処理に対しては正しい防御だった）。しかし await が `run` の**手前**に入ったことで、検索中に読者が別の小説へ移動すると、上限と `source_file` は小説Aのものなのに書き込み先が小説Bになる経路ができた。

`run` に省略可能な「要求時に確定した小説フォルダ」を渡し、渡された場合はそれを使う。渡された経路も**信用せず検証する**（`isRegisteredNovelFolder`）: 検索中にその小説が削除・登録解除されている可能性があり、リポジトリを開くと `novel_data.db` が作られてしまう。

これは `specs/llm-summary-context-menu-trigger` の「解析の対象フォルダは、要求を受けた時点で一度だけ決定しなければならない」を満たす形でもある。

### D11. 検索の失敗はスコープを広げず、報告して止める

初出解決の検索が例外を投げた場合、「語がどこにも無い」と同じ `null` に畳んではならない。両者は違う:

- **語が無い**: どの上限でも証拠は空なので、閲覧位置にフォールバックして既存の「ファクトなし」失敗に落ちるのが正しい
- **検索が失敗**: 上限が不明なだけで、閲覧位置にフォールバックすると**ヒットファイル数ぶんの抽出が走る**。読者が避けたかったコストそのものを、簡易解析の名前で実行して保存してしまう

後者は報告して中断する。当初は「後続の `run` が同じフォルダを再検索して同じエラーに当たるので、そこで報告される」と考えていたが、一時的な失敗（ダウンロードによる書き換え中、一瞬のロック）では再検索が成功しうるため、この前提は成り立たない。

失敗報告の診断情報には上限を「未解決」として記録する。簡易解析は上限を得る前に検索するため、上限が決まらないまま失敗しうる唯一のスコープである。

## Risks / Trade-offs

- **一致判定の変更が既存2モードの出力を変える** → 変わる方向は「これまで取りこぼしていた初出ページを拾う」であり品質は上がる。ただし同じ語を再解析した結果が以前と違うものになり得る。既存スナップショットは上書きされるまで残るため、ユーザーが明示的に再解析しない限り変化は起きない。
- **素とルビ分断が混在するファイルのキャッシュが不完全なまま残る**（D6） → 同一上限での再解析で治癒しうるが保証ではない（失敗した解析が書いた行は失効を免れる）。確実に作り直すにはその語の要約を削除する。全既存ユーザーに全再抽出を課すコストと引き換えに受け入れる。
- **簡易解析が既存スナップショットの話数に当たるとその語のファクトキャッシュを丸ごと失効させる** → Service を変更しない代償。100ページ目から簡易解析を実行して初出話数が既存スナップショットと一致した場合、以前の全話解析で溜めたファクトが失われる。D6 の治癒機構と同一の機構であり、無効化の粒度をファイル単位に変えるには Service に手を入れる必要があるため本変更では扱わない。
- **「LLM呼び出し2回」は保証ではない** → 話数は `^(\d+)` で抽出されるため `005_a.txt` と `005_b.txt` は同じ話数5に解決され、どちらも上限フィルタを通る。分割エピソードを含むフォルダではその話数を共有するファイル数だけ抽出が走る。
- **横書きの選択ツールバーが5項目になる** → `AdaptiveTextSelectionToolbar` は幅に応じてページ送りを出す。実用上の問題は想定していないが、狭い幅では項目が折り返される。
- **共有ヘルパ抽出は挙動を変える**（D7） → `<rb>` を加えたことでマーク描画と履歴ジャンプの挙動も変わった。どちらも改善方向だが、抽出コミットとタグ追加コミットを分け、両者に `<rb>` のテストを追加してレビューできる形にした。
- **上限解決の検索中はモーダルも表示も出ない** → `run` がモーダルを出すのはクライアントとリポジトリの解決後であり、フォルダ全読みはその手前で走る。100話規模の小説では読者が「反応がない」と判断して再度メニューから実行でき、`generateSummary` が二重に走る（モーダル二重、LLMコスト二重、同じ語への `saveSnapshot` / `upsert` の競合）。この窓は他の2スコープにも元から存在するが、本モードは検索を挟むため明確に長い。本変更では扱わない。
