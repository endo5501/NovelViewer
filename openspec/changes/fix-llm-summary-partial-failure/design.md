## Context

用語解析は `DefaultAnalysisRunner.run` → `LlmSummaryService.generateSummary` → `LlmSummaryPipeline` → `LlmClient.generate` の縦一列で、途中の例外は一切捕まらずランナーまで上がり、スナックバーに文字列化されて終わる。

```
DefaultAnalysisRunner.run
  └ LlmSummaryService.generateSummary
      ├ [再解析なら] factCacheRepository.invalidateWord      ← 全行に sentinel
      ├ for (file in files)                                   ← 逐次
      │    ├ pipeline.extractFileFacts()  ──✗ throw ──┐
      │    └ factCacheRepository.upsert()             │  成功分はここまで残る
      ├ pipeline.summarizeFromFacts()     ──✗ throw ──┤
      └ repository.saveSnapshot()          到達せず ◀──┘
                                                      │
                          catch → snackbar「失敗」 ◀──┘  成果物ゼロ
```

`_parseJsonResponse` は応答を3分岐で扱う。

| 入力 | 現在の扱い |
|---|---|
| 妥当なJSON、キーの値が文字列 | 採用（正常） |
| `jsonDecode` 失敗 | WARNING を出し、**生テキストをそのまま値として採用** |
| 妥当なJSONだがキーの値が非文字列/欠落 | WARNING を出し `LlmResponseFormatException` を **throw** |

2番目の経路は「モデルが素の散文で返した場合の救済」として設計されたが、実際に踏まれているのは「壊れたJSON」であり、`{"facts": "- ...` というJSONの残骸が facts として `fact_cache` に永続化されている。3番目の経路が解析全体を落としている。

実測値（`speed-up-llm-summary` の design より、gemma4:e4b・7ファイル・9コール）:

| 項目 | ベースライン | `think:false` |
|---|---|---|
| 生成トークン数/コール | 366〜1437（思考込み） | 43〜167（応答本文のみ） |
| 合計時間 | 128.4秒 | 34.0秒 |

`options.num_predict = 1024` は応答本文の実測最大 167 トークンに対し約6倍の余裕がある。

ログ（全期間）に現れた失敗の実測頻度:

| 種別 | 件数 | 結果 |
|---|---|---|
| 妥当JSONだが配列（type B） | 2 | 解析中断 |
| `jsonDecode` 失敗（type A） | 4 | 生テキストをキャッシュに保存 |
| 空応答（`length=0`） | 1 | 空 facts をキャッシュに保存 |

## Goals / Non-Goals

**Goals:**

- LLM応答の整形ミスに起因する解析中断を原理的に発生させない
- 一過性の障害（ネットワーク瞬断・Ollama 5xx）を1回のリトライで吸収する
- 解析が失敗しても、成功済みファイルの抽出結果を保持し、再実行を失敗ファイル分のコストに抑える
- 壊れた応答・空応答を `fact_cache` に書き込まない
- 空の facts から幻覚的な要約を生成・保存しない

**Non-Goals:**

- 欠落を含む要約のスナップショット保存（不完全な要約を残さない方針を採る）
- スナップショットへの「欠落あり」情報の永続化と履歴詳細画面での表示（今回はスナックバー通知まで）
- `OpenAiCompatibleClient` の `response_format` 対応（プロバイダ依存、別変更）
- `format` 非対応 Ollama 向けのフォールバック
- `done_reason: "length"` による打ち切り検知、`num_predict` の値変更
- 既存の汚染キャッシュ行に対する移行処理、`prompt_version` のbump
- タイムアウト・キャンセル（既知の負債 D-075、別軸）
- リトライ回数・スキーマ強制のON/OFF設定UI

## Decisions

### D1: 応答スキーマを `LlmClient.generate` の任意引数として上から下ろす

キー名（`facts` / `summary`）を知っているのは `LlmSummaryPipeline` だけで、ワイヤ形式を知っているのは各クライアントだけである。したがってスキーマの「意味」をパイプラインからクライアントへ渡し、ワイヤ形式への変換はクライアントに閉じる。

`generate` に任意の名前付き引数を1つ追加する形とし、既定値は「スキーマなし＝現行挙動」とする。これにより既存の呼び出し箇所とテストは無改修で通る。

生のJSONスキーマ Map を直接渡さず、`{"<key>": <string>}` という今回必要な形だけを表現する小さな値オブジェクトを介する。理由は2つ:

- パイプラインがOllamaのワイヤ形式を知ってしまうのを防ぐ
- 将来 `OpenAiCompatibleClient` が `response_format: json_schema` にマップする際、変換先が各クライアントに閉じる

**代替案**: パースごとクライアントへ移す（`generateStructured(prompt, key) → String`）。責務分割としては綺麗だが、`_parseJsonResponse` のテストがパイプライン側に厚く積まれており、移動コストに見合う利得がない。不採用。

### D2: `OllamaClient` は `format` を無条件に送信し、フォールバックを設けない

Ollama の Structured Outputs（`format` にJSONスキーマ）は 0.5.0（2024-12）以降で提供されている。2026-08 時点の最新は 0.32.5 であり、Ollamaは更新が容易なため対象バージョンを使用していないユーザーは実質存在しない。

`think` パラメータには既存の「HTTP 400 かつ本文に `think` を含む場合に1回だけ再送」フォールバックがあるが、これに `format` を加えると:

- 古いサーバが `format` を理由に400を返した場合、本文に `think` を含まないため rethrow され、**現状より悪化する**
- 原因パラメータを本文の文字列マッチで判別するロジックが2本になり脆くなる
- 最悪3リクエストが飛ぶ

存在しない環境のためにこの複雑さを負うのは割に合わない。`format` は無条件付与とし、既存の `think` フォールバックには手を触れない（挙動不変）。

**代替案**: 起動時に `GET /api/version` で能力判定。追加の往復とバージョン文字列比較という別の脆さを持ち込む割に、守る対象が存在しない。不採用。

### D3: スキーマは Stage ごとに単一文字列フィールドを要求する

- Stage-1: `{"type":"object","properties":{"facts":{"type":"string"}},"required":["facts"]}`
- Stage-2: 同じ形で `summary`

`format: "json"`（JSONモード）では不十分である点が重要。JSONモードは**構文的に妥当なJSON**しか保証せず、`{"facts": ["- ...", "- ..."]}` は妥当なJSONであるため、今回中断を引き起こしている type B を素通りさせる。スキーマ指定でのみ型が制約される。

| | type A（未エスケープ `"`） | type B（配列） |
|---|---|---|
| 現状 | 発生 | 発生 |
| `format: "json"` | 解消 | **発生したまま** |
| `format: <schema>` | 解消 | 解消 |

`releaseResources`（`keep_alive: 0`）は生成を行わないため対象外。

### D4: リトライは「同一リクエストを1回」に限定し、Stage-1・Stage-2 の両方に適用する

D1〜D3により整形ミスは発生しなくなるため、リトライが救う対象は一過性の障害（ネットワーク瞬断、Ollama 5xx、モデルの一時的な異常応答）に限られる。これらは同じリクエストを投げ直せば通ることが多く、`think` を戻す・プロンプトを変える等の変化を付ける必要はない。

Stage-1 にもリトライを置くのは D6 の帰結である。1ファイルでも救えなければスナップショットが保存されない以上、その場で救う価値がStage-2と同等に高い。Stage-1 のリトライ回数を増やさないのは、失敗ファイルがキャッシュに書かれない（D5）ため再実行で自動的に再試行され、実質的な追加リトライになるためである。

バックオフは設けない。ローカルLLM相手であり、接続拒否は即座に返る。

### D5: 構造化パースに成功した facts のみを `fact_cache` に書き込む

汚染の原因は「パースに失敗した結果」を無検査で `upsert` していることであり、既存行の掃除ではない。書き込み側を締めれば将来の汚染はゼロになり、既存の汚染行（全期間で5行程度）は再解析時の `invalidateWord` で自然に解消する。移行処理も `prompt_version` の bump も不要。

書き込まない対象:

- 生テキストフォールバックの戻り値（`jsonDecode` に失敗したもの）
- 空文字の facts（マッチしたファイルから事実が1つも出ないのは異常応答とみなす）

書き込まなかったファイルは次回解析でキャッシュミスとなり、自動的に再抽出される。

### D6: ファイル単位の失敗は記録して継続し、1件でも失敗があれば保存せず失敗させる

「継続する」目的は部分要約を作ることではなく、**残りファイルのキャッシュを温めて再実行を安くすること**である。

```
失敗即中断: A✓ B✓ C✗ → 終了            再実行は C D E の3コール
継続      : A✓ B✓ C✗ D✓ E✓ → 失敗扱い   再実行は C の1コール
```

失敗が1件でもある場合、Stage-2 は呼び出さない。どうせスナップショットを保存しないため、最終要約のコールが純粋な無駄になる。

Ollama自体が停止している場合に残りファイル分のリクエストを投げ続ける懸念があるが、接続拒否は即座にエラーが返るため、数ファイル分でも数百ミリ秒の無駄にとどまる。失敗の性質（一過性か systemic か）で分岐する複雑さは、この規模では割に合わない。常に継続する。

**代替案**: 欠落ありの要約を保存する。ユーザーが「その要約が不完全であること」を知る手段がなく（スナップショットに欠落情報を持たせるのは Non-Goal）、誤解を招く。不採用。

### D7: facts が空のまま最終要約を生成しない

現状 `summarizeFromFacts` は `nonEmpty` が空でも `facts = ''` としてLLMを呼び、空の `<facts>` から要約を「創作」させてスナップショットに保存する。今は到達しにくいが、D6のスキップ継続を入れると「全ファイル失敗」で確実に踏む。

facts が空の場合は最終要約を呼ばず、明示的に失敗させる。

### D8: 再解析時の無効化は、当該スナップショットより新しい `fact_cache` 行を対象外とする

`isReanalysis` の判定材料は「同一 `coveredUpToEpisode` のスナップショットが存在するか」だけである。失敗した試行はスナップショットを保存しないため、過去に一度成功している単語の再解析が失敗すると、次の試行でも `isReanalysis` が真になり `invalidateWord` が再び全行を無効化する。結果、直前の試行で温めたキャッシュが毎回破棄され、再実行が永久にフルコストになる（D6の効果が完全に打ち消される）。

`fact_cache.updated_at` が当該スナップショットの `updated_at` より新しい行は、そのスナップショットが保存された後に走った試行（＝先行する失敗試行）で再抽出済みである。これを無効化の対象外とする。

- `word_summaries` / `fact_cache` とも `updated_at` を既に持つため、スキーマ変更は不要
- 「再解析＝やり直し」の意味は保たれる（スナップショットより古い行はすべて無効化される）

**代替案**: 試行内の更新済みファイルをメモリ上のセットで管理する。アプリ再起動をまたぐと復元できず、長い解析ほど失われやすいため不採用。

### D9: 失敗の可視化はスナックバー文言のみ

失敗ファイル件数を含むメッセージを `AppLocalizations` に追加し（ja/en/zh）、既存の失敗スナックバーに代えて表示する。スナップショットへの永続化と履歴詳細画面での表示は、DBスキーマと `llm-summary-history-detail-view` に波及するため今回は行わない。

## Risks / Trade-offs

- [スキーマ制約による抽出品質の低下] → スキーマは単一文字列フィールドという最も単純な形であり、文法制約が生成内容に与える影響は小さい。プロンプト側のJSON指示も従来どおり残し、モデルへの指示とスキーマを一致させる
- [`format` 非対応の古いOllamaでエラーになる] → 対象バージョン（0.5.0未満、2024-12以前）を使用しているユーザーは実質存在しない。仮に該当した場合はエラーが即座に表面化するため、原因が不明瞭なまま劣化することはない
- [D6により、失敗する運命の実行でも全ファイル分のLLMコールを消費する] → 消費したコールの結果はキャッシュされ再実行で再利用されるため、作業は捨てられず前倒しされるだけ。Ollama停止時は接続拒否が即返るため実害はない
- [D5により、空 facts を返す正当なケースがキャッシュされず毎回再抽出される] → 検索でマッチしたファイルから事実が1つも抽出されないのは異常応答とみなすのが妥当。仮に正当なケースがあっても、コストは該当ファイルの再抽出1回分
- [D8の時刻比較] → 比較対象は同一DB内で `DateTime.now()` により書かれた値であり、単調性の前提は満たされる。等値の場合は「スナップショットと同時刻＝そのスナップショットを生んだ試行の産物」として無効化対象に含める（安全側）
- [リトライにより失敗時の待ち時間が最大2倍になる] → 失敗は稀であり、成功パスの所要時間は変わらない。バックオフを設けないため追加遅延は1リクエスト分にとどまる
- [`llm-generation-efficiency` の `think` フォールバックが実質的に不要なコードとして残る] → 今回のスコープ外とする。`format` と異なり既に出荷済みの挙動であり、除去は独立した判断（別変更）が適切

## Migration Plan

DBスキーマ変更・データ移行はない。`fact_cache.prompt_version` を据え置くため既存キャッシュは引き続き有効。既存の汚染行は再解析時に上書きされる。ロールバックはコードの revert のみで完結する。
