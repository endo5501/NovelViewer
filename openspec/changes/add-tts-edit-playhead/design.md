## Context

読み上げ編集ダイアログの再生系は次の構造になっている。

```
TtsEditDialog (:328 build)
  ├ _buildToolbar(isGenerating, isPlaying)          // isPlaying = playbackIndex != null
  │    [辞書] [全再生] (再生中なら[停止]) [全生成/中断] [全消去]
  └ ListView.builder
       └ TtsEditSegmentRow(isPlaying: playbackIndex == index, ...)

TtsEditController.playAll (:335)
  for (var i = 0; i < _segments.length; i++) {   // 開始位置は 0 固定
    if (_cancelled) break;
    if (!_segments[i].hasAudio) continue;         // 未生成はスキップ
    onSegmentStart?.call(i);
    await playSegment(i);
  }
```

再生ロジック自体は十分に薄い。欠けているのは**位置の状態**である。`ttsEditPlaybackIndexProvider` は `int?` で、再生中だけ値が入り、終わると null に戻る。したがって「次にどこから鳴らすか」を表現できない。

制約:

- 1エピソードのセグメント数は数十〜数百に達する
- セグメント行の高さは可変（本文は `maxLines: null`、メモは `minLines: 1, maxLines: 2`）
- `TtsEditDialog` は `initState` で実DB・`TtsIsolate`・`JustAudioPlayer`・`path_provider` を直接掴むため、ウィジェットテストで pump できない（既存 change `widen-tts-edit-dialog-memo` の D5 で確認済み）

## Goals / Non-Goals

**Goals:**

- 修正したセグメントの位置から、その前後のつながりを1操作で確認できること
- 再生がどこから始まりいまどこにいるのかが、常に画面上で分かること
- 従来の「頭から通しで確認する」動線が失われないこと
- 位置に関する状態を1つに保ち、状態の二重管理を作らないこと
- ヘッド移動と自動スクロールを自動テストで検証できる状態にすること

**Non-Goals:**

- 再生中にシーク（別の行をクリックして再生位置を飛ばす）できるようにすること — D4 で見送る
- 再生範囲の指定（「ここから3セグメント」など）や区間リピート
- 再生速度・音量の調整、再生キューの可視化
- 未生成セグメントを再生時に自動生成すること
- キーボードショートカットによるヘッド移動・再生操作
- 再生中の行操作の全面的な設計（D8 は再生ヘッドのロックを守るのに必要な範囲だけを扱う）

## Decisions

### D1: 位置の状態を「再生ヘッド」1つに統合する

`ttsEditPlaybackIndexProvider : int?` を廃止し、次の2つに置き換える。

```dart
ttsEditCursorIndexProvider : int   // 再生ヘッド。初期 0。null を取らない
ttsEditPlayingProvider     : bool  // 再生中かどうか
```

旧 provider は「位置」と「再生中か」を `int?` の1つに詰め込んでいた。ヘッドは再生していないときも位置を持ち続ける必要があるため、この表現では成立しない。2つに分ける方が、それぞれの意味も単純になる。

行の表示規則は次の2つに分かれる。

| 表示 | 条件 | 意味 |
|---|---|---|
| 背景の強調 | `cursorIndex == index` | 次に再生が始まる場所 |
| 🔊 アイコン | `cursorIndex == index && isPlaying` | いま鳴っている |

通常の再生中は両者が同じ行に重なるが、意味が異なるため両方残す。停止中は強調だけが残り、「ここから鳴る」ことを示す。

検討した代替案:

| 案 | 却下理由 |
|---|---|
| 既存の `playbackIndex` を残し、カーソルを別 provider で追加 | 位置の書き手が2つになり、再生中はどちらが正なのかが常に問われる。今回の設計はまさにその二重化を避けるためのもの |
| ヘッドを `int?` とし、未設定を null で表す | 「未設定」状態のUI（ボタン無効化など）が必要になる。初期値 0 なら [再生] は常に押せて、その挙動は従来の全再生と一致する。未設定という状態を作らないこと自体が単純化になる |

### D2: [全再生] を [再生] に統合する

ツールバーのボタンを1つに保ち、ラベルを `ttsEdit_playAllButton`（全再生 / Play all / 全部播放）から `ttsEdit_playButton`（再生 / Play / 播放）へ差し替える。旧キーは削除する。

ヘッドの初期値が 0 であるため、**ダイアログを開いた直後に [再生] を押した挙動は従来の [全再生] と完全に同一**である。「全再生」と「ここから再生」を2つ並べる案は採らない。両者は開始位置が違うだけの同一機能であり、ボタンを分けると「全再生はヘッドを 0 に戻すのか？」「押し分けの基準は？」という問いを利用者に課すことになる。ヘッドを見せた上でボタンを1つにする方が、状態と操作の対応が素直である。

### D3: ヘッドの移動規則

```
                  ┌──────────── 再生ヘッド (int, 初期 0) ────────────┐
  行をクリック ───┤ (再生中は無視 → D4)                              │
  再生の進行 ─────┤ playAll の onSegmentStart ごとに更新             ├─▶ 強調 / 自動スクロール / [再生]の開始位置
  末尾まで到達 ───┤ 0 に戻す                                         │
  [停止] ─────────┤ 移動しない（止まった位置に留まる）                │
                  └──────────────────────────────────────────────────┘
```

**末尾到達で 0 に戻す**のは、[再生] を2回続けて押したときに全体の通し再生が再び得られるようにするためである。末尾に留める案では、2回目の [再生] が最終セグメント1つだけを鳴らして終わり、従来の全再生が事実上失われる。

**[停止] では移動しない**ため、長い後半を小分けに確認する動線（停止 → [再生] で続きから）が自然に成立する。修正箇所を繰り返し聴きたい場合は、その行をもう一度クリックしてヘッドを戻す。

境界的な挙動として、ヘッド以降に生成済みセグメントが1つも無い状態で [再生] を押すと、何も鳴らないままループが末尾に達し、ヘッドは 0 に戻る。音が出ないのにヘッドが動くのは一見唐突だが、「末尾まで到達した」という事実としては正しく、追加の分岐を設けるほどの頻度ではないため許容する。

### D4: 再生中のクリックではヘッドを動かさない

再生中はヘッドの書き手を再生ループに専有させ、行のクリックによる移動を無視する。文字編集・メモ編集は従来どおり可能とする。

再生中もクリックで移動できるようにすると、書き手が2つになる。seg3 の再生中にユーザーが seg10 をクリックすると、ヘッドは一旦 10 へ飛び、次のセグメント開始で 4 に戻される。強調と自動スクロールがそれに追随するため、画面が跳ねる。

正しく解決するなら「クリック＝シーク（現在の再生を中断してその位置から再生し直す）」だが、`playAll` は `await` ループであり、`stopPlayback()` で `_cancelled` を立てても前のループが巻き戻るまでの間に新しいループを始めると、2つのループが同時に `SegmentPlayer` を触る。世代トークンによる無効化か、前の Future の完了待ちが必要になる。今回の動機（修正箇所の確認）はシークを必要としないため、範囲外とする。位置を変えたい場合は [停止] → クリック → [再生] の3操作で到達できる。

将来シークを入れる場合も、ヘッドという状態はそのまま使えるため、この設計は後戻りにならない。

### D5: ヘッド移動は行を包む `Listener` の `onPointerDown` で検知する

```dart
Listener(
  onPointerDown: (_) => onCursorRequested(index),
  child: Row( ...本文 / 参照音声 / メモ / [▶][↻][⟲]... ),
)
```

ポインタイベントはヒットテスト経路を親へ伝播するため、行のどこを押しても発火する。本文欄をクリックして編集を始めた場合も、メモ欄でも、[▶] を押した場合も、同じ1つの規則でヘッドが動く。`Listener` はイベントを消費しないので、既存の入力挙動（`TextField` のフォーカス、`onTapOutside` による確定、ドロップダウン、各ボタン）は一切変わらない。

「編集した行が起点になる（フォーカス追従）」と「明示的に選んだ行が起点になる（行選択）」という2つの要求が、これ1つに畳まれる。

検討した代替案:

| 案 | 却下理由 |
|---|---|
| 本文欄・メモ欄に `FocusNode` を持たせ `hasFocus` を監視 | 行あたり2つの `FocusNode` の生成・破棄を管理することになる。またボタンを押した瞬間にフォーカスは外れるため、「直近にフォーカスを持った行」を別途粘着保持する必要があり、状態が増える |
| 行に `InkWell` / `GestureDetector` を被せる | タップを消費するため、下にある `TextField` やボタンへイベントが届かなくなる（`behavior` の調整が必要になり、副作用が読みにくい） |
| 行ごとに「ここから再生」ボタンを追加 | 状態を持たずに済むが、既に7要素が並ぶ行がさらに横に伸びる。またヘッドという概念が生まれないため、強調表示も自動スクロールも成立しない |

Tab キーによるフォーカス移動ではヘッドが動かない。デスクトップでこのダイアログをキーボードだけで操作する動線は現状無いため許容する。必要になれば行全体を `Focus(canRequestFocus: false, onFocusChange: ...)` で包んで拾える。

逆に、ドラッグでスクロールを始めた場合はその起点の行にヘッドが移る。ただしデスクトップでは実質発生しない: Flutter の `MaterialScrollBehavior.dragDevices` はマウスを含まないためマウスドラッグでは一覧はスクロールせず、ホイールとトラックパッドのスクロールは `PointerDown` ではなくポインタシグナル／パンズームイベントとして届くため `onPointerDown` を発火させない。タッチスクリーンでのみ起こりうるが、本アプリはデスクトップ専用である。

### D6: リスト部分を `TtsEditSegmentList` として切り出す

`lib/features/tts/presentation/tts_edit_segment_list.dart` を新規作成し、次の責務を持たせる。

```
TtsEditSegmentList  (StatefulWidget)
  入力: segments, cursorIndex, isPlaying, generatingIndex, voiceFiles, enabled, 各コールバック
  保持: ScrollController, Map<int, GlobalKey>
  責務: 行の構築 / 再生中のヘッド移動の抑止 (D4) / 自動スクロール (D7)
```

理由は**テスト可能性**である。プロジェクトの必須ルールはTDDだが、`TtsEditDialog` は `initState` で実DB・`TtsIsolate`・`JustAudioPlayer`・`path_provider` を直接生成するため pump できない（既存 change `widen-tts-edit-dialog-memo` の D5 参照）。一方この切り出し後の `TtsEditSegmentList` が必要とするのは `List<TtsEditSegment>`（純粋なデータクラス）と int / bool とコールバックだけであり、単体で pump できる。

D4（再生中は無視）と D7（自動スクロール）はどちらも純粋に表示層の規則であり、DB も音声も関与しない。この widget に置くことで両方が自動検証の対象になる。`TtsEditDialog` に残るのは provider と controller の配線だけになる。

### D7: 自動スクロールは `Scrollable.ensureVisible` と方向別の `alignmentPolicy` で行う

行の高さが可変（本文 `maxLines: null`、メモ `maxLines: 2`）なので、`ScrollController.animateTo(オフセット計算)` は使えない。`Scrollable.ensureVisible` は対象要素の実レイアウトから必要量を求めるため、可変高でも正しく動く。行ごとの `GlobalKey` を `Map<int, GlobalKey>` として State に保持し、ヘッドが変わったフレームの後に対象行の `currentContext` へ適用する。

**「画面内にあるときはスクロールしない」を `alignmentPolicy` で表現する。**

| ヘッドの移動方向 | policy | 効果 |
|---|---|---|
| 前進（`new > old`） | `keepVisibleAtEnd` | 対象が下にはみ出しているときだけ、下端に来るまでスクロール。既に見えていれば何もしない |
| 後退（`new < old`） | `keepVisibleAtStart` | 対象が上にはみ出しているときだけ、上端に来るまでスクロール。既に見えていれば何もしない |

`ScrollPosition.ensureVisible` はこの2つの policy に対して「逆方向へは動かさない」クランプを行うため、対象が完全に見えている場合の目標値は現在位置と一致し、スクロールは発生しない。これによって、**再生中にユーザーが別の箇所を読みに行っても、対象行が画面内にある限り引き戻されない**。

この方式は「進行方向側にはみ出した場合のみ追う」ことを意味する。ユーザーが再生位置を追い越して下へスクロールし、ヘッドが表示領域より**上**に出た状態で再生が前進した場合、前進＝`keepVisibleAtEnd` はクランプされて何も起きず、ヘッドの行は画面外のままになる。これは欠陥ではなく、上記の「ユーザーが選んだ表示位置を奪い返さない」という性質の裏面である。仕様もこの通りに記述する。

`GlobalKey` は行ごとに固定して保持する。「ヘッドの行にだけ1つの `GlobalKey` を付け替える」実装は、`GlobalKey` の移動が要素の再親化を引き起こし、行の State（`TextEditingController` を持つ）ごと別の位置へ引きずられるため採らない。

**既知の限界**: `ListView.builder` は画面外の行を構築しないため、対象行が `cacheExtent`（既定250px、行にして4〜5行程度）の外にある場合は `currentContext` が null となり、スクロールは起きない。これが起きるのは**未生成セグメントが大量に連続していて、再生が遠くまで読み飛ばした場合**である。再生の通常の前進（+1行）とユーザーのクリック（クリックできたのだから見えている）では発生しない。末尾到達によるヘッドの 0 への復帰も対象が構築されていない可能性があるが、この場合は目標が必ずリスト先頭なので `animateTo(position.minScrollExtent)` で扱える。

末尾到達で 0 へ戻る場合の先頭復帰には `jumpTo(minScrollExtent)` を使う。`Scrollable.ensureVisible` の既定の `duration` は `Duration.zero`（＝即時）であり、この widget の他のスクロールもすべて即時であるため、ここだけアニメーションさせる理由がない。

大きな読み飛ばしにも追随させたくなった場合の選択肢は、(a) 概算オフセットへ `jumpTo` してから次フレームで `ensureVisible` する二段階スクロール、(b) `scrollable_positioned_list` パッケージの導入。どちらも今回は入れない。

### D8: 再生中は行の操作ボタンを無効にする

`enabled` の条件を `!isGenerating` から `!isGenerating && !isPlaying` に変える。再生中は行の [▶] [↻] [⟲] と参照音声セレクタがグレーアウトする。本文欄とメモ欄は `enabled` の制御対象ではないため、再生中も従来どおり編集できる（D4 が要求する「再生中も編集は可能」を維持する）。

**当初は「再生中も行ボタンは有効のまま」としていたが、実装中に D4 を破ることが判明したため改めた。**

当初の想定は「再生中に別の行の [▶] を押すと音が重なるが、それは [全再生] にもある既存の挙動なので触らない」というものだった。しかし `isPlaying` が単一のフラグである以上、次の順で**再生ヘッドのロックが解ける**。

```
通し再生が進行中（isPlaying = true、ヘッドはループが専有）
  → ユーザーが行 5 の [▶] を押す
  → 行の Listener は isPlaying なので抑止（ヘッドは動かない）
  → _playSegment(5) が走り、そのセグメントが終わると isPlaying = false
  → 通し再生はまだ走っているのに [停止] ボタンが消え、
     行クリックでヘッドが動くようになる
```

つまり「再生中はユーザーの押下による移動を無視する」という要件が、UI操作から破れる。これは既存の挙動の踏襲ではなく、今回導入したロックの欠陥である。

検討した代替案:

| 案 | 却下理由 |
|---|---|
| `_playSegment` 側で再生中の要求を握り潰す | 押せるのに無反応なボタンになり、なぜ鳴らないのかが画面から分からない |
| `isPlaying` をフラグでなく再生の世代カウンタにする | 単体再生と通し再生の重なりを正しく数えられるが、音が重なる問題自体は残る。ボタンを落とす方が状態も挙動も単純 |

同じ穴はツールバー側にもある。行の [▶] を押した直後（`isPlaying = true`）にツールバーの [再生] を押すと通し再生が二重に走り、先に終わった方が `isPlaying` を false にして同じロック解除を起こす。`SegmentPlayer` は `_activePlayCompleter` を1つしか持たないため、プレイヤ層でも壊れる。したがって [再生] ボタンも `isGenerating || isPlaying` で無効にする。再生中のツールバーが提供する操作は [停止] だけになる。

副次的に、共有された `SegmentPlayer` に2つの再生要求が重なる既存の問題も解消する。

**この判断は D5 の副産物も解消する。** 行ボタンが再生中に押せなくなったことで、`_playSegment` が再生ヘッドを自分で設定しても再生ループと競合しなくなった。そのため `_playSegment` は `index` をヘッドに設定する。ポインタ操作では `Listener` が既に同じ値を入れているので冗長だが、キーボードやアクセシビリティ経由で `IconButton` が起動された場合はポインタイベントが発生しないため、これが無いと**別の行に 🔊 が出たまま違う行が鳴る**。

さらに `_playSegment` / `_play` はいずれも `try/finally` で `isPlaying` を必ず false に戻す。プレビューはファイル書き込み・DB読み出し・プレイヤからのエラー転送のいずれでも例外を投げうる。フラグが立ったままになると、`enabled: !isGenerating && !isPlaying` により**何も鳴っていないのに全行の操作が無効のまま復帰しない**。

### D9: `playAll` は完走したかどうかを戻り値で返す

```dart
Future<bool> playAll({int startIndex = 0, void Function(int)? onSegmentStart})
```

`true` = 中断されずに末尾へ到達、`false` = `stopPlayback()` / `dispose()` による中断。呼び出し側はこれを見て、完走時のみヘッドを 0 に戻す（D3）。

コントローラ側にヘッドを持たせない理由は、ヘッドが表示層の状態（強調・スクロール・ボタンの起点）であり、コントローラの責務である音声再生とDBアクセスに属さないためである。コントローラは開始位置を受け取り、進行を通知し、完走可否を返すだけに留める。既存の `onSegmentStart` コールバックはそのまま流用する。

`startIndex` の既定値を 0 とすることで、既存の呼び出しとテストは無変更で通る。負値は 0 にクランプする。現在の呼び出し元はヘッド（常に有効なインデックスか 0）しか渡さないため到達しないが、同じクラスの `playSegment` が範囲外を防御している以上、片方だけが `_segments[-1]` で落ちるのは非対称である。`startIndex >= _segments.length` はループが空回りして `true` を返す（末尾に到達した、として正しい）。

## Risks / Trade-offs

- **[`ttsEditPlaybackIndexProvider` の廃止が他の参照を壊す]** → 参照は `tts_edit_dialog.dart` 内の5箇所と `tts_edit_segment_row.dart` の `isPlaying` パラメータのみ。ダイアログ外からは参照されていない。置換時に全参照を洗い出す
- **[未生成セグメントの大量スキップで自動スクロールが追随しない]** → D7 の既知の限界。発生条件が限定的（連続する未生成が5行以上）であり、その場合もユーザーは手動スクロールできる。追随が必要になった時点で二段階スクロールか `scrollable_positioned_list` へ移行する
- **[再生中に行の [↻] や [⟲] を押せなくなる]** → D8 の通り意図的に許容する。再生を止めれば操作できる。生成と再生を同時に走らせる動線は元々存在しない
- **[ヘッドが末尾到達で 0 に戻ることを利用者が予期しない]** → 強調表示と自動スクロールにより、戻ったことは画面上で明示される。また 0 に戻る挙動は「[再生] をもう一度押せば全体が鳴る」という従来の期待に一致する
- **[`TtsEditSegmentList` の切り出しで差分が「移動」に埋もれる]** → 既存 change と同様、切り出し（挙動不変）と機能追加をコミット単位で分ける
