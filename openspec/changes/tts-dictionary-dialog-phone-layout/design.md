# Design

## Context

`TtsDictionaryDialog` は `AlertDialog` の内容に `SizedBox(width: 480, height: 480)` を置き、その中の `Column` に追加フォーム（`_buildAddRow()` の1行の `Row`）、エラー文、`Expanded` のエントリ一覧を並べている。

- 幅: `AlertDialog` の左右インセット（40×2）と内容パディング（24×2）を引くと、デスクトップとiPadでは内容幅が上限の 480 になる。iPhone縦向きでは約 265pt（Pro Max でも約 302pt）。1行フォームのうち幅の固定な部品（チェックボックス、「読み上げしない」ラベル、追加ボタン、隙間）が約 204pt を取る。
- 高さ: キーボードが出ると `Dialog` が viewInsets のぶん縮み、`height: 480` は利用できる高さまで締められる。今は1行フォームが低いので崩れていない（スクリーンショット2）。しかし、フォームを縦並びにすると約 3 行ぶん高くなり、小型の iPhone では一覧に残る高さが 0 を下回る。

先例として、`tts_edit_segment_row.dart` の `LayoutBuilder` がある。`_kSingleLineRowMinWidth`（480）以上なら1行、未満なら2段にして、部品の状態を `GlobalKey` で引き継いでいる。

## Goals / Non-Goals

**Goals:**

- 狭い幅で入力欄が読める幅を持つ。
- 狭い幅でキーボード表示中もオーバーフローしない。
- 広い幅（デスクトップ / iPad）の見た目と挙動は変えない。

**Non-Goals:**

- ブレークポイントの値をアプリ全体で共有する定数にまとめること（`lib/shared/layout/` への移動）。
- 広い幅でウィンドウ高さが極端に小さい場合の対策（従来からの挙動で、今回のバグとは別）。
- ダイアログの重なり、ダイアログ自体のサイズ（480×480）の変更。

## Decisions

### 1. 切り替えはフォームに与えられた幅で決める（キーボードでは切り替わらない）

`LayoutBuilder` の `constraints.maxWidth` で判定する。キーボードが変えるのは高さだけなので、キーボードを出し入れしてもレイアウトは切り替わらない。切り替わるのは、端末の回転とデスクトップのウィンドウのリサイズのときだけ。

閾値は、このダイアログ専用のファイル内定数 `_kSingleLineFormMinWidth = 400` とし、`maxWidth >= 400` で1行にする。

- 400 にすると、固定部品（約 204pt）を引いた入力欄が1つあたり約 98pt になり、ラベルと数文字を表示できる。iPhone の最大幅（約 302pt）とデスクトップ / iPad の内容幅（480）の間にあり、どちらにも余裕がある。
- 比較を `>=` にする必要がある。デスクトップでは `maxWidth` がちょうど 480 になるため。
- 代替案: `tts_edit_segment_row.dart` の 480 を流用する。部品の構成が違う行の値を流用する根拠はない。さらに、デスクトップで `maxWidth == 480` ちょうどの境界に乗ってしまい、丸め誤差で縦並びに切り替わる危険があるため採らない。

### 2. 狭い幅のフォームは3行構成

```
+---------------------------------+
| [表記___________________________] |
| [読み___________________________] |
| [x] 読み上げしない            (+) |
+---------------------------------+
```

- 代替案: 表記と読みを左右に並べ（約 130pt ずつ）、2段にする。フローティングラベルと入力内容が窮屈になり、長い表記（記号の連なりなど）が読めない。全幅の3行のほうが確実なため採らない。
- 3行目は、チェックボックスとラベルを左、追加ボタンを右に寄せる。

### 3. 狭い幅では内容全体をスクロールさせる

狭い幅では、内容を `CustomScrollView` にする。追加フォームとエラー文を `SliverToBoxAdapter`、エントリを `SliverList` に入れる。一覧が空のときは、案内文を `SliverFillRemaining(hasScrollBody: false)` に入れる。

- フォームの高さがダイアログに残る高さを上回っても、はみ出す代わりにスクロールになる。フォーカスした `TextField` は、祖先の `Scrollable` によって見える位置まで自動でスクロールされる（`EditableText` の showOnScreen）。そのため、キーボード表示中も入力中の欄が見える。
- 広い幅は従来どおり、固定フォームの下に `Expanded` の一覧を置く構成のまま。デスクトップで一覧が長くなってもフォームが上に流れて消えないという、今の使い勝手を保つ。
- 代替案 A: `AlertDialog(scrollable: true)` にする。内側の `ListView` と `Expanded` の一覧と両立しないため採らない。
- 代替案 B: 縦並びのフォームを固定し、一覧だけ `Expanded` のままにする。小型の iPhone ではキーボード表示中に一覧の高さが 0 を下回り、空の案内文の `Center(Text)` がオーバーフローするため採らない。
- 代替案 C: 両方の幅で `CustomScrollView` に統一する。コードは単純になるが、デスクトップでフォームが一覧と一緒にスクロールして消える。広い幅の挙動は変えないという目標に反するため採らない。

### 4. 部品の状態を `GlobalKey` で引き継ぐ

「表記」欄、「読み」欄、チェックボックスに `GlobalKey` を付け、1行と3行の木を作り直しても同じ `Element`/`State` が移るようにする（`tts_edit_segment_row.dart` と同じ方式）。入力内容はコントローラがダイアログの `State` にあるため、もともと残る。`GlobalKey` が守るのは、フォーカス・選択範囲・IME変換中の文字。切り替えのきっかけは回転とウィンドウのリサイズである（キーボードではない）ことをコメントに書く。

### 5. テスト方針

`tts_dictionary_dialog_test.dart` に次のテストを追加する。

- `tester.binding.setSurfaceSize(Size(393, 852))` で狭い幅を作り、「読み」欄の上端が「表記」欄の下端以上にあること、両方の欄が hit-testable であることを確認する。ピクセル幅は確認しない。テスト用フォントは実機と幅が違うため。
- 800×600 で、4つの部品が同じ行に並ぶことを確認する（各部品の縦方向の中心がそろっている）。既存のテストは変更せずに通ること。
- キーボード表示は `tester.view.viewInsets = FakeViewPadding(bottom: 336 × devicePixelRatio)`で再現する（336 は日本語かなキーボードと変換候補バーの高さ。後片付けは `addTearDown(tester.view.resetViewInsets)`）。393×852 と 375×667 の両方で、エントリなしとエントリ多数のそれぞれについて `tester.takeException()` が null であること、両方の入力欄に到達できることを確認する。
- 入力後に surface size を 800×600 から 393×852 に変え、入力内容が残っていることを確認する。

## Risks / Trade-offs

- [テスト環境のフォント幅が実機と違い、閾値付近の判定がずれる] → 判定は `maxWidth` だけで決まり、文字幅に依存しない。テストでは、閾値から十分に離れた幅（393 / 800）だけを使う。
- [`SliverFillRemaining` の空表示が、極端に低い高さでもはみ出す] → `hasScrollBody: false` は、子の固有の高さが残りの高さを上回るとスクロールに回すので、オーバーフローしない。375×667 とキーボード表示の組み合わせのテストで確かめる。
- [狭い幅ではフォームも一覧と一緒にスクロールし、長い一覧の下のほうを見ているときはフォームが画面外にある] → 狭い幅で縦の空間を一覧に最大限使うための意図した挙動として受け入れる。追加操作はフォームが見えている状態で行うため、追加のたびにスクロールし直すことはない。
- [実機の見え方はウィジェットテストでは保証しきれない] → 最終確認で iPhone 実機に入れ、キーボード表示の有無の両方でスクリーンショットと同じ操作を確認する。
