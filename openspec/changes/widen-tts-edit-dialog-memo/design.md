## Context

読み上げ編集ダイアログ（`lib/features/tts/presentation/tts_edit_dialog.dart`）は次の構造になっている。

```
AlertDialog
  content: SizedBox(width: 800, height: 600)   // :331
    Column
      _buildToolbar(...)
      Divider
      Expanded > ListView.builder
        _TtsEditSegmentRow  (private, 同一ファイル内 :452-699)
```

セグメント行（`_TtsEditSegmentRowState.build` :553-695）の横方向の構成と現在の幅は次の通り。

```
[status 20 + padding 8] [本文 Expanded flex:4] [gap 8] [参照音声 120]
  [gap 8] [メモ SizedBox 100] [gap 4] [▶ 32][⟳ 32][↺ 32]
```

固定要素（アイコン、参照音声ドロップダウン、操作ボタン3つ、各隙間）の合計は実測 **312px**。したがって本文とメモが分け合える幅は `content幅 - 312` である。

Irodori-TTS 導入後、メモ欄の内容は `TtsEngineConfig.captionFromMemo`（`tts_edit_controller.dart:468`）経由でキャプションとして合成に渡るようになり、「落ち着いた女性の声で、ゆっくり悲しげに」のような自然文（最大20〜30文字程度）を入力する欄になった。しかしメモ欄は幅100px固定・`maxLines` 未指定（＝1行固定）のままである。`fontSize: 12` の日本語は1文字あたり約12pxなので、**100px では実質7文字しか見えない**。

一方、本文欄は `maxLines: null` で折り返す。同じ行の中でテキスト入力欄の折り返し挙動が非対称になっている。

制約:

- ユーザの常用解像度は 3440x1440。ただし通常は1ウィンドウをその半分程度（実効1500〜1700px）で使う
- メモに入力する文字数は最大20〜30文字程度で、本文より明確に補助的な位置づけ
- 高さ600は現状で不足していない

## Goals / Non-Goals

**Goals:**

- メモ欄で20〜30文字のキャプションが一目で全て読めること
- 広いウィンドウではダイアログが広がり、狭いウィンドウでは画面外にはみ出さないこと
- 本文欄の優先度を維持したまま、余剰幅をメモ欄にも配分すること
- レイアウトを自動テストで検証できる状態にすること

**Non-Goals:**

- キャプションのプリセット選択UIやテンプレート機能の追加
- 参照音声ドロップダウン（幅120、ファイル名が省略表示される）の改善
- ダイアログの高さの変更、リサイズ可能化、サイズの永続化
- メモの永続化タイミング（フォーカスアウト/Enter）や `captionFromMemo` の変換規則の変更
- 行の2段組み化などレイアウト構造そのものの再設計

## Decisions

### D1: ダイアログ幅を `width: 1400` の上限指定のみとする

`width: 800` を `width: 1400` に引き上げる。それ以上のことはしない。

**当初は `min(1400, ウィンドウ幅 * 0.9 - 48)` という可変式を採用していたが、その前提が誤りだったため撤回した。**

当初の想定は「上限だけでは狭いウィンドウで画面外にはみ出す。現状の `800` 固定にも同じ問題があり既存の潜在バグである」というものだった。しかし実測の結果、**`AlertDialog` は自身をウィンドウ内に収める機構を既に持っている**ことが確認できた。

- `Dialog` はデフォルトの `insetPadding`（`EdgeInsets.symmetric(horizontal: 40, vertical: 24)`）を適用するため、ダイアログの最大幅は `ウィンドウ幅 - 80` になる
- content の `SizedBox` は `RenderConstrainedBox` として親の制約に `enforce` されるため、指定幅が上回れば単純にクランプされる

`AlertDialog` に `SizedBox(width: N)` を与えて実測した結果:

| ウィンドウ幅 | 指定 | 実際の content 幅 | はみ出し |
|---|---|---|---|
| 700 | 800 | 572 | なし |
| 900 | 800 | 772 | なし |
| 1200 | 1400 | 1072 | なし |
| 1720 | 1400 | 1400 | なし |
| 3440 | 1400 | 1400 | なし |

したがって可変式が担っていた「はみ出し防止」はフレームワークが既に提供しており、式が生んでいた差は**最大40px**にすぎなかった。その40pxのために以下を抱えることになる:

- `MediaQuery.sizeOf` の購読（ウィンドウリサイズのたびにダイアログ全体が再ビルド）
- テスト専用に公開する top-level 関数
- 定数 `48`（`AlertDialog` のデフォルト `contentPadding` への依存）。しかもこの値は文字スケールに応じて縮む（`_scalePadding` により scale 2.0 で 48→16）ため厳密には定数ですらない
- 式が式自身を検証しているだけの境界値テスト5件

**上限1400を設ける理由**（この判断は維持）: 3440px の画面で全画面表示した場合、上限がなければ行が3000px級になる。行の右端に再生/再生成/リセットボタンが並ぶ構造上、視線移動が増えてむしろ使いにくい。1400px あれば本文とメモの双方が十分な幅を得られる（後述の幅予算参照）。

検討した代替案:

| 案 | 却下理由 |
|---|---|
| `min(1400, 幅 * 0.9 - 48)` | 上記の通り。得られる差は最大40pxで、部品数と内部実装への依存に見合わない |
| `insetPadding` で 0.9 を表現 | `- 48` は消えるが `MediaQuery` 購読と計算は残る。実益はやはり最大40px |
| 上限なし | 超ワイド画面で行が3000px級になり、視線移動が過大 |

高さは 600 のまま据え置く（ユーザ確認済み）。幅と同様、高さもフレームワークがウィンドウ内にクランプする。

### D2: メモ欄を `Expanded(flex: 2)`、本文を `flex: 5` にする

メモ欄の `SizedBox(width: 100)` を `Expanded(flex: 2)` に置き換え、本文の `flex` を 4 から 5 に上げる。

固定幅240px のような値を与える案もあったが、**ダイアログが縮んだときに固定幅が本文欄を圧迫する**。補助的な欄であるメモが、狭い画面で本文と同等の絶対幅を主張するのは配分として逆である。flex にすれば広い時も狭い時も一貫して「本文優先」を保てる。

5:2 とした幅予算（本文+メモ = content幅 - 312。312は実測値で、アイコン・参照音声ドロップダウン・操作ボタン・各隙間の合計）:

| ウィンドウ幅 | content幅 | 本文 | メモ | メモ収容量(2行) |
|---|---|---|---|---|
| 3440（全画面） | 1400（上限） | 777px | 311px | 約48文字 |
| 1720（常用） | 1400（上限） | 777px | 311px | 約48文字 |
| 1200 | 1072 | 約543px | 約217px | 約33文字 |
| 900 | 772 | 約329px | 約131px | 約19文字 |

1400 と 777/311 は実測値。それ以外はフレームワークのクランプ（content幅 = ウィンドウ幅 - 80 - 48）からの計算値。

常用幅では上限1400が効くため、実質「1400固定 + 狭い画面での自動縮小」として振る舞う。目標の30文字は余裕を持って2行に収まる。

### D3: メモ欄を `maxLines: 2` にする

幅を広げるだけでは不十分で、**1行固定をやめることが本質的な修正**である。幅311pxでも1行では約24文字が限界であり、30文字入力すると末尾が見えなくなる。2行にすれば同じ幅で約48文字を収容できる。

- `maxLines: null`（無制限）を選ばない理由: 長文を貼り付けた際に行の高さが際限なく伸び、高さ600の一覧に収まるセグメント数が減る。想定入力は30文字程度なので上限2で足りる
- `maxLines: 3` を選ばない理由: 2行で想定入力を十分に賄えるため、行高の増加を最小に抑える方を採る

実装上の注意: `maxLines: 2` だけを指定すると、Flutter の `TextField` は**高さを2行分に固定する**（`minLines` が null の場合、内容が1行でも2行分の高さを確保する）。これではメモが空の行まで一律に高くなってしまう。1行から2行へ内容に応じて伸縮させるには `minLines: 1` の併記が必須である。

`minLines: 1, maxLines: 2` とすることで**メモが空の行の高さは現状のまま変わらない**。行が高くなるのは実際に折り返した行だけで、一覧性への影響は限定的である。

### D4: メモ欄に下限幅を設けない

`ConstrainedBox(minWidth: ...)` による下限は設けない。ウィンドウ幅900px以下ではメモが約19文字分まで縮むが、その状況では本文欄（約329px）も同様に苦しい。片方だけに下限を与えると、狭い画面で本文が不自然に潰れる。**揃って縮む方が挙動として素直**という判断。

### D5: `_TtsEditSegmentRow` を public な `TtsEditSegmentRow` として別ファイルに切り出す

`lib/features/tts/presentation/tts_edit_segment_row.dart` を新規作成し、`_TtsEditSegmentRow` を `TtsEditSegmentRow` として移動する。ロジックは一切変更しない機械的な移動とする。State クラスは `_TtsEditSegmentRowState` のまま private に保つ（テストが必要とするのはウィジェット型だけであり、State を公開すると `GlobalKey<...State>` 経由の結合を招く）。

理由は**テスト可能性**である。プロジェクトの必須ルールはTDDだが、現状の `TtsEditDialog` はウィジェットテストで pump できない。

```
_TtsEditDialogState._initialize()  (:70-133)
  ├─ ref.read(ttsAudioDatabaseProvider(folderKey))   → 実DBが必要
  ├─ ref.read(ttsDictionaryDatabaseProvider(...))    → 実DBが必要
  ├─ ensureTemporaryDirectory()                      → path_provider が必要
  ├─ TtsIsolate()          ← 直接 new。差し替え不可
  └─ JustAudioPlayer()     ← 直接 new。差し替え不可
```

一方、切り出し対象の行ウィジェットが必要とするのは `TtsEditSegment`（純粋なデータクラス）、`List<String> voiceFiles`、各種コールバック、nullable な `TtsDictionaryRepository` のみで、**単体で pump できる**。今回変更するメモ欄の幅比・行数はすべてこの行ウィジェット内にあるため、切り出しによって修正対象そのものを実測できる。

検討した代替案:

| 案 | 却下理由 |
|---|---|
| ダイアログ全体を依存注入可能にする | `TtsIsolate` / `JustAudioPlayer` / repository の注入は改修範囲が大きく、レイアウト修正に対して初期化フローへ手を入れる回帰リスクが釣り合わない |
| 幅計算のみ純粋関数化し行は目視確認 | 本体である「メモ欄が実際に広く2行になる」ことが自動検証されない |
| private のままテストする | Dart の private は同一ライブラリ外から参照できず、テストファイルからは触れない |

### D6: 幅の検証はレイアウト実測テストのみとし、幅の計算関数は持たない

D1 で幅が単なる定数になったため、計算関数とその境界値テストは不要になった。検証対象は「行の中で本文とメモがどう幅を分け合うか」であり、これは `TtsEditSegmentRow` を実際に描画してサイズを実測するウィジェットテストで直接確かめる。行は幅に対して純粋に相対的（flex のみ、下限なし）なので、テストは任意の幅（700/900/1000/1300）で同じ性質を検証できる。

## Risks / Trade-offs

- **[切り出しにより差分が「移動」で膨らみ、レビューで実質的な変更が埋もれる]** → 切り出しコミットとレイアウト変更コミットを分け、切り出し時点では挙動を変えない。TDDの手順上もこの順序が自然
- **[メモが折り返すと行の高さが増え、一覧に収まるセグメント数が減る]** → `maxLines: 2` で増加分を1行に限定。メモが空の行は高さが変わらないため、影響を受けるのはキャプションを設定した行のみ
- **[非常に狭いウィンドウでメモが19文字分まで縮む]** → D4の通り意図的に許容する。本文も同時に縮むため相対的な配分は保たれる
- **[content幅 1400 がウィンドウに収まるかはフレームワークのクランプに依存する]** → `Dialog` の `insetPadding` と `RenderConstrainedBox` の `enforce` という Flutter の基本挙動であり、実測で確認済み。`insetPadding` を明示的に上書きした場合のみ再確認が必要
