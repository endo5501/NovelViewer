## Context

用語解析の LLM 呼び出しは `LlmClient` という一つの抽象の後ろにある。実装は `OllamaClient` と `OpenAiCompatibleClient` の二つで、どちらも HTTP でサーバに問い合わせる。その上に `LlmSummaryPipeline`（二段の抽出と要約）と `LlmSummaryService`（検索、ファイル単位の束ね、fact キャッシュ、スナップショット保存）が乗っている。

`PlatformCapabilities` の doc コメントには、すでに次の記述がある。「LLM 要約という能力は全プラットフォームで真になった。それでも残してあるのは、オンデバイスモデルが本当の区別を再導入するからだ。モデルを走らせられるかどうかはプラットフォームではなくハードウェアに依る」。この設計はその予告の続きにあたる。

Apple Foundation Models の API は Xcode 26.6 に同梱される iOS 26.5 / macOS 26.5 SDK のインターフェイスファイルで確認済み。主要な型はすべて `@available(iOS 26.0, macOS 26.0, *)` である。

- `SystemLanguageModel.default.availability` は `.available` または `.unavailable(理由)` を返し、理由は `deviceNotEligible` / `appleIntelligenceNotEnabled` / `modelNotReady` の三つ。
- `LanguageModelSession.respond(to:schema:includeSchemaInPrompt:options:)` は `Response<GeneratedContent>` を返す。
- `GeneratedContent` は `jsonString` を持つ。
- `DynamicGenerationSchema(name:description:properties:)` と `GenerationSchema(root:dependencies:)` で、実行時にスキーマを組み立てられる。
- `LanguageModelSession.GenerationError` には `exceededContextWindowSize` / `guardrailViolation` / `assetsUnavailable` / `rateLimited` / `concurrentRequests` / `decodingFailure` / `unsupportedLanguageOrLocale` がある。
- 文脈の窓は入出力あわせて 4,096 トークン。

対象読者は iPad mini (A17 Pro) と、macOS 26 の動く Mac を持つ開発者兼利用者。

## Goals / Non-Goals

**Goals:**

- サーバを用意せずに、対応端末だけで用語解析が完結すること。
- 既存の `LlmClient` / `LlmSummaryPipeline` / fact キャッシュ / 履歴を一切作り替えずに済ませること。
- 使えない理由が読者に伝わること。とくに「待てば使える」状態と「この端末では使えない」状態が区別できること。
- オンデバイスを選んだ読者の本文が、本人の明示的な操作なしに外部へ出ないこと。
- iOS と macOS が同じ Swift 実装を共有すること。

**Non-Goals:**

- ストリーミング生成。`LlmClient.generate` は応答全体を返す契約であり、パイプラインもそれを前提にしている。オンデバイスの遅さを体感で和らげる効果はあるが、契約を変えるほどの範囲は今回持たない。
- `fact_cache` にモデルの区別を入れること。別の変更として扱う。
- Windows / Linux / Android への対応。プラグインの実装を置かない。
- オンデバイスとサーバの自動的な使い分け。
- Foundation Models の tool calling。

## Decisions

### 決定1: 三つ目の `LlmClient` 実装として入れる

`FoundationModelsClient implements LlmClient` を作る。パイプラインもサービスもキャッシュも知らないまま動く。

代替案として、オンデバイス生成を別の機能系統として立てることを検討したが、採らない。解析の骨格（検索、ファイル単位の抽出、事実の畳み込み、スナップショット）はモデルがどこで走るかと無関係であり、二系統に割ると同じロジックが二つになる。抽象がすでに正しい位置にあるので、そこに実装を足すのが最小の変更になる。

### 決定2: ネイティブは共有 `darwin/` を持つ社内プラグインに置く

```
packages/foundation_models_llm/
├── lib/        Dart。MethodChannel の薄い口
├── darwin/     Swift 一式。iOS と macOS が同じものを参照
├── ios/        podspec が darwin/ を指す
└── macos/      同上
```

代替案A、`ios/Runner/AppDelegate.swift` と `macos/Runner/MainFlutterWindow.swift` に直接書く。Swift が二重になり、単体テストの置き場もない。却下。

代替案B、pub.dev の既存パッケージに依存する。Foundation Models 自体が新しく、この用途に必要な `DynamicGenerationSchema` まで面倒を見るものは見当たらない。プロジェクトは TTS や LAME のビルドスクリプトを自前で持っており、ネイティブを所有する方針と整合しない。却下。

これはこのプロジェクト初の MethodChannel になる。既存のネイティブ連携はすべて FFI（TTS エンジン）であり、非同期のメソッド呼び出しという形は初めて入る。

デプロイメントターゲットは iOS 13.0 と macOS 10.15 のまま変えない。Swift 側を `if #available(iOS 26.0, macOS 26.0, *)` で囲み、満たさない環境では「非対応」を返す。ターゲットを上げると対応端末以外でアプリが起動しなくなるため、これは譲れない。

### 決定3: 可用性を三層に割り、層1 だけを純粋モデルに入れる

```
層1  Apple プラットフォームか        → PlatformCapabilities.forPlatform (同期・純粋)
層2  deviceNotEligible               ┐
層3  appleIntelligenceNotEnabled     │→ 非同期プロバイダ (ネイティブ問い合わせ)
     modelNotReady                   ┘
```

`PlatformCapabilities.forPlatform` は現在 `isIOS` だけを取る。`isMacOS` を足し、`onDeviceLlm = isIOS || isMacOS` を導出する。既存仕様の「`Platform` を読むのは一箇所だけ」はこれで保たれる。

代替案として、層1 を捨ててプラグインの `MissingPluginException` を「非対応」の合図に使うことを検討したが、却下。例外を制御フローに使うことになり、通信路の障害と非対応が区別できなくなる。

層2 と層3 を純粋モデルに入れないのは、これらがプラットフォームフラグから導けないため。ネイティブへの非同期な問い合わせが要り、層3 は読者の操作やモデルのダウンロードで可と不可を往復する。既存仕様の「純粋関数」という性質を壊さないために、外に置く。

層1 が偽なら問い合わせ自体を行わない。

### 決定4: 使えないときは理由を添えて選択不可にする

理由の分かれ目は、読者がその状態を抜け出せるかどうかに置く。

| 状態 | 扱い |
|---|---|
| Apple Intelligence が無効 / モデル準備中 / 不明 | 項目を出し、選択不可にして理由を添える |
| 端末が非対応 / OS が古い / プラットフォームが非対応 | 項目自体を出さない |
| 問い合わせ中 | 項目を出さない |

選べないときは `DropdownMenuItem.enabled` を偽にし、理由の文面はドロップダウンの外、セクション本体に一行として置く。理由を出すのは、説明すべき項目が見えているときだけに限る。Ollama を使っている読者の設定画面に、自分には関係のない一文が居座るのは雑音でしかない。

恒久的な状態で項目を消すのは、「待てば使える」という伝えるべき中身がないからである。レビューでの指摘がここを動かした。当初は端末非対応も理由付きで見せる設計だったが、それでは 26 より前の OS を使っている大多数の読者に、永久に死んだ項目と「現在利用できません」という誤った文面を見せ続けることになる。

OS がフレームワークを持っているかどうかは、プラットフォームフラグからは分からない。層1 が真でもネイティブが `unsupportedPlatform` を返すことがあり、その答えが出た時点で項目を取り下げる。

問い合わせ中に項目を出さないのは、出してから引っ込めるほうが、少し遅れて出すより印象が悪いからである。26 より前の OS では必ず引っ込めることになる。

ただし読者が選んでいるプロバイダは、答えが何であれ常に一覧に載せる。`DropdownButton` は値に対応する項目が存在することを要求するので、別のマシンから引き継いだ選択値で項目が消えると設定ダイアログごと落ちる。

理由をドロップダウンの項目内に入れる案は採らない。`DropdownButton` の項目は既定で高さが固定であり、二行の文面を入れると項目の高さを可変にする必要が出る。加えて、ドロップダウンを開かないと理由が読めないのでは、伝える意味が薄い。

既存仕様の「使えない機能は無効化ではなく非表示にする」原則とは衝突しない。あの原則が支配するのは機能の面の有無であり、LLM 設定セクション自体は出ている。今回不可になるのはセクション内の選択肢一つで、粒度が違う。そして `modelNotReady` は待てば解消する状態なので、黙って消すとその事実を伝える手段が完全に失われる。

層1 が偽（Windows / Linux）のときは項目自体を出さない。こちらは恒久的に不可であり、伝えるべき「待てば使える」性質がない。

### 決定5: 自動フォールバックをしない。保存された選択も書き換えない

オンデバイスを選んだあとに可用性が失われても、サーバへ自動的に切り替えない。`llmClientProvider` は null を返し、解析は理由の分かる失敗になる。

オンデバイスを選ぶ動機は本文を外に出さないことである。使えなくなった瞬間に以前設定したサーバへ黙って本文を送り始める実装は、利便性ではなく事故になる。

保存済みの選択値も書き換えない。Apple Intelligence を一時的に切っただけの読者の意図を失わせないため。可用性が戻れば、設定を触らずにそのまま動く。

### 決定6: `LlmResponseSchema` を `DynamicGenerationSchema` に写す

`LlmResponseSchema.singleStringField(fieldName)` のフィールド名は実行時に決まる（`facts` と `summary`）。コンパイル時マクロの `@Generable` は使えないので、`DynamicGenerationSchema` で文字列プロパティ一つのスキーマを組み、`GenerationSchema(root:dependencies:)` に通して `respond(to:schema:)` に渡す。

戻りの `GeneratedContent.jsonString` は `{"facts": "..."}` の形をしており、これをそのまま Dart に返せばパイプラインの `jsonDecode` がそのまま通る。Swift 側に変換を書く必要がない。

副産物として、Ollama 相手に用意してある「JSON デコードに失敗したら生テキストに落とし、キャッシュしない」退避経路が、このクライアントでは実質発火しなくなる。構造がモデルの努力目標ではなく文法上の制約になるため。

`schema` が null のときは `respond(to:)` を使い、生成テキストをそのまま返す。

### 決定7: セッションは呼び出しごとに作り直す

`LanguageModelSession` は会話履歴を溜める。パイプラインが投げる各プロンプトは互いに独立なので、履歴を持ち越すと 4,096 トークンの窓を無駄に食うだけになる。`generate` のたびに新しいセッションを作る。

`prewarm()` は今回使わない。セッションが毎回新しい以上、事前ウォームの効果が乗る先がない。将来ストリーミングを入れるときに再検討する。

`releaseResources()` では保持しているセッション参照を捨てる。モデル本体はシステムが持つので、解放の主目的はメモリではなく、参照を残さないこと。

### 決定8: 文脈予算を `LlmClient` の性質にする

`LlmSummaryService` は現在 `LlmSummaryPipeline` を既定値のまま組み立てており、チャンク幅は 4,000 文字に固定されている。オンデバイスの窓は入出力あわせて 4,096 トークンで、日本語はおおよそ 1 文字 1 トークンなので、この幅では最初の一回で溢れる。

| 内訳 | 概算トークン |
|---|---:|
| プロンプト定型文 | 200 |
| contextChunk（4,000 文字） | 4,000 |
| 生成する facts | 300〜600 |
| 合計 | 4,500〜4,800 |

`LlmClient` に文脈予算を表す値を持たせ、既定を現行の 4,000 とする。`LlmSummaryService` はそれを読んで `LlmSummaryPipeline` に渡す。既存二クライアントは既定値を返すので挙動は変わらない。

**実測で上の見積もりは外れた。** macOS 上で、繰り返しのない日本語の散文を渡して測ったところ、要求が失敗し始めるのは 5,000 文字と 6,000 文字の間だった。つまり日本語はおよそ 0.7 トークン/文字で、1 トークン/文字という前提が保守的すぎた。

最初に測ったときは同じ一文を繰り返した文章を使い、10,000 文字でも通ってしまった。部分語トークナイザにとって繰り返しはほぼ無コストなので、この測り方では上限が出ない。文章に変化を持たせて測り直している。

採用する値は 3,000 文字。天井の 5,000〜6,000 に対して意図的に余裕を取る。漢字の密度が高い文章はサンプルより悪くトークン化されるので、その差を吸収するのが余裕の役目になる。これ以上下げても安全は買えず、チャンクあたり一回の呼び出しが増えるだけで、しかも実行時間の大半はモデルが占める。

出力側は `GenerationOptions.maximumResponseTokens` で抑え、窓の配分を予測可能にする。ただし締めすぎてはいけない。応答が上限に当たると構造化オブジェクトが閉じる前に切れ、「上限に当たった」ではなく「応答が解析できない」という形で返ってくる。

代替案として、溢れたら（`exceededContextWindowSize` を捕まえたら）幅を半分にして再試行する自己調整を検討した。魅力的だが、既存の「一度だけ再試行する」仕様と絡み合い、再試行の意味が二重になる。今回は静的な予算に留め、`exceededContextWindowSize` は予算の設定ミスを示す失敗として扱う。

### 決定9: 生成エラーを読者が読める失敗に写す

| Swift の case | 読者への意味 |
|---|---|
| `guardrailViolation` / `refusal` | 内容が安全ポリシーに触れたため、この部分は解析できない |
| `decodingFailure` | 応答が途中で切れた。応答上限に当たったときに出る |
| `exceededContextWindowSize` | 一度に渡す量が多すぎた（設定の問題） |
| `rateLimited` | いまは混み合っている。時間をおく |
| `unsupportedLanguageOrLocale` | この言語には対応していない |
| `assetsUnavailable` | モデルがまだ用意できていない |

`guardrailViolation` はファイル単位の抽出失敗として既存の経路を流れる。`LlmSummaryService` はファイル単位の失敗を記録して残りを続行し、最後に部分失敗として報告する仕組みをすでに持っているので、そこに乗る。

### 決定10: 結果の変わらない失敗は再試行しない

パイプラインは失敗を一度だけ再試行する。この既定は、この層で起きることの多くが一過性であるという前提に立っている。オンデバイスではその前提が崩れる原因がある。同じ本文は同じように拒否され、窓を超えたプロンプトは二度目も超える。

再試行するのは、答えが変わりうる原因だけに絞る。レート制限は待てば通り、応答が解析できない失敗はモデルがどれだけ喋ったか次第なので、どちらも一度はやり直す価値がある。拒否・窓超過・非対応言語・モデル不在はやり直しても同じなので、そのまま上に投げる。

これが効くのは、オンデバイスが三つのプロバイダの中で最も遅く、しかも連続失敗が既定の三回に達するまで解析が止まらないからである。無駄な再試行を挟むと、読者が「これは動かない」と知るまでの待ち時間が倍になる。

判定はパイプラインがオンデバイスの事情を知らずに済む形にする。失敗の側が「同じ要求をもう一度出す意味があるか」に答え、パイプラインはそれを尋ねるだけにした。

### 決定11: 読者に見せる失敗文面はプロバイダで変える

クライアントが作れなかったとき、既存の文面は「設定画面で LLM を設定してください」と言う。オンデバイスを選んでいる読者に対してはこれが誤りになる。設定は済んでおり、止めているのは Apple Intelligence が切れていることだからである。行き先のない案内を出すより、どの理由で使えないのかを名指しする。

サーバのプロバイダに対しては文面を変えない。

## Risks / Trade-offs

- **`guardrailViolation` が日常的に起きる** → Web 小説には暴力や性的な描写が普通に含まれる。オンデバイスモデルの安全ガードレールは迂回できない。緩和は二段構え。原因が分かる文面で伝えること、そしてファイル単位の失敗として扱い、他のファイルの解析を止めないこと。全ファイルが拒否される作品では、この機能はその作品に対して使えない。これは受け入れる制約であり、隠すべきではない。
- **初回解析が長い** → チャンク幅を半分にすると一ファイルあたりの呼び出し回数が倍になり、最終要約の畳み込み段数も増える。オンデバイス生成はサーバより遅いので、掛け算で効く。緩和は fact キャッシュ（二回目以降）と、読者が解析範囲を話数で絞れる既存の仕組み。実測して、許容できない場合は予算とプロンプトを見直す。
- **3B 級モデルの要約品質** → サーバの大型モデルとは差が出る。とくに複数話にまたがる人物関係の把握で顕著になりうる。緩和はしない。読者が選択でき、いつでもサーバに戻せることが答えになる。
- **A17 Pro は対応端末の下限** → iPad mini はメモリも最小構成。ここで成立すれば上位機では成立する。逆に言えば、ここでの実測が最悪ケースになる。テスト端末としては都合が良い。
- **macOS のサンドボックス** → アプリは entitlement を持つサンドボックス構成。Foundation Models が専用の entitlement を要求するかは未確認。実装の最初に確かめる。要求された場合は `DebugProfile.entitlements` と `Release.entitlements` の両方に足す。
- **初の MethodChannel** → テスト戦略の前例がない。Dart 側はチャンネルをモックして単体テストする。Swift 側のロジック（スキーマ組み立て、エラー写像）は薄く保ち、検証は実機での確認に頼る。
- **`if #available` の抜け** → iOS 26 未満の端末でクラッシュしないことは、シンボルを条件分岐の外で参照しないことに掛かっている。Swift の可用性チェックはコンパイラが強制するので、ビルドが通れば守られる。

## Migration Plan

データベースのスキーマ変更はない。保存済みの設定も読み替えを要さない。`LlmProvider` は列挙子の名前で永続化されており、値の追加は既存の保存値に影響しない。未知の名前は既存の `orElse` で `none` に落ちるため、将来この選択肢を消しても壊れない。

段階を分けて進める。

1. プラグインパッケージと可用性の問い合わせだけを通す。設定にも解析にも繋がない。macOS で先に疎通を確認する（Mac で完結するので回転が速い）。
2. 生成を通す。Dart 側の単体テストはチャンネルのモックで行う。
3. 文脈予算を `LlmClient` に足し、サービスから渡す。既存二クライアントの挙動が変わらないことをテストで固定する。
4. 設定と可用性の表示を繋ぐ。
5. iPad mini で実測する。

戻す場合は設定を別のプロバイダに変えるだけでよい。既存の解析結果は保存済みのまま読める。

## Open Questions

すべて実測で解決した。記録として残す。

- **macOS のサンドボックスで entitlement が要るか** → 要らない。既存の entitlement のまま、サンドボックス下の macOS アプリから `available` が返り、生成も通った。
- **文脈予算の実効値** → 上限は 5,000〜6,000 文字の間。採用値は 3,000 文字（決定8 を参照）。
- **日本語を含む三言語** → 日本語・英語・中国語のいずれでも `unsupportedLanguageOrLocale` は出ず、それぞれの言語で応答が返った。

代わりに、実測で新しい事実が二つ出た。どちらも仕様に反映してある。

- **ガードレールは実際に作動する。** 「剣を抜き、盗賊の首を刎ねた」程度の、Web 小説にありふれた戦闘描写で `guardrailViolation: Detected content likely to be unsafe` が返った。設計時には理論上の懸念として書いたが、実在する。ファイル単位の失敗として隔離する判断が効いてくる。
- **恒久的に使えない状態と一時的な状態は、扱いを分けるべきだった。** 当初の設計は不可の理由をすべて「見せて選べなくする」で揃えていた。レビューで、26 より前の OS では永久に死んだ項目が残り続けると指摘され、恒久的なものは隠す形に変えた（決定4 を参照）。
- **応答上限に当たると `decodingFailure` になる。** 構造化オブジェクトが閉じる前に切れるため、「上限」ではなく「解析できない応答」として返る。発生はモデルの饒舌さ次第で、同じ入力でも出たり出なかったりする。パイプラインが既に持っている一回の再試行が、この非決定性に対しては素直に効く。

  上限を 1,000 から 1,500 に上げても発生率は下がらなかったので、上限そのものが原因ではない。再現に使った合成文は同じ型の文を百回以上並べたもので、モデルがその一つ一つを別の事実として書き出そうとする。実際の小説の文脈ではそうならず、end-to-end の試行は毎回 1 秒で通っている。上限は 1,000 のままとする。3,000 文字のチャンクは漢字の密度が高い場合に 2,700 トークン程度まで膨らみうるので、定型文と応答を足して窓に収めるには 1,000 が上限になる。
