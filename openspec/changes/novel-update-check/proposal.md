# Proposal

## Why

登録した小説に新しい話が投稿されても、今は小説ごとに「更新」を実行しないと、そもそも更新があったかどうかがわからない。登録数が増えるほど、読みたい小説に新着があるかを確かめる手間が大きくなる。本文はダウンロードせずにライブラリ全体の新着の有無だけを確かめ、その結果をライブラリ上で常に見えるようにしたい。

## What Changes

- ファイルブラウザのツールバーに「新着チェック」ボタンを追加する（アプリ自体のアップデートの確認と紛れない名前にする）。押すと、ライブラリ全体の登録小説について、サイト上の総話数だけを取得する（本文は取得しない）。ダウンロード中は開始せず、既存の警告を出す。
- チェック中は進捗（`n / N`）とキャンセルを備えたモーダルダイアログを表示する。終了時には、新着があった作品数と、確認できなかった作品数を表示する。
- 取得した総話数とチェック日時を `novel_metadata.db` の `novels` に保存する。スキーマを v12 から v13 に上げ、列を追加する。
- `取得した総話数 > novels.episode_count` の小説は「新着あり」とし、ファイルブラウザの進捗バッジに NEW の印を表示する。話数は表示しない。小説を更新（再ダウンロード）すると `episode_count` が追いつくので、印は自動的に消える。
- 総話数の取得方法:
  - なろう（`ncode.syosetu.com` / `novel18.syosetu.com`）: 公式の小説API（一般向け / R18向け）に複数の ncode をまとめて問い合わせる
  - カクヨム / ハーメルン: 目次の1ページを取得し、既存の `parseIndex` で数える
- 汎用Web（記事コレクションを含む）と青空文庫はチェックの対象外とする。
- チェックは手動のみとする。起動時の自動チェックは今回含めない。

## Capabilities

### New Capabilities

- `novel-update-check`: ライブラリ全体の新着チェックを定める。開始の入口、対象の選び方、サイト別の総話数の取得、進捗とキャンセル、結果の保存、終了時の要約、失敗時の扱いを含む。

### Modified Capabilities

- `novel-metadata-db`: `novels` テーブルに、チェックで取得した総話数とチェック日時を保持する列を追加し、v12→v13 の昇格を定める。
- `reading-progress-badge`: 登録済み小説のバッジに「新着あり」の印を出す条件と、印が消える条件を追加する。

## Impact

- コード:
  - 新規 `lib/features/novel_update_check/`（チェック処理、なろうAPIクライアント、状態管理、進捗ダイアログ）
  - `lib/features/novel_metadata_db/`（v13 のスキーマと昇格、チェック結果の保存と読み出し）
  - `lib/features/file_browser/`（ツールバーのボタン、`ReadingProgressBadge` と `readingProgressBadgesProvider`、バッジの描画）
  - `lib/l10n/app_{ja,en,zh}.arb`（新規文字列）
- 外部サービス: なろう小説API（`api.syosetu.com/novelapi/api/`、`api.syosetu.com/novel18api/api/`）への新しいリクエストが加わる。カクヨムとハーメルンへは、作品ごとに目次1ページを取得する。
- データ: `novel_metadata.db` のスキーマが v13 になる。既存の行は変更しない。新しい列は NULL（未チェック）で始まる。
- 依存パッケージの追加はない（既存の `http` を使う）。
