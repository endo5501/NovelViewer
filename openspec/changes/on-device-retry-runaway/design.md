# Design

## Context

なぜこの変更が必要かは proposal.md の「Why」を参照。ここでは、方針を決める前提になる現状と計測だけを書く。

- `FoundationModelsLlmPlugin.swift` は `session.respond(to:schema:options:)` で回答全体を待ち、`response.content.jsonString` を返す。応答上限は `maxResponseTokens = 1000`、クライアントが宣言する応答予算（`maxResponseSize`）は 1300 字。
- `FoundationModelsClient.generate` は、制約付きの生成が `guardrailViolation` で失敗したときだけ、スキーマを外して greedy で1回再試行する。
- パイプラインの `_parseJsonResponse` は、正しい JSON の `summary` / `facts` をそのまま成功として扱う。今回の暴走した回答もこれに当たり、`isStructured: true` で保存され、Stage 1 ならキャッシュもされる。
- 計測（`integration_test/on_device_llm_runaway_test.dart`、iPhone 16 / iOS 27.0.1 (24A446)、`measurements/iphone16-ios27.0.1-before.json`）。プロンプトは「記憶人」の最終要約で、事実は iPhone の fact_cache にあった5件:
  - 制約付き ×5: 5回とも、要約の直後に `」}` を書き、上限まで書き続けた（1443〜2148 字、各 18〜21 秒）。拒否は0回
  - 続きの内容はまちまちだった。同じ文の繰り返し（「支援者: Appleです。」）、2〜3文の循環、プロンプトの復唱、など。同じ文が3回続く形は5件中2件だけ
  - スキーマなし（greedy / 既定サンプリング）: どちらも約1秒、約80字で、コードフェンス付きの正しい JSON を返した
  - クライアント経由: 制約付きの「成功」をそのまま返し、約20秒、1443字
- 同じプロンプトでも macOS 27.0.1 では、制約付きは5回中4回拒否、1回は正常。スキーマなしは正常（約1秒）。
- iPhone の DB に残っていた壊れた要約2件（「記憶人シィー」1972字、「キャロル」1556字）も、`」}` のあとに暴走している。
- `FoundationModels`（iOS 27.0 SDK）には、文字列のプロパティに正規表現の制約を付ける `DynamicGenerationSchema.Property(name:description:type:guides:)`、スキーマをプロンプトに含めない `includeSchemaInPrompt`、逐次受信の `streamResponse(to:schema:...)` がある。`streamResponse` の各要素（`Snapshot.rawContent`）は、その時点までの全文として届く。
- オンデバイスの不具合は iPhone 実機でしか再現しない。`flutter drive` での実機テストは終了時にアプリとデータを消すので、毎回バックアップと書き戻しが必要になる（1回あたり数分）。

## Goals / Non-Goals

**Goals:**

- iPhone のモデルで、制約付きの回答が上限まで暴走して壊れたまま保存されることをなくす（事実抽出と最終要約の両方で）
- できれば暴走そのものを起こさない。起きた場合も、短い時間で打ち切って正しい回答に置き換える
- 読めない最終要約を、どのプロバイダでも保存・表示しない
- 修正前と修正後を、同じ実機の計測テストで確かめる

**Non-Goals:**

- サンプリング方式の変更（スキーマなしは greedy のまま）
- guardrail がこの事実を拒否する理由の解明（macOS の挙動は変えない）
- `LanguageModelSession(instructions:)` によるロールの固定、`reasoningLevel` の指定
- 拒否されたときに、制約付きでもう一度試すこと（iPhone では拒否が起きておらず、macOS ではスキーマなしの再試行が正しく動いているため。以前の案 F は採らない）
- Stage 1 の生テキストへのフォールバックの撤廃
- 保存済みの壊れた要約の自動削除

## Decisions

### D1. 暴走を元から断てるか、実装より先に実機で試す

計測テストに次の条件を加え、制約付きの生成を各5回、iPhone で実行する。判定は「暴走した」= フィールドの値が 1300 字を超えた、または値に `}` を含む、とする。

| 条件 | 変えるもの |
|---|---|
| E0 | 現状（計測済み。5/5 暴走） |
| E1 | プロンプト末尾の `JSON形式で回答してください: {"summary": "..."}` の行を外す |
| E2 | `summary` フィールドに、`}` を含まない正規表現の制約（`[^}]*`）を付ける |
| E3 | `includeSchemaInPrompt: false` にする |
| E4 | E1〜E3 で効いたものの組み合わせ（効いたものが2つ以上あるとき） |

- E2・E3 はネイティブ側の変更が必要なので、プラグインに実験用の引数を一時的に加える。採らなかったものは、実験のあとで引数ごと削除する。
- 採用の基準は、iPhone で5回とも暴走せず、要約の中身がスキーマなしの回答と同程度であること。さらに macOS でも、制約付きの回答の形と拒否の回数が悪くならないこと。
- 採用したものは、仕様（`apple-on-device-llm`）とこの設計に、計測値を添えて書き足してから実装する。どれも効かなければ、D2〜D4 の打ち切りだけで対処する。
- 理由: 元から断てれば、約20秒の暴走も、スキーマなしへの切り替えも起きない。ただ、効くかどうかは実機でしか確かめられず、モデルが変われば効かなくなる可能性もある。そのため、D2〜D4 の打ち切りは、実験の結果にかかわらず入れる。

### D2. 制約付きの回答も逐次受け取り、暴走したら打ち切る

制約付きの要求は `streamResponse(to:schema:options:)` で受ける。届くたびに、フィールドの値（`rawContent` から取り出した、その時点までの文字列）を調べ、次のどちらかに当たったら打ち切る。

1. 値の長さが、クライアントから渡された応答予算（字数）を超えた
2. 値に `}` が現れた

打ち切ったら、プラグインは暴走を表す失敗（新しい原因 `runawayOutput`）を返す。クライアントはそれを guardrail の拒否と同じように扱い、スキーマなし・greedy・打ち切りあり（D3）の要求を1回だけ出す。

- 1 を入れる理由: 既存の仕様（応答上限は失敗を抑えるためのもの）は、「指示どおりの回答は予算に届かない。上限に近づくのは、何かがおかしくなったときだけ」という前提に立っている。予算を超えたことは、それ自体が暴走の証拠になる。計測した8件すべてを捕まえられ、モデルの癖にも依存しない。ただし、止まるのは 1300 字を書いたあと（約13秒後）になる。
- 2 を入れる理由: `}` が現れるのは、モデルが自分では閉じたつもりでいる印であり、計測した8件すべてで、要約の直後（約60字目）に現れた。要約や事実の文章に `}` が出ることは、まずない。今の iPhone のモデルの癖を捕まえるものだが、閉じたつもりのモデルが続きを正しく書くことはないので、癖が変わっても誤検知にはなりにくい。
- 打ち切った回答は返さない。`」}` の手前を切り出せば正しい要約に見えることが多いが、それを当てにすると、モデルの癖の形を仕様にすることになる。スキーマなしの回答が約1秒で正しく返るので、引き直すほうを選ぶ。
- 検討した他の案: 同じ文が3回続いたら止める（以前の D4）。計測では5件中2件しか捕まえられないので採らない。

### D3. スキーマなしの回答は、オブジェクトが閉じたら止める

クライアントが打ち切りを求めたスキーマなしの要求は、`streamResponse(to:options:)` で受ける。最初の `{` から括弧の深さを数え、深さが0に戻った時点で打ち切って、`{` からその `}` までを返す。文字列の中（`"` の内側。`\"` のエスケープも考慮する）の括弧は数えない。オブジェクトの前後（コードフェンスを含む）は返さない。

オブジェクトが閉じないまま、最初の `{` 以降の長さが応答予算を超えたら打ち切り、`runawayOutput` を返す。`{` が現れないまま予算を超えた場合も同じにする。

- 理由: iPhone でも macOS でも、スキーマなしの回答はコードフェンス付きで返ってきた。フェンスをプロバイダ側で取り除けば、パイプラインのフェンス処理に頼らずに済む。スキーマなしの回答も同じ暴走をしうるので、同じ予算で止める。
- 検討した他の案: 文字列を意識せず、括弧だけを数える案。値に `}` が入った正しい回答を途中で切ってしまうので採らない。

### D4. 打ち切りの判定は、Flutter ビルドの外でテストできる Swift コードに置く

D2・D3 の判定は、「その時点までの全文」を受け取って「続ける / 完成（範囲つき）/ 暴走」を返す純粋な型として実装する。`GenerationFailureWireCode` と同じく、ソースはプラグイン側に置き、`packages/foundation_models_llm/darwin/wire_code_tests` からシンボリックリンクで参照して、`swift test` で検証する。

- 打ち切りは、ストリームのループを抜けることで行う。それで実際にモデルの生成が止まるかは、修正後の計測（所要時間）で確かめる。止まらなければ、生成を走らせている `Task` を cancel する。

### D5. 応答予算はクライアントからプラグインに渡す

`FoundationModelsLlm.generate` に、打ち切りの基準になる字数（`maxResponseSize`）と、スキーマなしの回答を打ち切るかどうかを、引数として加える。プラグインは、自分では予算を決めない。

- 理由: 予算はクライアントがパイプラインに宣言している値なので、同じ値で判定すれば食い違いが起きない。再試行の判断はクライアントに置き、プラグインは頼まれた1回の呼び出しだけをする、という既存の仕様も守れる。
- 字数を渡さない呼び出し（今のどの呼び出し元とも違う）では、これまでどおり `respond` で回答全体を待つ。

### D6. 新しい失敗の原因 `runawayOutput`

`OnDeviceGenerationFailure.runawayOutput` を加える。`LlmOnDeviceGenerationFailure.isWorthRetrying` では true にする。パイプラインの再試行は、新しい要求として制約付きから始まり、違う結果になりうるからだ。クライアント内では、制約付きの要求での `runawayOutput` は「スキーマなしの要求に進む」きっかけになる。スキーマなしの要求での `runawayOutput` は、そのまま報告する。

### D7. 読めない最終要約は、新しい失敗型で終わらせる（全プロバイダ）

`LlmSummaryPipeline` の最終要約で、`_readableOr` の結果が `isStructured: false` のまま（2回とも読めない、または2回目の要求が失敗した）なら、`LlmAnalysisUnreadableSummaryFailure` を投げる。2回目の失敗はログに残す。`analysis_runner.dart` に分岐を加え、ja/en/zh の文言 `llmAnalysis_unreadableSummary` を表示する。スナップショットは保存しない。`_parseJsonResponse` の生テキストへのフォールバックは Stage 1 のために残す。

- `LlmResponseFormatException` は「JSON として読めたが、形が違う」ことを表し、再試行の対象にもなっている。意味の違う失敗を同じ型に入れないため、型を分ける。
- 今回の不具合は JSON として読めてしまうので、これでは防げない。D2〜D3 が対策で、これは防御にあたる。

### D8. 生成回数と所要時間

- 1つのプロンプトに対してプロバイダが出す生成は、これまでどおり最大2回（制約付き、スキーマなし）。
- iPhone で暴走していた要求は、`}` の検知で約60字目に打ち切り、スキーマなしで約1秒かかる。合わせて数秒になり、これまでの約20秒から縮む見込み。修正後の計測で確かめる。
- オンデバイスの最終要約1語あたりの最悪値は、パイプラインの失敗時の再試行で2回、`_readableOr` でさらに1回の、計3回の要求。それぞれでプロバイダが最大2回生成するので、最大6回になる。

## Risks / Trade-offs

- [実験がどれも効かない] → D2〜D3 の打ち切りで対処する。暴走するたびに数秒の切り替えが入る。
- [E2 の正規表現の制約で、生成が遅くなる、または中身が崩れる] → 採用の基準に、中身と所要時間を含める。
- [正しい回答の値に `}` が入っていて、誤って打ち切る] → 要約・事実の文章ではまず起きない。起きても、スキーマなしの要求で引き直すだけで済み、失敗にはならない。
- [予算を超える正しい回答を、暴走とみなす] → 予算はプロンプトで指示する長さより十分大きく取ってある（既存の仕様）。予算を超えた回答は、これまでも上限の近くで切れていた。
- [ストリームのループを抜けても生成が止まらない] → 修正後の計測で所要時間を見る。止まらなければ `Task` を cancel する。それでも止まらない場合は、アーカイブ前に、仕様の「Ending the generation SHALL stop the model's work on it」を実測に合わせて直す。
- [サーバー系のプロバイダで、地の文の回答が失敗になる] → ユーザー確認済みの仕様変更。スキーマ（`format` / `response_format`）を指定しているので、起きることは少ない。
- [実機テストのたびに iPhone のデータを消す] → 毎回バックアップと書き戻しを行い、実行の前にユーザーに確認する。実機での計測は、実験（D1）と修正後の確認の2回に抑える。

## Migration Plan

- データの移行はない。保存済みの壊れた要約（「記憶人シィー」「キャロル」）は自動では消さない。読者が再解析すると上書きされる。
- プラグインの引数は追加のみで、省略時はこれまでどおりに動く。ロールバックは、コミットを revert すればよい。
