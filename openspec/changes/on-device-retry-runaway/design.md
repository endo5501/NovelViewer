# Design

## Context

なぜこの変更が必要かは proposal.md の「Why」を参照。ここでは、方針を決める前提になる現状だけを書く。

- `FoundationModelsClient.generate` は、スキーマ制約付きの生成が `guardrailViolation` で失敗すると、スキーマを外し `OnDeviceSampling.greedy` で1回だけ再試行する。プラグイン（`FoundationModelsLlmPlugin.swift`）は `session.respond(to:options:)` で回答全体を待ってから返すため、モデルが止まらなければ応答上限（`maxResponseTokens = 1000`）まで生成が続く。
- 再現の記録: macOS 27.0.1 で、iPhone に表示された事実5件から最終要約プロンプトを組み立て、プラグインと同じ設定でモデルに渡した。制約付きの生成は3回中2回 guardrail に拒否され、1回は通った。スキーマなし・greedy は 59 文字で `}` まで書いて止まった。同じプロンプトでも iPhone（iOS 27.0.1）では `…」}` で文字列を閉じないまま「支援者: Appleです。」を繰り返した。
- パイプラインの `_parseJsonResponse` は、`jsonDecode` に失敗すると生テキストを `isStructured: false` の値として返す。`_readableOr` は最終要約に限ってもう1回要求し、2回とも読めなければ1回目を残す。そのため、壊れた生テキストが要約として保存される。
- 失敗の表示は `analysis_runner.dart` の switch で行っている（`LlmAnalysisNoFactsFailure` → `llmAnalysis_noFacts` など）。それ以外の失敗は `llmAnalysis_failed` に詳細を添えて表示される。
- オンデバイスの不具合は iPhone 実機でしか再現しない。実機計測の前例として、`integration_test/piper_ios_synthesis_test.dart` と `fvm flutter drive --profile` の手順（`docs/ios.md`）がある。

## Goals / Non-Goals

**Goals:**

- どの端末のモデルでも、スキーマなし再試行の所要時間と出力をプロバイダ側で抑える
- 読めない最終要約を、どのプロバイダでも保存・表示しない
- iPhone 実機で、修正前の再現と修正後の確認を同じ手順で行えるようにする

**Non-Goals:**

- サンプリング方式の変更（greedy を維持する。計測データは取るが、変えるかどうかは別の変更で判断する）
- guardrail がなぜこの事実を拒否するのかの解明、プロンプトの言い回しの調整
- `LanguageModelSession(instructions:)` によるロールの固定（iPhone 実機でしか効果を確かめられず、根拠を持って入れられないため）
- Stage 1 の生テキストへのフォールバックの撤廃

## Decisions

### D1. 拒否されたら、同じスキーマでもう1回試してからスキーマを外す（クライアント側）

`FoundationModelsClient.generate` の順序を「制約付き → (拒否) 制約付き・サンプリング指定なし → (拒否) スキーマなし・greedy・打ち切りあり」にする。次の要求に進むのは拒否のときだけで、それ以外の失敗はその場で報告する。

- 理由: 拒否は確率的に起きる（Context の記録）。制約付きの回答は必ずパースできるので、スキーマを外す前にもう一度引く価値がある。
- 検討した他の案: パイプライン側で拒否を再試行する案。`LlmOnDeviceRefusedFailure.isWorthRetrying == false` と「拒否はプロバイダが処理し終えてから届く」という既存の仕様を崩すことになり、再試行の方針が2か所に分かれるので採らない。
- コスト: 確実に拒否される文章（コード内コメントの礼儀作法の教師の例）では、チャンクごとに生成が1回増える（2回 → 3回）。拒否はチャンクの一部でしか起きないので許容する。

### D2. 打ち切りはプラグインの引数で要求する

メソッドチャネルの `generate` に真偽値の引数（仮称 `endAtObject`）を追加する。真のときだけ、プラグインは `session.streamResponse(to:options:)` で逐次受け取り、D3・D4 の判定で打ち切る。Dart 側では `FoundationModelsLlm.generate` に同名の引数を加え、クライアントはスキーマなしの再試行でだけ真にする。

- 理由: 「再試行の判断はクライアントに置き、プラグインは頼まれた1回の呼び出しだけをする」という既存の仕様を守れる。スキーマも引数もない呼び出しの挙動（テキストをそのまま返す）も変わらない。
- 検討した他の案: スキーマなしの呼び出しなら常に打ち切る案。暗黙の挙動が増え、「No schema returns plain text」の仕様を書き換えることになるので採らない。

### D3. オブジェクトの完成は、JSON の文字列を意識して判定する

逐次受け取ったテキストを先頭から走査し、最初の `{` から括弧の深さを数える。文字列の中（`"` の内側、`\"` によるエスケープを考慮する）にある括弧は数えない。深さが0に戻った時点で打ち切り、最初の `{` からその `}` までを返す。前後のテキスト（コードフェンスを含む）は返さない。

- 理由: 正しく書かれた回答で、要約の文字列に `}` が含まれていても途中で切らないようにするため。
- 限界: iPhone の出力のように引用符を閉じないまま `」}` と書いた場合、文字列が終わっていないので、この `}` は閉じ括弧として扱われない。この場合は D4（繰り返しの検知）で止める。打ち切りは時間と出力を抑えるためのもので、パースできることまでは保証しない。パースできない回答は D6 で失敗として扱う。
- 検討した他の案: 文字列を意識せずに括弧だけを数える案。iPhone の例ではより早く止まるが、正しい回答を `}` の位置で切ってしまう。どちらにしても D4 と D6 が受け止めるので、正しい回答を守るほうを選ぶ。

### D4. 繰り返しの検知は「同じ文が3回続いたら」

逐次受け取ったテキストを、「。」「！」「？」・改行のいずれかで終わる文に区切る。前後の空白を除いて空でない文が、直前の2文と同じなら繰り返しと判定し、打ち切る。打ち切ったら新しい原因 `repetitiveOutput` で失敗を返す（テキストは返さない）。

- 理由: iPhone の例（「支援者: Appleです。」）を3回目で止められる。事実の箇条書きで同じ行が3回続くことは、正しい回答ではまず起きない。判定が単純なのでテストしやすい。
- `repetitiveOutput` は `LlmOnDeviceGenerationFailure.isWorthRetrying` で true とする。パイプラインの再試行は新しい要求として制約付きから始まるので、違う結果になりうるため。
- 検討した他の案: 応答の長さの上限を下げる案。正しい長い回答まで切ってしまうので採らない。n-gram の出現頻度で判定する案。閾値の根拠を持てず、テストも難しいので採らない。

### D5. 打ち切りの判定は Flutter ビルドの外でテストできる Swift コードに置く

D3・D4 の判定は、文字列を逐次与えると「続ける / オブジェクト完成（範囲つき）/ 繰り返し」を返す純粋な型として実装する。`GenerationFailureWireCode` と同じく、プラグインのソースと `packages/foundation_models_llm/darwin/wire_code_tests` 相当の独立パッケージの両方から使えるようにし、`swift test` で検証する。

- 理由: プラグイン本体は Flutter ビルドの外では動かない。打ち切りの境界条件（エスケープ、文字列中の括弧、2回までは繰り返しとしない、など）は、単体テストで押さえるのが確実。
- ストリームの各要素は「その時点までの全文」として届く想定（未確認。3.3 で最初に確かめ、差分で届く場合はそれをそのまま渡す）。判定には、前回からの増分だけを渡す。
- 打ち切りは、ストリームを回しているループを抜けることで行う。それで実際にモデルの生成が止まるかは、計測テスト（D7）で所要時間を測って確かめる。止まらない場合は、生成を走らせている `Task` を明示的に cancel する。

### D6. 読めない最終要約は新しい失敗型で終わらせる（全プロバイダ）

`LlmSummaryPipeline` の最終要約で、`_readableOr` の結果が `isStructured: false` のまま（2回とも読めない、または2回目が失敗した）なら、新しい `LlmAnalysisUnreadableSummaryFailure`（`LlmAnalysisFailure` の実装）を投げる。2回目の失敗は原因としてログに残す。`analysis_runner.dart` の switch に分岐を加え、ja/en/zh の文言（`llmAnalysis_unreadableSummary`）を表示する。スナップショットは保存しない。

- `_parseJsonResponse` の生テキストへのフォールバックは Stage 1 のために残す。最終要約の段で `isStructured` を見て判断するので、パーサの共通部分は変えない。
- 理由: `LlmResponseFormatException` は「JSON として読めたが形が違う」ことを表し、再試行の対象にもなっている。意味の違う失敗を同じ型に入れないため、型を分ける。
- 生成回数の最悪値（オンデバイスの最終要約1語あたり）: パイプラインの失敗時の再試行で2回、`_readableOr` でさらに1回の、計3回の要求。それぞれでプロバイダが最大3回生成するので、最大9回になる。ただし、D3・D4 によってスキーマなしの生成は短く打ち切られる。また、D6 により、読めない回答が続いた時点で解析は終わる。

### D7. 実機計測テスト

`integration_test/on_device_llm_runaway_test.dart`（仮称）を追加する。Context に書いた最終要約プロンプト（iPhone で得られた事実5件と同じもの）を、`MethodChannelFoundationModelsLlm` 経由で実機のモデルに渡し、次を記録する。

1. 制約付きで N 回（例: 5回）実行したときの拒否の回数
2. スキーマなし・greedy・打ち切りなし（修正前の経路）の出力と所要時間。修正前の再現として使う
3. スキーマなし・既定サンプリング・打ち切りなしの出力と所要時間。サンプリングを比較するデータとして残す（合否には使わない）
4. スキーマなし・greedy・打ち切りあり（修正後の経路）の結果（オブジェクトか `repetitiveOutput` か）と所要時間
5. `FoundationModelsClient.generate`（スキーマあり）を通した最終的な結果

合否の基準は、4 が応答上限まで走らないこと（所要時間が 2 より明らかに短いこと）、5 が例外か、`summary` を持つ JSON を返すこと。実行手順は `docs/ios.md` に追記する（`fvm flutter drive --profile`。Apple Intelligence が有効な実機が必要）。

## Risks / Trade-offs

- [ストリームのループを抜けても生成が止まらない] → D7 で所要時間を測って確かめる。止まらなければ、生成を走らせている `Task` を cancel する（D5）。それでも止まらない場合は、アーカイブ前に、仕様の「Ending the generation SHALL stop the model's work on it」を実測に合わせて直す。
- [正しい回答の中で、同じ文が3回続く] → 事実抽出・要約でそうなることはまずない。誤って打ち切っても、パイプラインの再試行で制約付きから引き直す。
- [`」}` のように閉じない回答で、繰り返しも起きないまま上限まで書く] → 上限で止まり、パースに失敗して D6 で失敗として扱う。壊れた要約は保存されないが、時間はかかる。計測で頻度を見る。
- [D1 によってオンデバイスの解析が遅くなる] → 増えるのは拒否されたチャンクのぶんだけ。拒否が多い作品で遅くなりすぎるなら、別の変更で見直す。
- [サーバー系プロバイダで、地の文の回答が失敗になる] → ユーザー確認済みの仕様変更。スキーマ（`format` / `response_format`）を指定しているので、起きることは少ない。
- [iPhone のモデルが将来の OS 更新で変わり、再現しなくなる] → 計測テストは修正後の確認にも使える。再現しなくなっても、D3〜D6 は保険として意味を持つ。

## Migration Plan

- データの移行はない。すでに保存されている壊れた要約（今回の「記憶人」など）は自動では消さない。読者が再解析すると上書きされる。
- ロールバックは、コミットを revert すればよい。プラグインの引数は追加のみで、古い Dart から呼ばれても既定値（打ち切りなし）で従来どおり動く。
