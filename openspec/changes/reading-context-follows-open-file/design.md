## Context

動機と再現手順は proposal.md「Why」を参照。ここでは実装を決めるうえで効く現状だけを挙げる。

- **`directoryContentsProvider` はブラウザ専用に重い。** `file_browser_providers.dart:64` は `.txt` の列挙と並べ替えに加えて、サブディレクトリの列挙、登録済み小説名からタイトルへの解決、そして `tts_audio.db` が存在すればフォルダ別データベースを開いて TTS 状態を読む。読書コンテキストに要るのは最初のひとつだけである。
- **フォルダ別DBハンドルはブラウザの現在地に紐づいて解放される。** `CurrentDirectoryNotifier.setDirectory`（同 `:33`）が、離れたフォルダのハンドルを `perFolderDbRegistry` へ返す。読書側が別フォルダのハンドルを開くと、この解放の網にかからない。
- **小説フォルダの解決規則は既にある。** `resolveNovelFolderPath`（`lib/shared/utils/novel_id_resolver.dart`）。直前の変更で更新対象の解決にも使っており、`reading-progress` やフォルダ別DBと同じキーになる。
- **`selectedNovelTitleProvider` の本番利用者は1つだけ。** `selected_file_progress_title_provider.dart:15` のみ。テストからは複数参照されている。
- **一覧の無効化は5箇所に散っている。** `home_screen.dart:343`、`refresh_progress_dialog.dart:85`、`download_dialog.dart:590`、`tts_controls_bar.dart:204,325,378`。

## Goals / Non-Goals

**Goals:**

- 「いま読んでいるもの」を名前のある1つの導出値にし、タイトルと話送りの双方がそれだけを見る形にする。
- 読書側の話一覧が、ファイルブラウザ用の一覧と同じ並びでありながら、フォルダ別データベースを開かないようにする。
- 一覧の無効化漏れが起きにくい形にする。

**Non-Goals:**

- `directoryContentsProvider` とファイルブラウザ表示の変更。
- `reading-progress` の自動オープンの変更（ブラウザの現在地と結びついているのが正しい）。
- TTS 状態を読書コンテキストへ持ち込むこと。

## Decisions

### D1: 読書コンテキストを `lib/features/reading_context/` に置く

`readingNovelFolderProvider`（読書中の小説フォルダの絶対パス）と `readingEpisodesProvider`（その話一覧）を新設する。

- **なぜ独立した feature か:** capability 名と対応し、`novel_refresh` や `episode_navigation` と同じ粒度になる。`file_browser` に置くと、ブラウザから切り離すための仕組みがブラウザの中にある、という読みにくさが残る。

### D2: 小説フォルダは `resolveNovelFolderPath`、見つからなければファイルの親フォルダ

表示中ファイルのパスから最も近い登録済み小説フォルダを解決し、無ければ `p.dirname(selectedFile.path)` を使う。

- **なぜフォールバックが要るか:** `app-title-display` は「メタデータが未登録のフォルダではフォルダ名を表示する」を既に要求しており、手動で置いたテキストも読める。`resolveNovelFolderPath` は登録外で `null` を返すため、そこで打ち切ると既存挙動を落とす。
- 直前の変更の `refreshTargetProvider` は同じ解決を使うが、フォールバックは持たない。更新できる小説は登録済みに限るためで、意図的な差である。

### D3: 話一覧は専用の軽量プロバイダ（フォルダパスで family）

`FutureProvider.family<List<FileEntry>, String>` とし、中身は `listTextFiles` + `sortByNumericPrefix` のみ。サブディレクトリも TTS 状態も読まない。

- **なぜ `directoryContentsProvider` を family 化して共用しないか:** あちらは `tts_audio.db` があればフォルダ別DBハンドルを開く。読書側が別フォルダで同じことをすると、ブラウザの現在地に紐づくハンドル解放（Context 参照）の外側にハンドルが1つ増え、Windows でのフォルダ削除・移動を妨げうる。`database-connection-interlock` が守ろうとしている性質に、読書側から穴を開けることになる。
- **なぜフォルダパスで family にするか:** 話送りのたびに一覧を取り直さないため。キーは小説フォルダであり、同じ小説の中でエピソードを移動している限り再計算されない。
- 並び順は `sortByNumericPrefix` をそのまま使う。ブラウザと別の実装にすると、一覧の順と話送りの順がずれうる。

### D4: 一覧の無効化は共有ヘルパーに集約する

`directoryContentsProvider` を無効化している5箇所を、両方の一覧を無効化する1つのヘルパー呼び出しに置き換える。

- **なぜ:** 片方だけ無効化する箇所が1つでも残ると、更新で増えたエピソードが話送りに現れない、という再発の形になる。呼び出し側が2つのプロバイダを覚えている限り、次に無効化を足す人は片方を忘れる。
- ヘルパーは読書コンテキスト側に置き、ブラウザ側の一覧も一緒に無効化する。

### D5: `selectedNovelTitleProvider` は退役させる

本番利用者はタイトル組み立ての1箇所だけであり、その導出元が読書コンテキストへ移ると、同じ責務が2箇所に残る。spec からも REMOVED として落とす。

- テストは新しい導出のテストへ移す。`selected_novel_title_provider_test.dart` のうち、フォルダ名フォールバックと入れ子解決のケースは新プロバイダ側で引き継ぐ。

### D6: 何も開いていなければタイトルは「NovelViewer」

ブラウザが小説フォルダにいても、表示中のエピソードが無ければ「NovelViewer」になる。これは既存挙動からの変更である。

- **受け入れる理由:** 読者がその状態を目にするのは Drawer を開いている最中であり、Drawer は AppBar を覆っている。エピソードを選べば Drawer は閉じ、タイトルは作品名になる。実際に見える瞬間がほぼ無い一方で、「タイトルは表示中のエピソードについて答える」という規則を1つに保てる。
- 例外を作ると、ブラウザの現在地への依存が「ファイル未選択のときだけ」という形で残り、今回取り除こうとしている結合が半分生き残る。

## Risks / Trade-offs

- **[ディレクトリ一覧の I/O が1回増える]** → 読書中の小説フォルダごとに1回で、話送りでは再計算されない（D3）。ブラウザが同じフォルダにいる間は同じ内容を二重に読むが、読み取りは軽く、TTS/DB を伴わない。
- **[無効化漏れの再発]** → D4 のヘルパーで呼び出し側から選択肢を奪う。テストで、更新完了後に話一覧が取り直されることを確認する。
- **[起動時の復元との順序]** → 復元は小説フォルダへ移動してからエピソードを選ぶ。話一覧は選択後に解決されるため、順序の前提は増えない。一覧の取得中は話送りが一時的に `null` を返すが、これは既存の「選択ファイルが一覧に無い過渡状態」と同じ扱いである。
- **[表示中にエピソードが削除された場合]** → 一覧から消えるため話送りは `null` になる。既存の過渡状態と同じ扱いで、spec にもそう書いてある。
- **[`episode-boundary-prompt` への波及]** → 境界の検出は隣接ファイルの有無に従うため、話送りが正しくなれば境界プロンプトも正しくなる。プロンプト側の仕様は変えないが、これまで「ブラウザが別の場所にいると境界プロンプトが出ない」状態だったことになる。実装時に確認する。
