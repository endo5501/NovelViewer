## Context

`fact_cache` は Stage-1 の事実抽出結果をファイル単位で保存し、読み進めながら同じ語を何度も聞くという使い方を、話数に比例するコストで成立させるためにある。キャッシュがなければ、10 話ごとに全 100 話を聞いていった場合の Stage-1 呼び出しは累計 550 回になる。キャッシュがあれば 100 回で済む。

鍵は `(word, file_name)`、有効性は本文のハッシュとプロンプト版で判定する。プロンプトを組み立てる材料は「テンプレート・語・ファイル本文・出力言語」で、そこに答えるモデルが加わる。このうち鍵にも有効性判定にも入っていないのが、出力言語と、答えたモデルの二つである。

オンデバイスが三つ目のプロバイダとして入ったことで、モデルの側が実害のある段差になった。サーバの大きなモデルと、3B 級・窓 4096 トークン・戦闘描写を拒否する端末のモデルとでは、抽出される事実の質が違う。そして読者は両者を行き来する。

現状で部分的に救われている経路が一つある。同一話数での再解析は語のキャッシュを無効化するため、モデルを変えて同じ話数で解析し直せば全ファイルが新しいモデルで抽出される。ただし読み進めながらの解析 (30 話まで端末で解析したあと、40 話でサーバに切り替える) には効かない。

## Goals / Non-Goals

**Goals:**

- ひとつの解析実行が使う事実を、単一のモデル由来に揃える。
- モデルを行き来しても、戻ってきたときに前の抽出結果が残っている。
- 事実の由来が読者から見える。

**Non-Goals:**

- 出力言語による混在の解消。同じ形の穴だが、UI 言語の切り替えは頻繁ではない。
- 使わなくなったモデルの棚の掃除。
- モデルの質を比較したり、読者に推奨したりすること。
- 事実を常に原文の言語で抽出し翻訳を Stage-2 に寄せる案。言語を鍵から外す筋の良い解法だが、要約の質が変わる別の設計判断になる。

## Decisions

### 決定 1: 名乗りを有効性判定ではなく鍵に含める

`fact_cache` の一意キーを `(word, file_name, model_id)` にする。モデルごとに独立した棚ができ、解析実行は自分の棚だけを読み書きする。

**却下した案: 名乗りを有効性判定に足す。** `isFactCacheValid` に一行足すだけで済み、モデルが変わった行は miss になる。しかし切り替えのたびに語の全ファイルを払い直すことになり、行き来を前提にした設計と噛み合わない。これは実質、いま存在する「同一話数で再解析する」という逃げ道を自動で踏ませているだけで、問題を解いてはいない。

**却下した案: 記録して表示するだけ。** 沈黙している問題を見える問題に変えるが、混在そのものは残る。読者は毎回自分で判断させられる。

鍵に含める形を選んだ副次的な効果として、粒度の問題がほぼ消える。有効性判定に足す案では、細かく見るほど切り替えのコストが上がるためティアに丸めるか悩む必要があった。棚を分けるなら新しいモデルは新しい棚を作るだけで、古い棚は残る。

### 決定 2: 粒度はモデル名まで、baseUrl は含めない

名乗りは `ollama:<モデル名>` / `openai:<モデル名>` / `apple:on-device` の形とする。

baseUrl を含めないのは、それが「どこにあるか」であって「何であるか」ではないからである。自宅サーバの IP が DHCP で変わるたびに棚が増えるのは無駄で、同じモデル名を二つのホストで動かしているなら同じモデルである。

**却下した案: オンデバイスかサーバかの二段に丸める。** 本当の段差はティアの側にあるという理屈は正しいが、`ollama:llama3.2:1b` のような「サーバにいる小さいモデル」が強い側に分類される。決定 1 により細かくしても churn が出ないので、丸める理由がない。

### 決定 3: 名乗りはクライアントが持ち、既定値を置かない

`LlmClient` に `String get modelId` を追加する。前回 `maxChunkSize` を「窓の広さはパイプラインではなくモデルの性質だ」という理由でクライアント側に置いたのと同じ理屈で、自分が何者かもクライアントが一番よく知っている。

`maxChunkSize` と違い既定値は置かない。`maxChunkSize` には「知らないなら従来どおり 4000」という安全な既定があったが、名乗りの既定は別のモデル同士を同じ棚に入れてしまう。既定があること自体が事故になる。

この判断のコストとして、`LlmClient` を `implements` しているテスト内の偽クライアントがコンパイルを通らなくなる。黙って既定に落ちて棚を共有するより良い壊れ方として受け入れる。

名乗りは単一の不透明な文字列として保存し、等値比較だけに使う。分解して解釈しない。`ollama:qwen3:30b` のようにモデル名自体がコロンを含んでも、比較と表示には差し支えない。

### 決定 4: 名乗りの要件は `llm-summary-fact-cache` が持つ

`maxChunkSize` の要件が `llm-summary-pipeline` にあるので対称性からはそちらだが、パイプラインは名乗りを一度も触らない。使うのはキャッシュだけである。`llm-summary-fact-cache` の spec を読む人は名乗りがどこから来るかを知る必要があり、`llm-summary-pipeline` の spec を読む人は知る必要がない。

### 決定 5: 不明な名乗りの行は存在させない

移行前から存在する行は、どのモデルが書いたか分からない。これらを空文字の名乗りで残す案を採らず、移行の時点で削除する。

名乗りが鍵に入っている以上、空文字の行は現行のどのクライアントからも引かれず、`upsert` でも上書きされない (鍵が違うので別の行が挿入される)。つまり永久に残り、二度と有効にならず、詳細ダイアログで「不明」として同じファイル名の重複を作るだけになる。それはキャッシュ行ではなく残骸である。

読者が失うものは、次の解析でその語の全ファイルが抽出し直しになることだけである。これは `prompt_version` を上げたときに起きることと同じで、既存の仕組みが正常な事象として前提しているコストである。事実から作られた要約 (`word_summaries`) には一切触れない。

この規則は二つの移行経路の両方に一様に適用する。

- `novel_data.db` v1→v2: `fact_cache` を作り直す。
- `novel_metadata.db` v8→v9 (グローバルからフォルダへの移送): `fact_cache` をコピーしない。`word_summaries` と `bookmarks` は従来どおり移送する。

**却下した案: 移行時点で設定されているモデルの名乗りを書き込む。** `novel_data.db` は小説フォルダごとに遅延で開かれる一方、LLM 設定はグローバルで、移行の実行時点にそこへ手が届かない。配線を通すことはできるが、当てずっぽうを安くない配線で書き込むことになる。

### 決定 6: v1→v2 は列追加ではなくテーブルの作り直し

決定 5 により保存すべき行がないので、`ALTER TABLE ADD COLUMN` ではなく `fact_cache` を drop して現行スキーマの DDL で作り直す。

`ALTER TABLE ADD COLUMN` で NOT NULL 列を足すには SQLite が DEFAULT 句を要求するため、昇格した DB のスキーマだけが `DEFAULT ''` を持ち、新規作成の DB と食い違う。`db-schema-test-fidelity` が排除しようとしているスキーマドリフトそのものである。作り直せば両者は完全に一致する。

`createCurrentSchema` から `fact_cache` の DDL を単独で再利用できるように切り出す。単一の正であることは維持する。

drop してから create するまでの間にクラッシュしたらどうなるか、という懸念には答えておく。sqflite は `onUpgrade` とバージョンの書き込みを同一の排他トランザクションで実行し、失敗時に ROLLBACK する (`sqflite_common` の `database_mixin.dart`)。SQLite の DDL はトランザクショナルなので、テーブルが消えたまま残る経路はない。次回起動で同じ昇格がやり直される。

### 決定 7: 再解析時の無効化は現在のモデルの棚だけに及ぼす

再解析 (同じ話数でもう一度) は「この結果が悪いからやり直す」という意思表示であり、悪い結果を出したのは現在のモデルである。他の棚は無関係の作業で、巻き込む理由がない。`invalidateWord` に名乗りを渡し、`updated_at` による絞り込みと併用する。

### 決定 8: 詳細ダイアログは名乗りをバッジで表示する

棚が分かれると、履歴の詳細ダイアログ「事実」タブで同じファイル名が複数並ぶ。由来が見えないと区別できない。読み取り専用の検査画面なので、由来を見せるのはまさにその役目である。既存の「無効」バッジと同じ `OutlinedTextBadge` を使い、ファイル名の見出し行に併記する。

## Risks / Trade-offs

**オンデバイスのモデルはバージョンを公開していない** → `apple:on-device` は OS 更新でモデルが差し替わっても同じ名乗りのままで、古い事実が再利用される。OS のバージョンを名乗りに混ぜれば検出できるが、OS を上げるたびに全棚が作り直しになる害のほうが大きい。既知の限界として受け入れ、読者は再解析で回避できる。

**モデル名を無視するサーバがある** → llama.cpp のサーバのように `model` フィールドを無視する実装では、読者が中身を差し替えても名乗りが変わらず同じ棚に混ざる。baseUrl を含めても解決しない (同じホストで差し替わる)。自動的な検出手段はなく、再解析が唯一の回避策になる。

**切り替え直後は棚が空なので払い直しになる** → 決定 1 が意図した挙動だが、オンデバイス側では実質的な影響が出る。いまはサーバが抽出した事実に乗ることで、端末のモデル単独では通らない解析が通る場合がある。棚を分けるとそれが止まる。ただし新しく増えたファイルが拒否されればどのみち実行は失敗するので、失われるのは「新規ファイルがたまたま穏当だった場合」に限られる。

**同期されたライブラリは端末をまたいで棚を共有する** → `novel_data.db` は小説フォルダの中にあるので、Mac と iPad で同じライブラリを同期していると、両方の `apple:on-device` が同じ棚を使う。二台のオンデバイスモデルは別物でありうるが、名乗りは同じである。OS 更新の限界と同じ性質だが、そちらより踏みやすい。

**棚が溜まる** → 使わなくなったモデルの行を掃除する経路がない。語ごとの削除と小説ごとの削除では消える。一行は数百文字で、読者が使うモデルは現実には二つか三つなので、当面は放置する。

**`LlmClient` の破壊的変更** → 既定値を置かないため、外部・テストの実装がコンパイルを通らなくなる。意図した設計 (決定 3) で、修正は一行の追加で済む。

**出力言語の穴は残る** → 日本語で抽出した事実が英語の実行で再利用される状態は変わらない。今回の鍵の変更は言語を足す余地を残す形なので、必要になれば同じ場所に一列足せる。

## Migration Plan

1. `novel_data.db` のバージョンを 2 に上げ、`onUpgrade` を配線する (このDBにとって初めての移行経路)。
2. v1→v2 は `fact_cache` を drop し、`model_id` を含む現行 DDL で作り直す。他の 2 テーブルには触れない。
3. `novel_metadata.db` v8→v9 の移送から `fact_cache` のコピーを外す。グローバル 3 テーブルの drop 手順は変えない。
4. 新規作成の `novel_data.db` は最初から v2 スキーマで作られる。
5. v8→v9 の移送が作る `novel_data.db` も、アプリ本体と同じバージョン・同じコールバックで開く。現行のテーブルを古い刻印の下に作れば、スキーマと `user_version` が食い違う。

ロールバック: 一方通行である。旧バージョンのアプリで v2 の `novel_data.db` を開いても失敗しない。sqflite は `onDowngrade` が未指定なら何もせず、そのうえで要求されたバージョンを書き込むため、テーブルは v2 のまま `user_version` だけが 1 に戻る。旧ビルドはその刻印を信じて `ON CONFLICT(word, file_name)` の upsert を投げ、テーブルにもう存在しない一意キーを指すため、事実キャッシュへの書き込みが毎回失敗する。すでに読者の手元にあるビルドは後から直せないので、この経路は塞げない。

塞げるのは次からである。`NovelDataDatabase` に `onDowngrade` を与え、知らないバージョンの DB を開く要求を拒否する。刻印を下げて壊れた状態を作るより、open が失敗するほうが起きたことを言い当てている。`openOrResetDatabase` は `deleteOnFailure: false` なのでファイルは残る。

### 決定 9: 知らないバージョンの DB は開かずに拒否する (レビューで追加)

当初の設計は「旧バージョンのアプリで開くと失敗する」と書いていたが、事実ではなかった。`onDowngrade` が未指定のとき sqflite は何も実行せず、そのうえでバージョンだけを書き換える。スキーマは新しいまま刻印だけが古くなる。

そこで `NovelDataDatabase` に `onDowngrade` を与え、例外を投げて open を失敗させる。`openOrResetDatabase` にも受け口を足した (他の DB は未指定のままなので挙動は変わらない)。

これは既に配布済みのビルドを救わない。救えるのは次のビルドからで、それが手当てできる範囲である。

拒否には代償がある。従来の挙動は事実キャッシュの書き込みだけが壊れたのに対し、拒否すると `novel_data.db` 全体の open が失敗し、ブックマークにも届かなくなる。それでも拒否を選ぶ。`deleteOnFailure: false` なのでファイルは残り、失われるものはない。原因の分からない解析失敗が続くより、開けないと言われるほうが読者にとって扱いやすい。

## Open Questions

なし。実装前に決めるべき事項は決定 1 から 8 で尽きている。決定 9 はレビューで判明した事実誤認の訂正である。
