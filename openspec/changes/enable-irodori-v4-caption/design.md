## Context

`2026-08-05-add-irodori-v4-variant` で v4 を導入した際、「参照音声 × caption」で末尾にテキストへ存在しない発話が付く現象 (10/10) を実測し、v4 を **caption 非対応 variant** として扱うことで回避した。当時これは「本家のモデル/ランタイム側の課題」として Non-Goal に置かれていた。

その後の検証で原因と回避策が確定した。全実測・試聴結果は `tmp/irodori-eval/PLAN-duration-workaround.md` にある (gitignore 配下。本 change のアーカイブ後に消える可能性があるため、判断に必要な数値は以下に転記する)。

**原因**: 「余り」= 生成尺 − 本文を読み終える時刻。余りが大きいとモデルがその時間を埋めるように発話する。実測 16 セルで一貫している。

| 余り (秒) | 0.07 | 0.34 | 0.44 | 0.58 | 0.60 | 0.97 | 1.29 | 1.35 | 1.92 | 2.37 | 2.61 | 2.95 | 3.00 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 発生率 | 0/10 | 0/10 | 0/10 | 1/10 | 4/10 | 2/10 | 1/10 | 3/10 | 8/10 | 8/10 | 9/10 | 8/10 | 9/10 |

**上流 Python 実装でも同じ発生率で再現する** ため、GGUF / C++ 固有の問題ではない (`tmp/irodori-eval/python/FINDINGS.md`)。上流 (Aratako/Irodori-TTS) に本件の Issue は無く、修正の見込みは不明。

**検証の制約**: 判定は最終的にすべて**試聴**で行った。当初使った「発話区間数」の音響プロキシは**偽陽性も偽陰性も出す**ことが分かったためである (長文は補正なしでも壊れていないのにプロキシは 8/10 と誤検出し、逆にクリーンと判定した clip に実際は残渣があった)。

## Goals / Non-Goals

**Goals:**

- Irodori v4 で caption (セグメントメモ) を使えるようにする
- 生成尺の補正を audio.cpp fork の Irodori セッション内で完結させる
- 補正の挙動をリクエストオプションで制御可能にし、native 再ビルドなしにチューニングできる状態を保つ
- 既定では現行の挙動を変えない (CLI / WebUI など他のフロントエンドの出力を変えない)

**Non-Goals:**

- **末尾トリム (生成後の音響的な切り詰め)** は入れない。予防だけで全条件がクリーンになったため、正当な「間」と区別できないリスクを負う理由が無い。必要になれば後から足せる
- v4 の末尾アーティファクトそのものを上流で直すこと
- 尺補正の他エンジン (Qwen3 / Piper) への適用
- 日本語以外の言語での字数則の校正

## Decisions

### D1: 補正を audio.cpp のエンジン内部で完結させる (Dart から 2 回呼ばない)

**採用**: `session.cpp` の尺決定箇所で、condition graph を 2 回目実行して noref 予測を得る。

**却下した案**: Dart 側から「予測値だけ取得する API」を呼び、その値を使って合成を呼ぶ 2 段構え。

**理由**: audio.cpp は渡されたテキストを**内部で分割する** (`chunk_text_request`、既定 Endline / `max_text_len`)。予測も尺決定もチャンクごとのループ内で行われる。Dart は分割境界を知らないため、分割ロジックを再実装しない限りチャンクと予測値を対応づけられない。加えて現行の `duration_sec` はループ内で参照されるため、**指定秒数が全チャンクに同じ値で適用**され、複数チャンクのテキストでは使い物にならない。

**成立根拠**: `has_speaker` / `has_caption` は condition graph の**実行時入力テンソル**であり、run のたびに書き換えられている。`use_caption_condition` は「モデルが caption 重みを持つか」というアセット側の性質でリクエスト単位ではない。したがってフラグを 0 にして同じグラフをもう一度実行するだけでよく、**グラフ再構築もモデル再ロードも不要**。

### D2: 3 値の min を採る (noref 予測だけでは足りない)

**採用**: `min(通常予測, noref 予測, 字数(記号除) × 0.207 + 0.4)`

**却下した案 A**: 固定倍率 (`duration_scale`) で縮める。上流 Issue ドラフトが勧める `0.93` 相当。
→ 9/10 が 2/10 になるだけで 0 にならない。数百チャンクの朗読では実質毎回発生する。さらに過剰見積もりの量は加算でも乗算でも説明できない (加算合成なら +3.28 秒の予想に対し実測 +2.40、乗算合成なら ×1.675 の予想に対し実測 ×1.432)。

**却下した案 B**: noref 予測 + マージンのみ。
→ noref 予測が正確なのは**中程度の長さだけ**。短文では実発話長を大きく過大評価する。

| テキスト | noref 予測 | noref 実測本文終端 | 誤差 |
|---|---:|---:|---:|
| 32 字 | 5.56 | 5.49 | +1% |
| 54 字 | 11.20 | 10.35 | +8% |
| **12 字** | **3.76** | **2.05** | **+83%** |

**却下した案 C**: 字数則のみ。
→ 速い caption では字数則の値 (6.40) でも余りが残り、残渣が出た。noref 予測 (5.56) が必要。

**両方必要**であり、片方だけでは全条件を説明できない。

| セル | 通常予測 | noref 予測 | 字数則 | min | 試聴 |
|---|---:|---:|---:|---:|---|
| 32字 標準 | 7.96 | **5.56** | 6.40 | 5.56 | クリーン |
| 32字 遅い caption | 8.56 | **5.56** | 6.40 | 5.56 | クリーン |
| 32字 速い caption | 7.28 | **5.56** | 6.40 | 5.56 | クリーン |
| 12字 短文 | 4.60 | 3.76 | **2.47** | 2.47 | クリーン |
| 54字 長文 | 11.64 | 11.20 | **10.75** | 10.75 | クリーン・欠けなし |
| 別話者 | 6.24 | **5.56** | 6.40 | 5.56 | クリーン |

補正なしでは同条件が 8〜9/10 で破綻していた (試聴確認済み)。本番既定の steps=40 でも結論は変わらない。

### D3: 字数則の単位は「文字」であって「トークン」ではない

**採用**: 句読点・括弧類を除いた符号点数 × 0.207。

**理由**: 実測で文字あたりの秒数の方がトークンあたりより安定していた。

| | token 数 | 字数(記号除) | 実測本文終端 | 秒/token | 秒/字 |
|---|---:|---:|---:|---:|---:|
| 32字 | 13 | 29 | 5.49 | 0.4223 | 0.1893 |
| 12字 | 6 | 10 | 2.05 | 0.3417 | 0.2050 |
| 54字 | 26 | 50 | 10.35 | 0.3981 | 0.2070 |
| ばらつき | | | | ±11% | **±5%** |

**トレードオフ**: 符号点数は日本語前提であり、他言語では再校正が要る。トークンの方が言語非依存だが、実測では安定性で劣った。**既定を「補正無効」にすることで、日本語以外の用途に影響を出さない。**

### D4: 短くしすぎない (下限を切らない)

**制約**: noref 予測を 0.2 秒下回らせると、余りは小さくなるのに**逆に残渣が出た** (試聴で 2 seed とも確認)。余りと発生率の単調性は下端で崩れる。尺が足りず圧縮された副作用と考えられる。

一方、遅い caption で余りが 0.06 秒まで詰まった条件では欠けも早口も出なかった。したがって危険なのは「余りが小さいこと」ではなく「**noref 予測を下回ること**」である。

`min` の 3 項のうち字数則は noref 予測を下回りうる (短文・長文で実際に下回り、それが必要だった)。**下回ること自体が禁止なのではなく、`min` が返す値が実発話長を割り込むことが危険**である。字数則は実発話長の推定なので、この構造では割り込まない。**実装では既存の `min_duration_sec` クランプを必ず維持すること。**

### D5: 既定は補正無効、有効化はオプションで

**理由**: audio.cpp fork は CLI / WebUI からも使われる。既定を変えるとそれらの出力が変わる。NovelViewer 側から明示的に有効化する。

**トレードオフ**: NovelViewer が有効化を忘れると v4 + caption が壊れたまま出荷される。→ Dart 側で「caption を渡すリクエストには補正オプションを必ず付ける」ことを spec 化し (`irodori-caption-synthesis`)、テストで担保する。

### D6: fork の差分は `irodori_tts/` 配下に閉じる

フレームワーク層に触らないため、他エンジンへの波及がない。`session.cpp` には既に自前パッチ (abort patch) の前例があり、upstream マージ時の扱いも同様にできる。

### D7: 最適化は後回し

追加コストはチャンクあたり condition パス 1 回 (text encoder + caption encoder + duration predictor)。RF 40 ステップ + codec decode に比べれば小さいはずだが、**実測すること**。既に `condition_ms` の計測がある。

重い場合、`has_*` に依存するのは duration predictor だけで text / caption の encode 結果は使い回せるため、duration 部分だけの小グラフに分ける余地がある。**最初はやらない。**

## Risks / Trade-offs

- **[検証した話者が実質 1 名]** → 別話者として使えたのは 1.13 秒しかない非典型な参照音声のみ。話者依存性が強い現象であることは実測で分かっている (同じテキスト・caption でも話者が違うと予測尺が 7.96 → 6.24 と変わる)。→ 実装後、複数の実利用参照音声で試聴確認を行う。オプション化してあるので係数の再調整は再ビルドなしで可能

- **[テキスト 3 種・日本語のみで係数を当てはめた]** → `text_rate = 0.207` は n=3 の当てはめ。→ 既定を補正無効にすることで影響範囲を限定。実装後に実小説テキストで追加検証する

- **[字数則が日本語の符号点数前提]** → 他言語では過大/過小になる。→ 現状 Irodori の用途は日本語。オプションで無効化できる

- **[検証は PyTorch 本家経路のみ]** → 製品は GGUF q8_0 + audio.cpp。予測尺・余り・発生率が両実装でほぼ一致することは確認済みだが、**補正後の再確認は C++ で未実施**。→ tasks の phase 5 で必須確認とする

- **[チャンク分割まわりは Python では検証不能]** → Python ハーネスは単一テキストを分割しない。**分割ごとに補正が効くことは C++ でしか確かめられない**。→ tasks の phase 5 で複数チャンクに分かれる長文を必須ケースにする

- **[steps=40 の確認が 1 セルのみ]** → 他条件は steps=24 (CPU 都合) での検証。確認したセルでは本文終端も余りも steps=24 と完全一致した。→ 実装後の C++ 確認は本番既定の steps で行う

- **[判定手段が試聴しかない]** → 区間数プロキシは偽陽性も偽陰性も出すため、回帰検知を自動化できない。→ 自動テストで担保するのは「補正オプションが正しく伝搬すること」「尺が期待値どおりに決まること」まで。**音の良し悪しは試聴でしか確認できない**ことを受け入れる

- **[C API の拡張形]** → 現行 `audiocpp_synthesize` は固定 7 引数。引数を足し続けると破綻する。→ options を渡す器 (構造体または key-value) を導入するが、既存呼び出しの後方互換を壊さないこと

- **[v4 + caption で補正を忘れると出荷事故]** → D5 のとおり spec + テストで担保する

## Migration Plan

1. audio.cpp fork に補正を実装 (既定オフ)。この時点では NovelViewer の挙動は一切変わらない
2. C シム 〜 Dart の伝搬経路を追加。まだ有効化しない
3. C++ / GGUF で補正の効果を確認 (phase 5)。ここで問題があれば 1 に戻る
4. `v4.supportsCaption` を `true` にし、caption 経路で補正を有効化。UI の制限表示を解除

**ロールバック**: `v4.supportsCaption` を `false` に戻せば、補正の有無にかかわらず元の状態に戻る。fork 側の補正は既定オフなので残しておいて害がない。

### D8: 契約解決は既存のシム機構で足りる (実装中に判明)

新しいリクエストオプションは `model_specs/irodori_tts.json` に登録するが、
`default_package_spec_path()` の優先順位は

```
--model-spec-override  >  GGUF 埋め込み  >  builtin  >  外部ファイル
```

であり、**配布済み GGUF の埋め込み契約が builtin より優先される**。このため CLI から
新オプションを渡すと `unknown Irodori-TTS request option` で弾かれる (実測)。

当初これを「GGUF 再生成が要るのでは」と危惧したが、**シムは既にこの問題を解いていた**。
`audiocpp_c_api.cpp` の `resolve_model_spec()` が DLL の隣の `model_specs/irodori_tts.json`
を探して `model_spec_override` に渡しており、これは最優先で効く。
`scripts/build_irodori_windows.bat` はそのファイルを配布先へコピーしている。

**したがってアプリ経路では追加作業は不要。** GGUF の再生成もユーザの再ダウンロードも要らない。
影響を受けるのは CLI から直接叩く場合だけで、そこは `--model-spec-override` を渡せばよい
(phase 4 の検証手順に反映済み)。
