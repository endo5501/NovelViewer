## Context

TTS入力テキストの生成は、次の一本道で行われる。

```
原文 .txt
   │
   ▼ TextSegmenter.splitIntoSentences()      改行 と 。！？ で分割。空チャンクは捨てる
   ├─ TextSegment[i] { text, offset, length }
   │
   ▼ applyDictionaryWithEntries(entries, text)  最長一致で surface→reading 置換
   │                                            ※ DBレコードを持たないセグメントにのみ適用
   ▼
 synthText ──► TtsSession.synthesize() ──► WAV ──► tts_segments.audio_data
```

合成を呼ぶ箇所はコードベース全体で2つしかない。

| 経路 | ファイル | 現在の判定 |
|---|---|---|
| 閲覧画面のストリーミング再生 | `tts_streaming_controller.dart` | `dbRow.audioData != null` → 無ければ生成 |
| 編集画面の単体生成／一括生成 | `tts_edit_controller.dart` | `!segment.hasAudio` → 生成対象 |

`tts-batch-generation` が指す一括生成は編集画面の `generateAllUngenerated` そのものであり、第3の合成経路は存在しない。

現状の制約:

- `TtsDictionaryRepository.addEntry` / `updateEntry` が `reading.isEmpty` で `ArgumentError` を投げる。辞書ダイアログも表記・読みの両方が非空であることを要求する。
- 一方で `applyDictionaryWithEntries` は `buffer.write(entry.reading)` を実行するだけなので、読みが空文字なら何も書かず、結果として削除として正しく振る舞う。変換アルゴリズムには手を入れる必要がない。
- `tts_dictionary.db` の `reading TEXT NOT NULL` は空文字を許容する。
- `tts_segments` には「生成不要」を表す状態が存在しない。

## Goals / Non-Goals

**Goals:**

- 辞書エントリで特定の文字列を読み上げ対象から除外できる（小説フォルダ全体に効くパターン単位の除外）。
- 読み上げ編集画面で、任意のセグメントを音声生成の対象外にできる（この話数のこの1文だけの除外）。
- 辞書適用の結果テキストが空になったセグメントが、合成へ渡って一括生成を停止させないようにする。
- スキップは誤操作から復帰可能であること。

**Non-Goals:**

- 「読み上げなし」の代わりに無音や間（ポーズ）を挿入すること。今回は純粋な削除・除外のみを扱う。
- 辞書エントリを既存の生成済み・編集済みセグメントへ遡って適用すること。現行の辞書と同じく、新規セグメントとリセット後のセグメントにのみ適用する。
- 閲覧画面（縦書き・横書き）からセグメントをスキップ指定する導線。操作は読み上げ編集ダイアログに限定する。
- セグメント分割規則の変更。辞書は分割の**後**に適用されるため、削除エントリはセグメント境界にもハイライトの `textOffset` にも影響しない。

## Decisions

### D1: 辞書の「読み上げなし」は `reading = ''` として保存する（列を追加しない）

チェックボックスはUI上の見せ方とし、永続化は既存の `reading` 列に空文字を入れることで表現する。一覧表示時は `reading.isEmpty` からチェック状態と「（読み上げなし）」表示を導出する。

*理由*: 「読みが空」と「読み上げなし」は同義であり、両者を区別する必要のある将来のケースが見当たらない。完全に導出可能な状態のために列を増やすと、2つの真実の源が生まれて不整合の余地ができる。またこの選択により `tts_dictionary.db` のマイグレーションが不要になる。

*代替案*: `no_reading INTEGER` 列を追加する。意図がDB上で明示的になるが、`reading` との整合を常に保つ責務が増え、マイグレーションのコストに見合わない。

### D2: セグメントのスキップは `tts_segments.skip` 列で表現する（テキストを空にする方式は採らない）

`skip INTEGER NOT NULL DEFAULT 0` を追加し、`tts_audio.db` を v3 → v4 へ移行する。手順は `memo` 列追加時（v2→v3）のテーブル再作成方式をそのまま踏襲する。

*代替案とその却下理由*: 「`text` が空文字ならスキップ」という表現はマイグレーション不要で魅力的だが、次の理由で採らない。

- 編集画面の行が空欄になり、元が何の文だったか判別できなくなる。ヒント表示には原文が出るが、それは「未編集」の行と区別がつかない。
- 本文欄を全消しした瞬間に意図せずスキップ状態が生まれる。
- 「読み上げないが原文は残しておきたい」という要求そのものと矛盾する。

### D3: スキップしても生成済み音声は削除しない

*理由*: 状態アイコンのクリックという軽い操作でスキップが切り替わるため、誤操作が起こり得る。数分かけた合成結果を一度のクリックで失う設計は割に合わない。音声を残せばスキップ解除が即座に元へ戻る。

*帰結（重要）*: 「音声を持つかどうか」ではスキップを判定できなくなる。したがって**すべての消費側に明示的なスキップ判定が必要**になる。音声を削除する設計であれば `hasAudio` の判定だけで自動的に除外されていた通し再生とMP3エクスポートも、明示的な除外が要る。特にエクスポートは、除外を忘れると「スキップしたはずの文がMP3に混入する」という気付きにくい不具合になる。

| 消費側 | 現在の条件 | 変更後 |
|---|---|---|
| 編集画面の一括生成対象 | `!hasAudio` | `!hasAudio && !skip` |
| 編集画面の通し再生 | `!hasAudio` なら次へ | `!hasAudio \|\| skip` なら次へ |
| ストリーミング再生ループ | 音声が無ければ生成 | `skip` なら再生も生成もせず次へ |
| MP3エクスポート | `audioData != null` を連結 | `skip` を除外 |
| 編集画面の完了判定 | `every(hasAudio)` | `every(hasAudio \|\| skip)` |
| 生成済みセグメント数 | `WHERE audio_data IS NOT NULL` | `... OR skip = 1` |
| 行の再生・再生成ボタン | `hasAudio` で活性 | スキップ行は非活性 |

### D4: 空テキストのスキップは「生成が到達した時点」でDBへ記録する（案B）

合成直前のテキストが `trim().isEmpty` の場合、合成を呼ばずに `skip = 1` のレコードを書き、次のセグメントへ進む。判定と記録は2つの合成サイト（`TtsEditController._generateSegmentWithEntries` と `TtsStreamingController` の再生ループ）に置く。

*代替案（案A）*: `TtsEditController.loadSegments` で辞書適用直後に空を検出し、その場で `skip = 1` を書く。開いた瞬間から「スキップ」と表示できる利点があるが、次の副作用を招く。

- ダイアログを開くという読み取り操作がDBへの書き込みを発生させる。`_ensureEpisodeExists()` が走り、何も生成していないのに `tts_episodes` 行が作られ、ファイルブラウザにバッジが出る。
- `_updateEpisodeStatusAfterReset` の「DBレコードが1つも無ければエピソードごと削除する」というロジックと正面から噛み合わない。

案Bなら現状の「開くだけでは何も起きない」性質が保たれ、合成サイトが2つしかないため漏れが生じにくい。「どのようにTTSをするかはDBに記録される」という要件は、記録の時点が生成実行時になるだけで満たされる。

*トレードオフ*: 生成前は当該行が「未生成」と表示される。必要であれば、テキストが空白のみの行に対して表示上のヒントを出すことは将来の追加で可能。

### D5: スキップの切替は状態アイコンのクリックに割り当てる

セグメント行は既に7要素（状態・本文・参照音声・メモ・再生・再生成・リセット）で幅が埋まっており、専用の列やチェックボックスを足すと本文欄とメモ欄の可変幅配分（既存要件の 5:2）を圧迫する。状態アイコンは既に生成状態を表す場所であり、スキップは第4の状態として自然に収まる。

*トレードオフ*: 発見しづらい。ツールチップで補う。応用的な機能であり、常用される操作ではないため許容する。

### D6: リセットと全消去はスキップも解除する

`resetSegment` / `resetAll` は既にテキスト・音声・メモ・参照音声のすべてを初期状態へ戻す。スキップだけ残るのは一貫しない。

辞書由来で空になっていた行は、リセット後に再び辞書適用で空になり、次の生成で再びスキップとして記録される。したがってこの挙動は自己整合する。

## Risks / Trade-offs

- **[エクスポートからの除外漏れ]** → D3により、音声を持ったままのスキップ行が存在する。除外を忘れると無音ではなく「スキップしたはずの音声」がMP3へ混入し、しかもエラーにならないため気付きにくい。エクスポート経路のシナリオをspecに明記し、テストで固定する。

- **[完了判定の取りこぼし]** → スキップ行を「充足」として数えないと、エピソードが永久に `completed` へ到達せず、ファイルブラウザの完了アイコンが付かない。判定箇所は編集画面（`every`）とストリーミング（`getGeneratedSegmentCount` との比較）の2つで、片方だけ直すと表示が経路によって食い違う。両方を同時に変更する。

- **[原文変更によるスキップの付き替わり]** → スキップは `segment_index` でマージされるため、原文が変わると別の文へ付く。これは既存のテキスト編集・メモと完全に同一の性質であり、新たなリスクではない。`text_hash` による既存の防御をそのまま適用し、追加対応は行わない（既知の限界として受け入れる）。

- **[テストフィクスチャへの誤った列追加]** → `test/features/tts/data/tts_audio_database_test.dart` は v1 / v2 / v3 のスキーマを手書きの `CREATE TABLE` で再現している。これらは**マイグレーションの入力**であり、`skip` 列を足してはならない。足すと v3 → v4 の `ALTER TABLE ... ADD COLUMN skip` が重複列で失敗し、あるいは移行済みの状態を入力にしてしまい、テストが実際の移行経路を検証しなくなる（`db-schema-test-fidelity` の要請は「テストのスキーマが実物と一致すること」であって「全フィクスチャを最新版に揃えること」ではない）。v4 の検証は、既存の v3 フィクスチャを入力とする新しいテストで行う。

- **[辞書が遡及しないことによる混乱]** → 読みなしエントリを追加しても、既に生成済み・編集済みの行には効かない。「読み替え」が効かない場合は音声を聞けば分かるが、「削除」が効いていないことは「元々そう読んでいた」と区別しづらい。既存の辞書と同じ挙動であり仕様変更は行わないが、ユーザーがリセットで対処できることを前提とする。

## Migration Plan

1. `tts_audio.db` の `_databaseVersion` を 3 → 4 へ。
2. `_onCreate` の `tts_segments` 定義に `skip INTEGER NOT NULL DEFAULT 0` を追加。
3. `_onUpgrade` に v3 → v4 の分岐を追加。`ALTER TABLE tts_segments ADD COLUMN skip INTEGER NOT NULL DEFAULT 0` で足りる（NOT NULL + DEFAULT のため SQLite の `ADD COLUMN` 制約に抵触しない）。v2→v3 のようなテーブル再作成は不要。
4. 既存DBは全行が `skip = 0` となり、挙動は変更前と同一。ロールバックは v4 で追加された列を無視するだけで成立するが、`openOrResetDatabase` の `deleteOnFailure: true` によりダウングレード時はDBが再作成される点に留意する。

`tts_dictionary.db` は変更なし。既存の空でない読みを持つエントリは影響を受けない。

## Open Questions

なし。当初の未決2点は次のとおり決定済み。

### D7: スキップ行の再生成ボタンは非活性とする

押下でスキップを解除してから生成する案は採らない。「生成不要」と「生成せよ」が同時に成立しないため、解除を明示的な操作（状態アイコンの押下）に一本化する。ボタンが押せないことが、そのセグメントが対象外であることの表示そのものになる。

### D8: 生成前の空テキスト行に視覚的ヒントは出さない

テキストが空白のみだがまだ生成されていない行は、生成が到達するまで「未生成」として表示する。D4（案B）が意図的に受け入れたトレードオフであり、専用の第5の表示状態を足すとスキップ状態との区別がユーザーにとって難しくなる。生成を一度通せばスキップとして表示されるため、混乱が持続しない。
