## Context

LLM 解析パイプライン（`LlmSummaryPipeline._parseJsonResponse`）は、LLM レスポンスを JSON デコードし、要求キー（`facts` / `summary`）の値が **文字列** であることを必須としている。文字列以外（`null`・数値・オブジェクト・配列）は一律「不正な構造」とみなし `LlmResponseFormatException` を投げて棄却する。

この設計は「Ollama の `format`（JSON スキーマによる構造化出力）が値を文字列に強制するので、パーサ側は文字列以外を防御的に弾けばよい」という前提（`ollama_client.dart` の `_formatFor` とコメント）に立っていた。しかし Ollama の **MLX ランナー**（例: `qwen3.8:27b-mlx`）は `format` を実際には強制しないことが確認された（`format` にスキーマを渡しても散文が返る）。安全網が外れた結果、賢いモデルはプロンプト例 `{"facts": "..."}` を「箇条書きは配列が自然」と解釈し `{"facts": ["事実1", "事実2"]}` を返す。内容は正しいのに配列であるため棄却され、解析全体が失敗する。

実ログでも `LLM response for facts decoded as JSON but had no string value; rejecting. prefix={"facts": [...]}` が多数記録されている。小型モデル（`gemma3n:e4b`）は例を素直に文字列でコピーするため成功しており、「大きいモデルほど失敗する」という逆転が起きている。

## Goals / Non-Goals

**Goals:**
- 要求キーの値が「文字列の配列」の場合、内容を失わずに単一文字列へ正規化して受理する。
- 正規化されたレスポンスを構造化デコード成功（`isStructured: true`）として扱い、既存のキャッシュ書き込みポリシー（`llm-summary-fact-cache`）にそのまま乗せる。
- ランナー実装（MLX / GGUF）に依存せず、パーサ単体で堅牢にする。

**Non-Goals:**
- `OllamaClient` の `format` 送信やスキーマ生成の変更（`format` はベストエフォートとして残す。強制されなくてもパーサが吸収する方針）。
- MLX ランナーが `format` を無視する挙動そのものへの対処（上流 Ollama 側の問題であり本変更の範囲外）。
- 配列以外の非文字列値（`null`・数値・オブジェクト）の受理（従来どおり棄却を維持）。
- プロンプトの変更（賢いモデルほど指示に従わない配列化を、プロンプト強化で防ぐのは不確実なため採らない）。

## Decisions

### 決定1: 正規化はパーサ側（`_parseJsonResponse`）で行う

`decoded[key]` が `List` の場合に分岐を追加し、全要素が `String` であれば `\n` 結合して単一文字列として返す。既存の `is String` 成功パスと同じく `isStructured: true` とする。

- **なぜ**: `format` の強制はランナー依存で信頼できない。パーサで吸収すればどのプロバイダ／ランナーでも一律に効く。プロンプト強化（案C）は賢いモデルほど守らず不確実。GGUF 版利用（案B）はモデル選択を縛る回避策にすぎない。
- **代替案**: `OllamaClient` 側でレスポンスを後処理 → パイプラインのプロバイダ非依存性が崩れ、`OpenAiCompatibleClient` 経由の Ollama でも同じ問題が再発するため不採用。

### 決定2: 各要素の結合形式は「素の `\n` 結合」

要素を改行で連結する。`- ` プレフィックスは付与しない。

- **なぜ**: プロンプトは箇条書き（`- 事実1\n- 事実2`）を期待するが、モデルが返す配列要素は `"- 機械化人は…"` のように既に `- ` を含む場合と含まない場合が混在する（実ログで両方確認済み）。パーサが機械的に `- ` を付けると二重化する。素の `\n` 結合なら要素の元の体裁を保て、後段の要約プロンプトは「重複統合」を指示しているだけなので箇条書き記号の有無に依存しない。
- **代替案**: `- ` 正規化（付いていなければ付ける）→ 判定ロジックが増え、要素内に改行を含むケースで崩れるため見送り。素結合で十分。

### 決定3: 空配列・非文字列要素混在は従来どおり棄却

配列だが (a) 空、または (b) `String` 以外の要素を含む場合は、箇条書きとして意味をなさないため `LlmResponseFormatException` を投げ、WARNING ログを出す（既存の非文字列棄却パスに合流）。

- **なぜ**: 「正しい内容の配列」だけを救済し、壊れた構造を無条件受理しない。空配列を受理すると空文字列が facts として下流に流れ、要約段が空エビデンスから捏造するリスク（既存 `LlmAnalysisNoFactsFailure` の意図）に反する。

## Risks / Trade-offs

- **[要素内に想定外の改行や JSON 断片が混入]** → 素の `\n` 結合なので生テキストがそのまま連結されるが、これは現状の文字列パスと同等のリスク。要約段の重複統合で吸収される。
- **[空配列を棄却することで、正当だが facts ゼロのケースも失敗扱いになる]** → facts ゼロは元々 `LlmAnalysisNoFactsFailure` で失敗させる設計であり、挙動として一貫。
- **[将来 `format` が MLX でも効くようになると配列は来なくなる]** → その場合も文字列パスが動くだけで、本変更は無害な後方互換の防御として残る。

## Migration Plan

- 純粋なパーサロジックの追加変更で、データ構造・永続化スキーマ・API は不変。マイグレーション不要。
- ロールバックは当該コミットの revert のみで完結（配列レスポンスが再び棄却されるだけで、文字列レスポンス動作は影響なし）。
