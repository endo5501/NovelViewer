## Context

Apple のオンデバイスモデルは `FoundationModelsClient` から `foundation_models_llm` プラグイン経由で呼ばれる。現在の実装は `LanguageModelSession()` を素の状態で作り、呼び出し側がスキーマを渡したときは `DynamicGenerationSchema` で制約をかける。`guardrailViolation` は `LlmOnDeviceRefusedFailure` に変換され、`LlmRetryableFailure.isWorthRetrying` が false を返すのでパイプラインは再試行しない。

実測でわかったこと。判定はモデルの出力に対して行われ、登場人物への否定的な記述が引き金になる。累積プレフィックスで境界を取ると結果が単調にならないため、入力の静的判定ではない。

実データ `narou_n9669bk/017` の「エドナ」で確認した結果は次の通り。12件の文脈は単体ならどれも通り、結合した964文字のチャンクだけが落ちる。

| 条件 | 実チャンク |
|---|---|
| スキーマあり + default | 拒否 |
| スキーマあり + permissive | 拒否 |
| スキーマなし + default | 拒否 |
| スキーマなし + permissive | 成功 |

スキーマを外すと反復ループで応答上限に当たり、JSON が閉じないまま切れる。`GenerationOptions(sampling:)` の指定でこれが変わる。

| サンプリング | 既存パーサで読めた割合 |
|---|---|
| 指定なし | 8回中4回 |
| `.greedy` | 8回中8回 |
| `.random(top: 50)` + 温度0.9 | 8回中3回 |

プロンプトに項目数の上限を書く方法は効かなかった（8回中4回）。`.greedy` は上限指定の有無にかかわらず 22回中22回成功した。

検証に使ったプローブは `scratchpad/guardrail-probe/` にある。

## Goals / Non-Goals

**Goals:**

- 無害な本文がガードレールで解析不能になる事象をなくす
- スキーマ制約が効いている通常経路の挙動を変えない
- 制約を外した経路の返答を、既存パーサが変更なしに読めるようにする
- ガードレール回避の方針を Dart 側の一箇所で読めるようにする

**Non-Goals:**

- MLX Swift などオンデバイスの別ランタイムの導入。今回は見送る
- プロンプト自体の書き換えによる回避
- 退化した経路を通ったことの読者への通知
- Ollama / OpenAI 互換プロバイダの挙動変更

## Decisions

### 再試行は Dart 側に置く

`FoundationModelsClient.generate` が二回呼ぶ。プラグインは一回の呼び出しにつき一回だけ生成する。

代案はプラグイン内で完結させることだった。往復が一回で済むが、何を諦めて何に切り替えるかというのは方針であって橋渡しではない。プラグインは `availability` と `generate` を素直に渡す薄い層として書かれており、そこに方針を埋めると、クライアント側のコードを読んでも二回呼ばれていることがわからなくなる。

### permissive は最初から使う

ガードレール拒否時だけ切り替える案もあったが、実測で不利益が見つからなかった。

| 条件 | 単体文脈12件 | 無害チャンク5回 |
|---|---|---|
| スキーマあり + default | 11/12 | 4/5 |
| スキーマあり + permissive | 12/12 | 5/5 |

出力も permissive の方が詳しい。同じ無害チャンクで default は一項目しか返さず、permissive は複数項目を返した。条件分岐を減らせる分だけ単純になる。

### greedy は制約なし経路にだけ渡す

スキーマ制約が効いている経路は現状で安定しており、サンプリングを変える理由がない。制約を外したときだけ反復が起きるので、そこにだけ `.greedy` を指定する。

プラグイン側で「スキーマがなければ greedy」と暗黙に決めることもできるが、それはプラグインに方針を持たせることになる。サンプリング方式は引数で受ける。

### ワイヤ表現

メソッドチャネルの `generate` 引数に `sampling` を足す。値は `'greedy'` か未指定。列挙を文字列で渡すのは `availability` の返り値と同じ流儀で、Swift 側で解釈できない値は未指定として扱う。

ガードレールは引数にしない。常に permissive なので、切り替える必要がない。将来必要になったときに足せばよい。

### 返答の形はパイプラインを変えずに吸収できる

制約なし経路の返答は、実測した範囲で次の2形のいずれかに収まった。どちらも既存の処理が吸収する。

1. コードフェンスで囲まれた、`facts` が文字列のオブジェクト。`_stripCodeFence` がフェンスを剥がし、`decoded[key] is String` の分岐が拾う。
2. コードフェンスで囲まれた、`facts` が文字列の配列であるオブジェクト。配列正規化が改行で結合する。

配列正規化は Ollama の MLX ランナー向けに既に入っているもので、今回そのまま再利用できる。

### ただし最終要約の段だけはパイプラインに手を入れる

当初は「パイプラインは一切変更しない」と決めていた。返答の形については上の通りで正しかったが、読めなかったときの扱いを見落としていた。レビューで指摘されて改めた。

最終要約の値は、何の判定も受けずにスナップショットとして保存され、そのまま読者の目に触れる。生テキストへの退避は既存の意図的な設計で、プロバイダによっては散文で答えるのが正常なので、そこは変えない。問題は、その退避が「打ち切られた JSON」まで拾うようになった点で、これは本変更が作った経路である。

`summarizeFromFacts` に `_readableOr` を挟み、読めない答えなら一度だけ問い直す。二度目も読めなければ一度目を残す。二度目が失敗しても一度目を残す。最悪値は今までと同じで、通常は改善される。

事実抽出の段は同じ扱いにしない。読めない抽出は `isStructured` が false になってキャッシュから外れるだけで、読者に見えるものは何も壊れない。

## Risks / Trade-offs

**制約なし経路の返答形が実測の2形に収まらない** → 既存の `_parseJsonResponse` は JSON デコード失敗時に生テキストへ落ちるので、解析が止まることはない。`.greedy` で 22回中22回成功しているが母数は小さい。実装時に両方の形と壊れた形のテストを書く。

最終要約の段だけは、この生テキスト落ちが読者の目に触れる。レビューで指摘を受けて、読めない答えが返ったら一度だけ投げ直す形にした。二度目も読めなければ一度目を残す。二度目が失敗しても一度目を残す。生テキスト落ち自体は既存の意図的な設計で、プロバイダによっては散文で答えるのが正常なので、そこは変えていない。変えたのは、読めない答えを一度も問い直さずに保存していた点だけ。

**前置き付きコードフェンスが剥がせない** → `_stripCodeFence` は文字列全体がフェンスであることを要求する。モデルが「以下がJSONです:」のような前置きを付けると剥がせず、その行は永久にキャッシュされないまま毎回2回生成を払う。実測22回では前置きは出なかったので、今は手を入れない。実地で観測されたら正規表現を非アンカー化する。

**`.greedy` の効果が本文依存である** → 検証したのは実データ1件と合成サンプル1件。別の小説で反復が再発する可能性は残る。その場合は生テキスト落ちとして観測できるので、まず記録に残す形にしておく。

**permissive でも拒否される本文が残る** → 今回の変更は拒否率を下げるものであって、ゼロにするものではない。残った拒否は従来通りファイル単位の失敗として隔離され、他のファイルの解析は続く。

**要約の質が下がる場合がある** → 制約なし経路では、モデルが項目を水増しする傾向が観測された。拒否されて何も出ないよりは良いという判断で受け入れる。

**Apple が構造化生成経路のガードレール適用を修正した場合** → 再試行が発火しなくなるだけで、通常経路がそのまま通る。害はない。

**再試行が一過性の理由で失敗すると、1チャンクあたり最大4回の生成になる** → 両レビューが独立に指摘した。拒否 → 制約なし再試行 → `rateLimited` などで失敗、という並びのとき、パイプラインの `_withSingleRetry` が `isWorthRetrying` を見て `generate` をもう一度呼び、その中でまた2回生成される。クライアント層の「1要求につき最大2回」は保たれており、パイプラインの一過性再試行も既存の方針そのままなので、どちらも単独では誤っていない。掛け算になるのは本変更が作った新しい並びなので、ここに記録する。オンデバイスは最も遅いプロバイダなので、実地で問題になるようなら先に見直すのはパイプライン側ではなくこの組み合わせ。

## Open Questions

- `.greedy` を制約あり経路にも広げるべきか。現時点では変える理由がないので現状維持とするが、制約あり経路でも `decodingFailure` が観測されているため、別の変更として検討する余地がある。
