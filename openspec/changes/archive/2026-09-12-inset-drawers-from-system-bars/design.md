## Context

narrow レイアウトは左カラムを `Drawer`、右カラムを `endDrawer` に移す。`Scaffold` のレイアウトはドロワーを原点に画面全体の大きさで配置するため、ドロワーはステータスバーの裏まで広がる。body は `AppBar` があるときに上インセットを取り除いた `MediaQuery` を受け取るが、その扱いはドロワーには及ばない。Flutter 3.41.2 の `Drawer` にも `SafeArea` は含まれない。

このアプリには現在 `SafeArea` が一箇所もない。デスクトップではインセットが常にゼロで、iPad でも body だけは `AppBar` に守られていたため、これまで表面化しなかった。

左右のドロワーに入る `LeftColumnPanel` と `SearchResultsPanel` は wide レイアウトでも同じものが使われる。

## Goals / Non-Goals

**Goals:**

- narrow レイアウトのドロワーの中身を、上下のシステム UI と重ならない位置に配置する
- 左右どちらのドロワーも同じ扱いにする
- wide レイアウトの見た目と挙動を一切変えない

**Non-Goals:**

- 横持ちの左右インセットへの個別対応。iPad にノッチがないため値はゼロで、対処すべき現象がない
- ドロワー内の検索入力欄がソフトウェアキーボードに隠れる件。ドロワーは `resizeToAvoidBottomInset` の対象外だが、これは重なり問題とは別の課題であり本変更では扱わない
- アプリ全体へのセーフエリア対応の展開

## Decisions

### インセットを `Drawer` の子として入れる

`Drawer` の `child` を `SafeArea` で包む。`Drawer` 自身の Material は画面全高を塗ったままなので、背景はステータスバーの下まで届き、中身だけが内側に寄る。ドロワーの下に地の色が透けることはない。

検討した代替案:

- **`LeftColumnPanel` の内部に入れる**: 同じウィジェットが wide レイアウトでも使われる。`Scaffold` は body の上インセットを取り除くので上端は無害だが、下インセットは残り、左カラムだけに余白が付いて中央のテキストビューアと不揃いになる。採らない。
- **`TabBar` にだけ上パディングを足す**: 右の検索ドロワーと下端が直らない。採らない。
- **ドロワーを `AppBar` の下から出す**: body 内に入れ子の `Scaffold` を置く構成。見た目は良いが、`_scaffoldKey` を介した開閉制御と既存のドロワーテスト群に広く影響する。得られるものに対して変更が大きい。採らない。

### `SafeArea` の既定値をそのまま使う

`top`、`bottom`、`left`、`right` はすべて既定の有効のままとする。iPad に左右インセットがないため、左右を明示的に無効化してもしなくても描画結果は同じであり、書かないほうが記述が少ない。

`maintainBottomViewPadding` も既定の false のままとする。キーボードが出ると下インセットはゼロになり、キーボードに覆われた領域に余白を残さない。これが望ましい振る舞いである。

### テストはビューのインセットを偽装して書く

`tester.view.padding` に `FakeViewPadding` を設定してインセットのある画面を再現し、ドロワーを開いて中身の上端と下端の座標がインセットの内側にあることを確かめる。テスト後に `tester.view.reset()` を呼んで他のテストに漏らさない。`FakeViewPadding` の値は物理ピクセルなので、論理ピクセルへの換算にデバイスピクセル比を使う。

既存の narrow レイアウトのテストはインセットをゼロのままにするので、`SafeArea` は何もしない。回帰は起きない。

## Risks / Trade-offs

- **ドロワーの表示可能な高さがインセット分だけ減る** → 減るのは元々システム UI に隠れて操作できなかった領域なので、実質的な損失はない
- **`SafeArea` の追加を他の画面にも広げたくなる** → 本変更はドロワーの重なりだけを直す。他の面はそれぞれ症状が確認されたときに扱う
- **テストが `tester.view` のグローバル状態に触れる** → ティアダウンで必ず `reset()` を呼び、テスト間の汚染を防ぐ
