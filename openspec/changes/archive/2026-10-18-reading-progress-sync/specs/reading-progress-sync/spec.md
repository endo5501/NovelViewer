# Spec Delta

## Purpose

利用者の Google Drive にあるアプリ専用領域を経由して、読書進捗（最後に開いた話とその中の本文位置）を端末間で共有する。別の端末で読み進めた小説を、続きの位置から開けるようにする。

## ADDED Requirements

### Requirement: 同期の対象は読書進捗だけである
システムは、登録済みの小説ごとの読書進捗（最後に開いた話、本文位置、本文ハッシュ）だけを同期しなければならない（SHALL）。小説本体、ブックマーク、TTS の結果、LLM の結果は同期してはならない（SHALL NOT）。
汎用 Web コレクションは、端末間で同じ小説であると判定できないため、同期の対象にしてはならない（SHALL NOT）。送信からも、受け取った記録の適用からも除外する。

#### Scenario: 汎用 Web コレクションは送らない
- **WHEN** 端末に `narou_n1234ab` と汎用 Web コレクション `web_my_list` の読書進捗がある状態で送信する
- **THEN** 送信される記録には `narou_n1234ab` だけが含まれる

#### Scenario: 受け取った汎用 Web コレクションの記録は使わない
- **WHEN** 他の端末の記録に `web_my_list` の進捗が含まれていて、この端末で `web_my_list` のフォルダに入る
- **THEN** その記録は適用されず、確認も表示されない

### Requirement: 各端末は自分の記録だけを書き込む
システムは、Google Drive のアプリ専用領域に、端末ごとに 1 つの記録ファイルを置かなければならない（SHALL）。各端末は自分の記録ファイルだけを作成・更新しなければならず（SHALL）、他の端末の記録ファイルを書き換えてはならない（SHALL NOT）。
記録には、形式の版、端末 ID、端末名、そして小説ごとに「実効エピソード番号」「ファイル名」「本文位置」「本文ハッシュ」「位置が動いた時刻（UTC）」を含めなければならない（SHALL）。
知らない形式の版の記録ファイルは、WARNING をログに出して無視しなければならない（SHALL）。

#### Scenario: 2 台の端末が交互に送信しても互いの記録を消さない
- **WHEN** 端末 A と端末 B が、それぞれ別の小説の進捗を送信する
- **THEN** アプリ専用領域には A の記録ファイルと B の記録ファイルがあり、それぞれの小説の進捗が残っている

#### Scenario: 知らない形式の記録を無視する
- **WHEN** 取得した記録ファイルの形式の版が、この端末が対応していない値である
- **THEN** そのファイルの記録は使われず、WARNING が `Logger('progress_sync')` に出力され、他の端末の記録の取得は続行される

### Requirement: 位置が動いた時刻は、開いただけでは進まない
記録の「位置が動いた時刻」は、その小説の位置が、前回送信した位置から動いたときにだけ更新しなければならない（SHALL）。同じ実効エピソード番号で、本文位置の差が許容幅未満の場合は、同じ位置とみなさなければならない（SHALL）。
同じ位置のまま小説を開いただけでは、時刻を進めてはならない（SHALL NOT）。
他の端末の記録を適用したとき（自動適用と、確認で「移動する」が選ばれたとき）は、その位置を、記録元の時刻のまま、前回送信した位置として扱わなければならない（SHALL）。
取得では、自分の端末の記録ファイルを、他の端末の記録として扱ってはならない（SHALL NOT）。

#### Scenario: 開いただけでは時刻が変わらない
- **WHEN** 3 話の位置 1000 を送信した後、同じ小説を開き直し、位置 1000 から動かさずに再び送信する
- **THEN** 送信される 3 話の記録の時刻は、前回送信した時刻と同じである

#### Scenario: 受け取った記録を適用しただけでは時刻が進まない
- **WHEN** Windows が時刻 T に送信した 5 話の記録を iPad が適用し（自動適用、または確認で「移動する」）、iPad で位置を動かさずに送信する
- **THEN** iPad が送信する 5 話の記録の時刻は T のままで、Windows で同じ小説に入っても確認は表示されない

#### Scenario: 読み進めると時刻が変わる
- **WHEN** 3 話を送信した後、4 話を開いて読み、再び送信する
- **THEN** 送信される記録は 4 話を指し、時刻は 4 話の進捗が保存された時刻である

### Requirement: 同期のタイミング
ログインしている間、システムは次のときに他の端末の記録を取得しなければならない（SHALL）。
- アプリの起動時（前回の終了時の送信が届いていない場合に備え、取得の前に自分の記録を送信する）
- アプリが前面に戻ったとき

システムは次のときに自分の記録を送信しなければならない（SHALL）。
- 小説フォルダから離れたとき（別の小説や、小説ではない場所へ移ったとき）
- アプリが非表示または一時停止の状態になったとき
- アプリの終了が要求されたとき（終了を長く妨げないよう、時間を区切る）

設定画面の「今すぐ同期」では、送信してから取得しなければならない（SHALL）。
送信の前には、保存待ちの本文位置を書き込まなければならない（SHALL）。送信する内容が前回送った内容と同じなら、アップロードしてはならない（SHALL NOT）。
取得と送信は同時に実行してはならず（SHALL NOT）、実行中に来た要求は、実行が終わった後に 1 回にまとめて実行しなければならない（SHALL）。
デスクトップでウィンドウがフォーカスを失っただけでは、送信してはならない（SHALL NOT）。

#### Scenario: 小説を離れると送信される
- **WHEN** ログインしている状態で、小説フォルダからライブラリのルートへ移る
- **THEN** 保存待ちの位置が書き込まれた後で、自分の記録が送信される

#### Scenario: 内容が変わっていなければアップロードしない
- **WHEN** 前回の送信後、どの小説の位置も変わっていない状態で送信の契機が来る
- **THEN** Drive へのアップロードは行われない

#### Scenario: 連続した要求はまとめられる
- **WHEN** 送信の実行中に、送信の要求が 3 回来る
- **THEN** 実行中の送信が終わった後、送信は 1 回だけ実行される

#### Scenario: 起動時に送信してから取得する
- **WHEN** ログイン済みの状態でアプリを起動する
- **THEN** 自分の記録が送信され（前回から変わっていなければアップロードはしない）、その後で他の端末の記録が取得されて、この端末に保持される

### Requirement: 受け取った記録の話を、実効エピソード番号で特定する
他の端末の記録を適用するとき、システムは小説フォルダの一覧から、実効エピソード番号（`episode-resolution` の共有規則）が記録と一致するファイルを特定しなければならない（SHALL）。一致するファイルが 1 つに決まらない場合は、ファイル名が一致するファイルを使わなければならない（SHALL）。それでも決まらない場合は、適用してはならず（SHALL NOT）、記録を保持したまま次の機会に再び試みなければならない（SHALL）。
本文ハッシュが一致しない場合の扱いは、`reading-position` の検証規則に従う（その話の先頭から開く）。

#### Scenario: ゼロ埋めの桁数が違っても同じ話を開く
- **WHEN** 他の端末の記録が 5 話（ファイル名 `05_第五話.txt`）を指し、この端末のフォルダには `005_第五話.txt` がある
- **THEN** `005_第五話.txt` が適用先として選ばれる

#### Scenario: その話がまだ無い
- **WHEN** 他の端末の記録が 120 話を指し、この端末のフォルダには 100 話までしか無い
- **THEN** 記録は適用されず保持され、小説を更新して 120 話ができた後に入ったときに適用される

### Requirement: この端末に進捗が無い小説には、受け取った記録を自動で適用する
この端末に読書進捗が無い小説のフォルダに入ったとき、他の端末から受け取った記録があれば、システムは最も新しい記録を、確認せずに適用しなければならない（SHALL）。この判断は、以前の確認で「このまま」が選ばれたかどうかに関わらず行わなければならない（SHALL）。
まだダウンロードしていない小説の記録も保持し、その小説をダウンロードした後に初めてフォルダに入ったときに適用しなければならない（SHALL）。

#### Scenario: 別の端末で読んだ小説を初めて開く
- **WHEN** Windows で 5 話まで読んで送信した小説を、iPad で新しくダウンロードし、取得の後でそのフォルダに入る
- **THEN** 確認なしに 5 話が開き、Windows で読んでいた位置が表示される

#### Scenario: 削除してダウンロードし直した小説
- **WHEN** 以前の確認で「このまま」を選んだ小説を削除し、ダウンロードし直してフォルダに入る
- **THEN** 受け取った最も新しい記録が確認なしに適用される

### Requirement: この端末に進捗がある小説では、移動するかを確認する
この端末に読書進捗がある小説のフォルダに入ったとき、他の端末から受け取った記録の中で最も新しいものが次のすべてを満たす場合、システムはこの端末の進捗で開いた後に、その記録の位置へ移動するかを確認しなければならない（SHALL）。
- 位置が動いた時刻が、この端末の現在の記録の時刻より新しい
- 位置が動いた時刻が、この小説で以前に確認した記録の時刻より新しい
- この端末の位置と同じ位置ではない
- 話を特定できる

確認には、記録元の端末名、話の番号、位置が動いた日時を示さなければならない（SHALL）。「移動する」が選ばれたら、その記録の話と位置を開き、この端末の進捗をその位置に更新しなければならない（SHALL）。「このまま」が選ばれた、または確認が閉じられた場合は、位置を変えてはならない（SHALL NOT）。どちらの場合も、その記録を確認済みとして記録しなければならない（SHALL）。
確認済みの記録より新しい記録を受け取らない限り、同じ小説で再び確認してはならない（SHALL NOT）。条件を満たさない場合は、確認を出さずにこの端末の進捗で開かなければならない（SHALL）。

#### Scenario: 別の端末で先まで読んでいた
- **WHEN** iPad に 3 話の進捗があり、その後 Windows で 5 話まで読んで送信し、iPad で取得してからフォルダに入る
- **THEN** iPad はまず 3 話を開き、「Windows (…) で 5 話を読んでいました（日時）。移動しますか？」と確認する

#### Scenario: 移動を選ぶ
- **WHEN** 上の確認で「移動する」を選ぶ
- **THEN** 5 話が開いて Windows の位置が表示され、iPad の読書進捗は 5 話のその位置になる

#### Scenario: このままを選ぶと再び聞かない
- **WHEN** 確認で「このまま」を選び、新しい記録を受け取らないまま同じ小説に入り直す
- **THEN** 確認は表示されない

#### Scenario: 開いただけの端末に戻されない
- **WHEN** iPad が 3 話の進捗を送信済みの小説を、その後 Windows で 5 話まで読んで送信し、iPad でその小説を開いて（確認には「このまま」を選び）何も動かさずに閉じて送信し、Windows で同じ小説に入る
- **THEN** Windows では確認は表示されず、5 話が開く

#### Scenario: 同じ位置なら確認しない
- **WHEN** 他の端末の最も新しい記録が、この端末と同じ話で、本文位置の差が許容幅未満である
- **THEN** 確認は表示されない

### Requirement: 取得が終わったら、開いている小説を照合する
取得が終わったときに小説フォルダの中にいる場合、システムはその小説について、フォルダに入ったときと同じ規則で照合しなければならない（SHALL）。この端末に進捗がある場合は、表示中のファイルを選び直さずに、必要なら確認だけを出さなければならない（SHALL）。

#### Scenario: 起動直後の取得が後から終わる
- **WHEN** 起動時に前回読んでいた小説が自動で開かれ、その後に終わった取得で、他の端末のより新しい別の位置が届く
- **THEN** 表示はそのまま、移動するかの確認が表示される

### Requirement: 同期の失敗は読書を妨げない
取得・送信・認証の失敗は、WARNING レベルで `Logger('progress_sync')` に記録しなければならない（SHALL）。失敗によって、エラーダイアログを出したり、読書の操作を止めたりしてはならない（SHALL NOT）。失敗した送信は、次の契機で最新の状態から組み立て直して送らなければならない（SHALL）。
最後に同期が成功した時刻と、最後の失敗の内容は、設定画面の同期セクションで確認できなければならない（SHALL）。

#### Scenario: オフラインで小説を離れる
- **WHEN** ネットワークに接続していない状態で小説フォルダを離れる
- **THEN** WARNING が記録され、ライブラリの操作はそのまま続けられる
- **AND** 次に接続できた契機で、その時点の進捗が送信される

### Requirement: 使えない状態では通信しない
同期が無効なビルド、またはログインしていない状態では、システムは取得も送信も行ってはならず（SHALL NOT）、Google への通信を発生させてはならない（SHALL NOT）。同期の実行の入口そのものが拒否しなければならず（SHALL）、画面側の制御だけに頼ってはならない（SHALL NOT）。
この状態でも、読書進捗の保存と自動オープンは、同期が無いときと同じに動作しなければならない（SHALL）。

#### Scenario: ログインしていない
- **WHEN** ログインしていない状態で、アプリの起動、小説の移動、バックグラウンドへの移行が起きる
- **THEN** Google へのリクエストは 1 件も発生しない

#### Scenario: 入口を直接呼んでも通信しない
- **WHEN** 同期が無効なビルドで、同期の実行を画面を経由せずに直接呼ぶ
- **THEN** 何も実行されず、リクエストは発生しない
