## Context

LLM設定の読み書きは `SettingsRepository` の4つのメソッドに閉じている。

| 方向 | メソッド | 保存先 |
|---|---|---|
| 書き込み | `setLlmConfig` | SharedPreferences |
| 書き込み | `setApiKey` | flutter_secure_storage |
| 読み出し | `getLlmConfig` | SharedPreferences |
| 読み出し | `getApiKey` | flutter_secure_storage |

呼び出し側は設定画面 (`llm_settings_section.dart`) と `llmConfigProvider` / `llmClientProvider` だけで、他に書き込み経路はない。したがってリポジトリ層に正規化を置けば全経路を覆える。

設定不足の判定は現在 `llmClientProvider` の中に散っている。OpenAI互換APIでAPIキーが空のときだけ null を返し、エンドポイントURLやモデル名が空でもクライアントは生成される。生成されたクライアントは `Uri.parse('$baseUrl/chat/completions')` で `FormatException` を投げるか、モデル名なしのリクエストとしてサーバに拒否される。

文言を決める側は `analysis_runner.dart` の `_noServiceMessage` にあり、オンデバイスモデルについては可用性に応じた3種の案内を出し分けている。サーバ系プロバイダにはその粒度がない。

## Goals / Non-Goals

**Goals:**

- 入力欄に紛れ込んだ空白や末尾スラッシュが、解析実行時の不透明なエラーに化けないようにする。
- 既に空白付きで保存されている設定を、利用者の操作なしに救済する。
- 設定が不足しているとき、リクエストを送る前に不足項目を名指しする。
- クライアント生成の可否と利用者に見せる文言を、同じ判定から導いて二重管理を避ける。

**Non-Goals:**

- HTTPリクエストのタイムアウト導入。別changeで扱う。
- 解析進行モーダルのキャンセル操作。導入しない方針を決定済み。
- 設定画面でのインライン検証（入力中に赤字で警告する等）。実行時の案内で足りる。
- エンドポイントURLの到達性検査。ネットワークアクセスを伴う検証は行わない。
- エンドポイントURLの到達性以外の形式検証。スキームやポートの妥当性は判定しない。

## Decisions

### 決定1: 正規化を書き込み時と読み出し時の両方に置く

書き込み時だけでは、既に保存済みの壊れた値が残る。読み出し時だけでは、SharedPreferences の中身が汚れたままになる。両方に置くと、読み出し側がマイグレーションの役割を果たし、次にいずれかの設定が保存された時点で保存値も洗われる。専用のマイグレーション処理は書かない。

検討した代替案:

- 読み出し時のみ。保存値が汚れたままで、他の読み手が将来増えたときに漏れる。
- 書き込み時のみ + 起動時マイグレーション。既存の `migrateApiKeyToSecureStorage` と同じ形になるが、値の正規化のためだけに起動時処理を1つ増やすのは重い。

### 決定2: 正規化は `SettingsRepository` に置き、設定画面のコントローラには書き戻さない

設定画面のコントローラは `initState` で `getLlmConfig()` から初期化され、以後は書き戻されない。この性質を保つ。書き戻すと、末尾スラッシュを打った瞬間に消える、`http://` の入力途中が壊れる、といった挙動になる。

結果として、既に空白付きで保存されている設定は、次に設定画面を開いた時点で表示も直る。

一方、`ollamaModelListProvider` に渡すURLだけは正規化を通す。当初はコントローラの生テキストのままにする予定だったが、レビューで行き止まりが判明した。貼り付け直後は保存値が正規化されてもフィールドには空白が残るため、モデル一覧の取得が `Uri.parse` で失敗し、ドロップダウンが空になる。読者はモデルを選べないまま解析を実行し、「モデル名を入力してください」と言われる。フィールドへの書き戻しは行わないまま、取得キーだけを正規化する。

### 決定3: 正規化の内容を項目ごとに分ける

| 項目 | 前後の空白 | 末尾スラッシュ |
|---|---|---|
| エンドポイントURL | 除去する | 除去する |
| モデル名 | 除去する | 除去しない |
| APIキー | 除去する | 除去しない |

末尾スラッシュを落とすのはエンドポイントURLだけ。クライアントが `'$baseUrl/chat/completions'` のように連結するため、`http://host/v1/` がそのまま渡ると二重スラッシュになる。連続した末尾スラッシュは全て落とす。

ただしクエリ文字列やフラグメントを持つ値は例外とし、末尾スラッシュを残す。`https://host/proxy?route=/v1/` の末尾の `/` はパスの区切りではなくクエリの一部であり、こちらが解釈していないデータである。落とせば同じリクエストの正規形ではなく別のリクエストになる。

モデル名とAPIキーにスラッシュの規則はない。モデル名には `org/model` 形式のものがあり、末尾でなくとも触るべきではない。APIキーは値そのものであり、内部を触ることは許されない。いずれも前後の空白除去にとどめる。

APIキーの空白除去は目的が他と異なる。ペーストで末尾に改行が紛れると `Authorization: Bearer sk-xxx\n` となり、HTTPヘッダの検証で失敗するか、サーバに401で拒否される。エンドポイントURLより気づきにくい。

### 決定4: 不足判定を純粋関数に切り出す

```
findLlmConfigProblem(config, apiKey) -> LlmConfigProblem?
```

| プロバイダ | 必須項目 |
|---|---|
| 未設定 | なし（`noProvider` を返す） |
| Ollama | エンドポイントURL、モデル名 |
| OpenAI互換API | エンドポイントURL、モデル名、APIキー |
| オンデバイス | なし（null を返す） |

この関数を `llmClientProvider`（クライアントを作るか否か）と `_noServiceMessage`（どの文言を出すか）の両方から使う。判定を1箇所に置くことで、クライアントが作られないのに汎用の文言が出る、あるいはその逆、という不整合が構造的に起きなくなる。

純粋関数であるため、プロバイダとRiverpodのコンテナを立てずにテストできる。

検討した代替案: `llmClientProvider` が理由付きの結果型（`Either` 相当）を返す。判定は1箇所に寄るが、`LlmClient?` を期待する既存の読み手すべてに影響が及ぶ。判定だけを切り出す方が変更範囲が小さい。

### 決定5: 不足時はクライアントを生成しない

現在はAPIキー未設定のみが null を返す。これを「必須項目が1つでも欠けていれば null」に広げる。生成してから失敗させるより、生成しない方が失敗の位置が入口に寄り、原因が明確になる。

オンデバイスモデルの分岐は変えない。`findLlmConfigProblem` はオンデバイスに対して常に null を返し、可用性の判定は既存の `onDeviceModelAvailabilityProvider` に委ねられたままとなる。

### 決定6: 不足の案内は素のスナックバーで出す

直前のchangeで導入した永続スナックバー + 詳細ダイアログの経路は使わない。設定不足には原因となる例外もスタックトレースも存在せず、詳細ダイアログを開いても診断情報の一覧が出るだけで、読者が得るものがない。文言自体が短く具体的であるため、既存の表示時間で読み切れる。

この経路は `analysis_runner.dart` の `_snack` をそのまま使う。

### 決定7: 既存の文言はプロバイダ未選択の case に残す

「設定画面でLLMを設定してください」(`llmAnalysis_noLlmConfigured`) は `noProvider` の文言として残す。もともとその状況を指す文であり、役割が正しい位置に収まる。

新規に追加する文言は3つ。

| キー | 用途 |
|---|---|
| `llmAnalysis_missingEndpoint` | エンドポイントURLが未設定 |
| `llmAnalysis_missingModel` | モデル名が未設定 |
| `llmAnalysis_missingApiKey` | APIキーが未設定 |

日本語・英語・中国語の3言語すべてに追加する。既存文言と同じく、設定画面へ向かわせる形で書く。

### 決定8: 判定の優先順位を固定する

複数の項目が同時に欠けている場合、返す `LlmConfigProblem` は1つに定める。順序はエンドポイントURL、モデル名、APIキーとする。接続先が決まらなければ他の項目を埋めても進めないため、利用者が最初に埋めるべき項目を先に示す。

## Risks / Trade-offs

**エンドポイントURLの末尾スラッシュを意図的に付けている利用者がいる** → 除去してもリクエストURLは変わらない。クライアントは常に `/` 始まりのパスを連結するため、除去後の方が正しい形になる。

**APIキーの前後に空白を含む正当な鍵が存在しうる** → 既知の発行形式にそのようなものはない。前後の空白を含む鍵を扱えなくなるが、改行混入で沈黙のうちに401になる現状より、失敗の確率は下がる。

**`findLlmConfigProblem` が厳しすぎて、これまで動いていた設定が弾かれる** → 判定は空文字列の検査のみで、形式の検証は行わない。ただしモデル名については、既定のモデルを持つOpenAI互換プロキシに対して空のまま送れば動いていた、という構成があり得る。その構成は今後拒否される。モデル名を明示する一手間と引き換えに、モデル名を書き忘れた大多数が受け取るエラーを取り除く判断とする。

**APIキーがプロバイダにキャッシュされ、保持時間が延びる** → `llmApiKeyProvider` を `autoDispose` とし、OpenAI互換API以外を選択した時点で監視が外れて破棄されるようにする。

**設定は完全なのにサービスが構築できなかった場合、汎用の「設定画面でLLMを設定してください」が出る** → 変更前からの挙動であり、代わりに出せる正確な文言がない。リポジトリ側のFutureが先に例外を投げるため、実際にはほぼ到達しない。

**読み出し時の正規化が毎回走る** → 文字列の `trim` と末尾文字の除去のみで、`getLlmConfig` は SharedPreferences の同期読み出しである。無視できる。
