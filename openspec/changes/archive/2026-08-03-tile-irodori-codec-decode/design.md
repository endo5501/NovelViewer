# 設計

## 前提となる計測値

### 環境の壁 (実測)

```
$ vulkaninfo | grep -E "deviceName|maxBufferSize|maxMemoryAllocationSize|maxStorageBufferRange"
deviceName              = AMD Radeon RX 6800
maxStorageBufferRange   = 4294967295     (4 GiB - 1)
maxMemoryAllocationSize = 0x80000000     (2 GiB)
maxBufferSize           = 0x80000000     (2 GiB)
```

`ggml-vulkan.cpp:2666` が確保前にこの上限をチェックして `vk::OutOfDeviceMemoryError` を投げる。よって**失敗時に VRAM 使用量は増えない**。この特性が「GPU メモリに余裕があるのに落ちる」という一見矛盾した症状を作る。

ggml 側のエラーは `std::cerr` に出るため (`ggml-vulkan.cpp:2859`, `ggml-alloc.c:939`)、Flutter の `app.log` には残らない。診断には `audiocpp_cli` をターミナルから直接実行する必要がある。

### メモリ消費のモデル

デコーダで最大になるのは block3 / block4 の residual unit にある `Conv1d(k=7)` の im2col テンソル。両者は偶然ぴったり同サイズになる。

| ブロック | 出力長 | チャンネル | im2col 要素数 |
|---|---|---|---|
| block3 | 960 F | 192 | 960F × (192×7) = 1,290,240 F |
| block4 | 1920 F | 96 | 1920F × (96×7) = 1,290,240 F |

DACVAE の重みは f32 (`weights.safetensors` 429 MB) で、`codec_weight_storage_type_` の既定が `Native` (ソース dtype 保持) のため im2col も f32 になる。`ggml_conv_1d` は im2col の型を重みの型に合わせる (`ggml.c:4561`)。

```
単一テンソル = 5.16 MB × latent_steps = 129 MB / 音声 1 秒
2 GiB / 129 MB = 16.6 秒   ← f32 での限界
```

### 実測による裏付け (タスク 1)

`audiocpp_cli` を Vulkan バックエンドで直接実行し、問題の 116 文字の一文を合成した結果:

```
ggml_vulkan: Device memory allocation of size 2570158080 failed.
ggml_vulkan: Requested buffer size exceeds device buffer size limit: ErrorOutOfDeviceMemory
ggml_gallocr_reserve_n_impl: failed to allocate Vulkan0 buffer of size 4222414848
audiocpp_cli failed: failed to allocate Irodori-TTS codec graph
```

失敗したチャンクは **2,570,158,080 バイト**。1 フレームあたり 5,160,960 バイト (= 1,290,240 要素 × 4) で割ると

```
2,570,158,080 / 5,160,960 = 498.0 フレーム   ← 端数なしの完全一致
```

**モデルの検証はこれで完了**である。チャンクは「最大の単一テンソル 1 個」でちょうど埋まっており、`ggml-alloc.c:170` の「単一テンソルが `max_chunk_size` を超えるときだけ専用チャンクを作る」という挙動とも整合する。グラフ全体は 4,222,414,848 バイト (3.93 GiB) で、複数チャンクに分散していた。

latent_steps = 498 → **19.92 秒**。同じ文を 2 つに割った場合:

| ケース | latent フレーム | 秒 | 最大単一テンソル | 結果 |
|---|---:|---:|---:|---|
| 元の一文 | **498** | 19.92 | **2.39 GiB** | 確保失敗 |
| 分割 1 | 347 | 13.88 | 1.67 GiB | 成功 (壁まで 20%) |
| 分割 2 | 128 | 5.12 | 0.62 GiB | 成功 |

**分割 1 が壁の 80% に達している点は注目に値する。** 13.88 秒という決して極端でない長さで既に余裕が 2 割しかない。閾値 16.64 秒は「稀にしか踏まない特殊ケース」ではなく、日常的な長さのすぐ隣にある。

(測定条件: AMD Radeon RX 6800 / Vulkan / seed 1234 / 参照音声なし / `num_inference_steps` 既定)

### なぜ「単一テンソル」が指標なのか

`ggml_dyn_tallocr` はチャンクを最大 16 個作れる (`ggml-alloc.c:95`)。チャンクの既定サイズは `suballocation_block_size` = 1 GB (`ggml-vulkan.cpp:5240`) で、**単一テンソルがそれを超えるときだけ**専用の大きなチャンクが作られる (`ggml-alloc.c:170`)。したがって:

- 単一テンソル ≤ 1 GB → 全チャンクが 1 GB 以下。合計 16 GB まで使えて壁に触れない
- 単一テンソル ≤ 2 GiB → 専用チャンクが作られるが確保は成功する
- 単一テンソル > 2 GiB → **確保失敗**

グラフ全体のサイズではなく単一テンソルのサイズが閾値を決める。

## D1. タイル分割は近似ではなく厳密である

**決定**: オーバーラップ付きタイル分割を採用し、「音質への影響を実機で確認する」ではなく「直接経路との一致をユニットテストで検証する」ことを受け入れ基準とする。

**理由**: デコーダ (`codec.cpp:220-253`, `189-218`, `336-375`) を全て読んだところ、構成要素は次の 5 つだけだった。

- `Snake1dModule` — 要素毎 (時間軸に対して局所)
- `Conv1dModule` — 有限カーネル
- `ConvTranspose1dModule` — 有限カーネル
- `SliceModule` — 位置の付け替えのみ
- `AddModule` — 要素毎

**GroupNorm / LayerNorm / Attention のような系列全体に依存する演算が 1 つも無い。** よって出力の各サンプルは有限の入力窓にしか依存しない。

受容野を層ごとに積むと (片側):

| 層 | そのスケールでの文脈 | latent フレーム換算 |
|---|---|---:|
| `decoder_input` Conv1d k7 pad3 dil1 | ±3 latent | 3.000 |
| block1 ConvT k24 s12 | ±1 latent | 1.000 |
| block1 residual ×3 (dil 1/3/9, pad 3d) | ±39 @12× | 3.250 |
| block2 ConvT k20 s10 | ±1 @12× | 0.083 |
| block2 residual ×3 | ±39 @120× | 0.325 |
| block3 ConvT k16 s8 | ±1 @120× | 0.008 |
| block3 residual ×3 | ±39 @960× | 0.041 |
| block4 ConvT k4 s2 | ±1 @960× | 0.001 |
| block4 residual ×3 | ±39 @1920× | 0.020 |
| watermark Conv1d k7 pad3 | ±3 @1920× | 0.002 |
| **合計** | | **7.73 → 8** |

**受容野は片側 8 latent フレーム。** overlap がこれ以上あれば、タイル内の畳み込みが境界に入れるゼロパディングは全てトリム領域に落ちるので、**残す中央部分はフル復号とビット一致する**。

さらに全ての Conv1d が長さを保つ (pad = (k-1)·d/2、k は奇数) ため、T フレームのタイルは厳密に 1920·T サンプルを出す。トリム位置の計算に丸めが入らない。

**却下した案**: streaming conv (境界の活性を状態としてキャッシュする) 方式。`src/framework/modules/streaming_conv_modules.cpp` に基盤はあるが、オーバーラップ再計算が 14% しかないのに対して実装と検証の複雑さが桁違いに大きい。

## D2. tile の既定はバックエンド別 (Vulkan 256 / それ以外 512)、overlap は一律 16

**決定**:

```
Vulkan            → tile 256 (10.24 秒)
Metal / CUDA / CPU → tile 512 (20.48 秒)
overlap           → 16 (全バックエンド共通)
```

### なぜバックエンドで変えるのか

**2 GiB の壁は Vulkan/AMD 固有であり、他バックエンドには単一バッファの上限が存在しない。** 各バックエンドの `get_max_size` 実装を確認した結果:

| バックエンド | 単一バッファ上限 | 根拠 |
|---|---|---|
| **Vulkan / AMD RX 6800** | **2 GiB (固定)** | ドライバ申告 `maxBufferSize = 0x80000000`。`ggml-vulkan.cpp:2666` が確保前に弾く |
| Vulkan / NVIDIA | ドライバ申告次第 (通常は大きい) | 同上のチェックは通る |
| CUDA | **無し** | `ggml-cuda.cu:823` `get_max_size = NULL // defaults to SIZE_MAX` |
| CPU | **無し** | `ggml-backend.cpp:54` 同上 |
| Metal | `MTLDevice.maxBufferLength`。**超過分はビュー分割で自動吸収** | `ggml-metal-device.m:1611-1640` |

したがって Vulkan 以外では tile を大きく取れる。壁が無い環境に Vulkan と同じ制約を課すのは、理由の無いオーバーヘッドを払わせることになる。

`src/models/ace_step/vae_decoder.cpp:764-770` の `decode_direct_frame_limit()` が既に同じ形でバックエンド別の定数を持っており、本リポジトリでは確立された書き方である。分岐は `codec.cpp` の `decoder_block()` が既に使っている `ctx.backend_type == core::BackendType::Vulkan` と同じ形式で書く。

### Vulkan の 256 の根拠

単一テンソル 5.16 MB/フレームに対する選択肢:

| tile | 最大テンソル | 壁 (2 GiB) 比 | stride (ov=16) | 長文時のオーバーヘッド |
|---:|---:|---:|---:|---:|
| 128 | 660 MB | 31% | 96 | +33% |
| 192 | 991 MB | 46% | 160 | +20% |
| **256** | **1.32 GB** | **61%** | **224** | **+14%** |
| 320 | 1.65 GB | 77% | 288 | +11% |
| 384 | 1.98 GB | 92% | 352 | +9% |

384 は壁の 92% で、ドライバ更新や別 GPU で即座に破綻する。256 は 39% の余裕を残しつつオーバーヘッドを 14% に抑える。

### Metal / CUDA / CPU の 512 の根拠

単一テンソルは 2.64 GB になるが、これらのバックエンドに単一バッファの上限は無い (Metal はビュー分割で吸収する)。制約は総メモリ量だけであり、2.64 GB のピークは 8 GB クラスの環境でも通る。

**512 = 20.48 秒は `max_seconds = 30` に対して十分大きい。** Dart 側の 200 文字上限を踏まえると、コストを払うのは 20.5〜30 秒の稀な発話だけになる。そしてその領域は、8 GB クラスの Apple Silicon / NVIDIA では現状**総メモリ枯渇で失敗している**範囲でもある。

### NVIDIA の Vulkan が 256 に巻き込まれる件

ggml は Vulkan の実際の上限 (`device->max_buffer_size`) を外部に公開しておらず、`get_max_size()` は AMD でも NVIDIA でも `suballocation_block_size` = 1 GB を返すだけである (D3 参照)。したがって AMD と NVIDIA を実行時に区別できず、Windows では一律 256 になる。NovelViewer の Windows ビルドは全環境で Vulkan を使うため実質的な不公平は生じない。より大きなタイルが欲しい場合は D3 のオプションで指定できる。

### overlap を 16 にする理由

受容野 8 (D1) の 2 倍。厳密性に必要なのは 8 だが、受容野の算出は手計算なので 2 倍の安全率を取る。overlap を 8 に減らしても Vulkan で得られるのは 14% → 7% であり、安全率を捨てる価値は無い。バックエンドで変える理由も無いので一律とする。

### tile 以下は無変更

tile 以下の発話は直接経路を通りオーバーヘッドがゼロになる (D5)。Vulkan の 256 = 10.24 秒は日本語小説の一文 (通常 5〜7 秒) の大半をカバーし、Metal の 512 = 20.48 秒はほぼ全てをカバーする。

## D3. バックエンド別の定数 + オプション上書き (バッファ上限からの動的算出は採らない)

**決定**: tile / overlap は D2 のバックエンド別定数を既定とし、`irodori_tts.codec_decode_tile_frames` / `irodori_tts.codec_decode_overlap_frames` で上書き可能にする。`ggml_backend_buft_get_max_size()` から逆算はしない。

**理由**:

1. 逆算の根拠になる `suballocation_block_size` は **ggml が全バックエンド共通で 1 GB にハードコード**している (`ggml-vulkan.cpp:5240`) 上、環境変数 `GGML_VK_SUBALLOCATION_BLOCK_SIZE` で外から変えられる。デバイス固有値ではないので、動的算出しても得られる情報は「1 GB」だけである。実際に問題を起こしている `device->max_buffer_size` (2 GiB) は ggml のバックエンド API に出ていないため、**そもそも取得できない**。
2. 動的算出はフレームワーク層 (`core::ExecutionContext` 周辺) にバッファ上限を取り出す導線を足す必要があり、Irodori 以外の全モデルに影響評価が要る。本 change を `codec.cpp` + `session.cpp` に閉じ込められなくなる。
3. NVIDIA / Metal でより大きなタイルを使いたくなった場合は、オプションで指定すれば足りる。

**バリデーション**: `overlap * 2 >= tile` は stride が非正になるため拒否する。`overlap < 8` は D1 の厳密性が崩れるため拒否する。いずれも起動時ではなく `IrodoriCodec` の構築時に例外を投げる。

## D4. ウィンドウ長は可変とし、グラフは必要な回数だけ再構築する

**決定**: ACE-Step (`vae_decoder.cpp:854-881`) と同じループ構造を採る。ウィンドウ長を tile に揃えるためのゼロ詰めはしない。

```
for core_start = 0; core_start < F; core_start += stride:
    core_end  = min(core_start + stride, F)
    win_start = max(0, core_start - overlap)
    win_end   = min(F, core_end + overlap)
```

この構造では 1 回の `decode()` で最大 3 種のウィンドウ長が現れる (先頭・中間・末尾) ため、グラフ再構築が最大 3 回発生する。

**却下した案 A: 全ウィンドウを tile フレームにゼロ詰めする。** グラフは 1 個で済み、末尾のゼロ詰めは conv のゼロパディングと等価なので厳密性も保たれる。しかし F=500 / tile=256 の場合 3×256 = 768 フレーム分を計算することになり **+54%**。可変ウィンドウの +14% + グラフ構築 3 回より明確に悪い。

**却下した案 B: ウィンドウ位置をスライドさせて長さを tile に揃える** (`win_start = min(k·stride, F - tile)`)。グラフ 1 個かつ無駄な計算も無い。ただし core 領域の境界計算が非自明になり、テストすべき不変条件が増える。**まず A/B なしで実装し、`irodori_tts.codec_decode.graph_rebuild` の実測値を見てから B を検討する** (タスク 4.3)。

**再構築コストの見積り**: グラフ構築の実体は ggml ノードの生成 (数百ノード、無視できる) と `ggml_gallocr_reserve` による 1.3 GB のバッファ確保。現状のコードも **文ごとに毎回**再構築している (`decode()` は `latent_steps` が変わると再構築し、さらに `mem_saver_` 既定 true が各チャンク後に `release_graphs()` を呼ぶ — `session.cpp:662-664`) ので、長文 1 文あたり 1 回 → 3 回になるだけであり、構造的な悪化ではない。

## D5. 短い発話の経路は 1 命令も変えない

**決定**: `F <= tile` のときは現在と完全に同じコードパス (単一グラフの `Graph::run()`) を通す。

**理由**: 回帰リスクを長文ケースだけに閉じ込める。既存の全ユーザーの体験 (一文 5〜7 秒) は定義上無変更になる。これは ACE-Step の `decode_direct_frame_limit()` と同じ考え方である。

## D6. エンコード側は本 change の範囲外

**決定**: `EncodeGraph` (`codec.cpp:642-711`) は変更しない。

**理由**: 同じ壁が存在する。エンコーダの residual unit は `64 × 7 × L × 4 = 1.79 KB/サンプル` を消費するので、**参照 wav 約 24 秒で 2 GiB に到達**し `failed to allocate Irodori-TTS codec encode graph` で失敗する。

しかし切り離す理由がある:

- 参照音声は `reference_speaker_cache_` でキャッシュされ、1 セッションで 1 回しか実行されない
- タイル境界を `hop_length` (1920) の倍数に揃える制約が加わり、デコード側とは別の設計判断が必要になる
- 発生頻度が低く (長い参照 wav を選んだ場合のみ)、ユーザーは短い wav を選び直せる

デコード側を先に入れて設計を確立し、同じパターンをエンコードに適用する別 change を後で立てる。

## D7. モデルファイル無しでテストする

**決定**: 検証の主軸を、合成重みによる「タイル経路 == 直接経路」のユニットテストに置く。実機の音声確認は補助とする。

**理由**: `tests/unittests/test_conv_transpose_fast_path.cpp` が、CPU バックエンド上で合成重みを使い 2 つの実装経路を比較する形になっている。これをそのまま流用できる。

- モデルファイル (2.9 GB) を CI やテスト環境に用意しなくてよい
- CPU バックエンドなので Vulkan/Metal に依存せず、どの環境でも回る
- 「厳密に一致する」という D1 の主張が**そのまま assert になる**。聴感評価のような主観が入らない

デコーダ全体 (decoder_dim 1536) を合成重みで作るとテストが重いので、**同じ構造で次元を縮めたスタック** (decoder_dim 48 程度、rates は本物と同じ {12,10,8,2}) を使う。受容野は次元ではなくカーネルとストライドで決まるため、縮小しても D1 の性質は保存される。

## 実測結果 (タスク 4)

AMD Radeon RX 6800 / Vulkan / seed 1234 / 参照音声なし。すべて直列実行。

### 修正の確認

タスク 1.1 で `failed to allocate Irodori-TTS codec graph` になっていた 116 文字の一文が、
**19.92 秒 (956,160 サンプル) の音声を生成するようになった**。

```
irodori_tts.codec_decode.tile_frames  256      ← Vulkan 既定 (D2)
irodori_tts.codec_decode.overlap_frames 16
irodori_tts.codec_decode.tile_count   3
irodori_tts.codec_decode.graph_rebuild 3
irodori_tts.codec_decode_ms           2515 (中央値)
session.wall_ms                       6241
```

さらに 159 文字の一文 (691 フレーム = 27.64 秒、分割しなければ単一テンソル 3.32 GiB) も成功した。

### 短い発話が無変更であること (D5 の検証)

実装前後のソースからそれぞれ `audiocpp_cli` を建て直し、同一の短文 (128 フレーム = 5.12 秒) で比較した。

| | run 1 | run 2 | run 3 | 中央値 |
|---|---:|---:|---:|---:|
| before | 547.6 | 552.2 | 544.1 | 547.6 |
| after | 546.2 | 552.2 | 555.8 | 552.2 |

差は +0.8% で、両者の分布は完全に重なっている (before 544〜552 / after 546〜556)。
そして**出力 WAV の SHA-256 が完全に一致した**。`tile_count = 1` / `graph_rebuild = 1` も確認済みで、
直接経路が選ばれている。D5 の「短い文は 1 命令も変わらない」は実証された。

### タイル境界の不連続 (D1 の検証)

19.92 秒の出力について、core 境界 (latent 224 と 448 = サンプル 430,080 と 860,160) の
前後 10 サンプルの隣接差を全体分布と比べた。

| 位置 | 近傍の最大隣接差 | 全体 mean (271.5) 比 | 全体 max (6584) 比 |
|---|---:|---:|---:|
| 境界 1 | 46 | 0.2 倍 | 0.7% |
| 境界 2 | 3 | 0.0 倍 | 0.0% |

境界は周囲の信号と区別できない。ユニットテストが実デコーダ構造で `max_diff = 0`
(ビット完全一致) を出していることと整合する。

### グラフ再構築のコスト (D4 の検証)

素朴な線形回帰は成立しなかった。窓が小さいほど 1 フレームあたりの復号コストが上がる
(GPU の利用効率が落ちる) ためである。

| tile | 窓の内訳 | 総フレーム | 再構築 | decode_ms 中央値 | ms/フレーム |
|---:|---|---:|---:|---:|---:|
| 128 | 112, 128×4, 34 | 658 | 3 | 3554.6 | 5.40 |
| 256 | 240, 256, 66 | 562 | 3 | 2515.3 | 4.48 |
| 320 | 304, 226 | 530 | 2 | 2389.1 | 4.51 |

そこで**総フレーム数を揃えて再構築回数だけを変える**構成を作った。

| tile | 窓の内訳 | 総フレーム | 再構築 | decode_ms 中央値 |
|---:|---|---:|---:|---:|
| 281 | 265, 265 | 530 | **1** | 2295.7 |
| 320 | 304, 226 | 530 | **2** | 2389.1 |

差 93.4 ms が再構築 1 回分にあたる。対照として、総フレーム数も再構築回数も揃えて
窓サイズ分布だけを変えた場合 (tile 249: 233/249/80 vs tile 256: 240/256/66、
どちらも 562 フレーム・3 再構築) の差は 21 ms だった。よって窓サイズ効果を差し引いても

**グラフ再構築 1 回 ≒ 70〜95 ms**

既定構成 (tile 256) では 3 回で約 280 ms、**`codec_decode_ms` の約 11%、`session.wall_ms` の約 4.5%** を占める。

### オーバーヘッドの実測 (D2 の見積りとの比較)

19.92 秒の発話 (498 フレーム) で実際に復号したのは 562 フレーム、**+12.9%**。
D2 の見積り (stride/tile = 256/224 = +14%) とよく一致する。先頭と末尾の窓が
フルタイルより小さいぶん、見積りをわずかに下回った。

ただし**グラフ再構築の増加分を含めた実効オーバーヘッドはより大きい**。
1 フレームあたり (2515 - 3×93)/562 = 3.98 ms から、分割しない場合の仮想値を
498 × 3.98 + 93 = 2076 ms と見積もると、実測 2515 ms は **+21%** にあたる。

**proposal.md の性能表に載せた「+14%」は演算量のみの値であり、実効値は +21% である。**
比較対象が「失敗」である以上この差は判断を変えないが、記録として残す。

### D4 案 B の却下 (実測による)

案 B (全窓を tile フレームに揃えるスライドウィンドウ) を F=498 / tile=256 / overlap=16 で
展開すると、窓は 3 つとも 256 フレームになり総計 **768 フレーム** を要する。
現行の 562 フレームに対し +206 フレーム ≒ **+820 ms** を払って、
再構築 2 回 ≒ 190 ms を節約することになる。**明確に損である。**

**結論: D4 の現行方式 (可変ウィンドウ) を維持する。案 B は採用しない。**

### 見つかった改善余地 (本 change の範囲外)

先頭と末尾の窓は、外側に存在しないオーバーラップのぶんだけフルタイルより小さくなる。
これを core 側に吸収すれば (先頭窓を `[0, tile)` とし core を `[0, tile - overlap)` にする)、
**演算量を一切増やさずに再構築を 3 回から 2 回に減らせる** (約 93 ms、`decode_ms` の 3.7%)。
効果が小さく、境界計算の不変条件が増えるため本 change では採らない。
