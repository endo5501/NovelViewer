## Context

`HamelnSite`（`lib/features/text_download/data/sites/hameln_site.dart`）は 2026-06-08 の `add-hameln-site` で追加され、当時の目次マークアップ（`<table>` + `class="bgcolor2"/"bgcolor3"` 行 + `<NOBR>` 日付セル）に依存している。2026-08-13 時点で syosetu.org は目次をセマンティックなリスト構造に刷新しており、依存セレクタが全滅している。

## Goals / Non-Goals

**Goals:**

- 新マークアップの目次から全話（章見出しをまたいでフラットに）を取得できる。
- 改稿を確実に検知できる `updatedAt` を組み立てる。
- 作者が書いたタイトルを改変せずに保存する。
- タイトル変更に伴う旧ファイル残留を発生させない。
- 実サイト由来のフィクスチャでテストし、次回のマークアップ変更を検知しやすくする。
- 他サイト（なろう・カクヨム・青空・汎用Web）の挙動・既存データに影響を与えない。
- TDD（テストファースト）で実装する。

**Non-Goals:**

- 章情報のデータモデル保持。
- 読める話が0件の作品への特別対応。
- ハーメルンのログイン／会員限定作品。
- `saveEpisode` の保存経路そのものの変更。

## Decisions

### 決定1: 走査対象を `a.episode-list__link` にし、`href` パターンによる絞り込みは維持する

`li.episode-list__item` を列挙し、その中の `a.episode-list__link` を取る。ただし `href` が `^(?:\./)?\d+\.html$` にマッチすることの確認は**残す**。関連作品リンクや将来の構造変更で別のアンカーが混ざった場合の保険であり、旧実装から引き継ぐ価値のある防御。

章見出し `li.episode-list__chapter` は `a.episode-list__link` を持たないため、明示的な除外を書かなくても自然に落ちる（旧実装で章行が `bgcolor` クラスを持たないため落ちていたのと同じ構図）。

- **代替案**: `section.episode-list` を起点に `querySelectorAll('a.episode-list__link')` で一発取得 → `li` 単位で日付・改稿マーカーを取る必要があるため、`li` 走査のほうが素直。ただし新マークアップでは `<time>` と `<span class="episode-list__revision">` が **`<a>` の内側**にあるので、`a` 起点でも取得できる。実装しやすいほうを選んでよい。

### 決定2: 話数カウンタ除去 (`^\d+　`) を撤廃する

実サイトの実測により、ハーメルンは表示カウンタを自動付与していないことが確認された。

```
./1.html  → 「プロローグ」            ← 自動カウンタなら "1　" が付くはず。付いていない
./4.html  → 「3　運ぶための力」        ← ファイル番号4に対し表示3 = 作者自身の連番
./11.html → 「10 　京都参戦」          ← 半角スペース混じり。現行の正規表現に当たらない
```

したがって先頭の数字は作者のタイトルの一部であり、現行処理は作者タイトルを一貫性なく破壊している。`_displayCounterPattern` を削除し、`span.episode-list__title` のテキストを `trim()` してそのまま格納する。

- **代替案**: 互換のため除去を維持 → 作者タイトルの破壊を継続することになるため不採用。

### 決定3: `updatedAt` は「`<time>` テキスト + 改稿 `title` 属性」で組み立てる

これは精度向上ではなく、**既存要件を満たすための必須条件**である。

```
改稿前: <time>2026/02/21 16:20</time>  <span class="episode-list__revision"> </span>
1回目 : <time>2026/02/21 16:20</time>  <span … title="2026/02/27 23:54改稿">(改)</span>
2回目 : <time>2026/02/21 16:20</time>  <span … title="2026/03/01 06:05改稿">(改)</span>
        └──── 変化しない ────┘        └──── ここだけが変化する ────┘
```

`<time>` のテキストは投稿日時で改稿しても変わらず、`(改)` も固定文字列なので、両者だけでは2回目以降の改稿を検知できない。改稿ごとに変化する唯一の値が `episode-list__revision` の `title` 属性（`2026/03/01 06:05改稿`）である。

格納形式は `"{timeテキスト} ({title属性})"`（例: `2026/02/21 16:20 (2026/03/01 06:05改稿)`）とする。`updatedAt` は `_shouldDownload` の**完全一致比較にのみ**使われ日付として解釈されないため、可読性（デバッグ時）のみを基準に決めてよい。改稿マーカーが無い場合は `<time>` テキスト単体、`<time>` が無い場合は `null`（`_shouldDownload` は `null` で毎回再DLにフォールバックするため安全）。

`<time>` の `datetime` 属性（ISO形式）は先頭 (`itemprop="datePublished"`) と末尾 (`itemprop="dateModified"`) のエントリにしか付かないことを実測で確認したため、**属性ではなくテキストを使う**。

- **代替案**: 旧形式 (`2026年02月25日(水) 22:58`) に整形して既存キャッシュと互換を取る → 改稿情報を落とすと差分検知が壊れる。また全話再取得はユーザ判断で受容済み。

### 決定4: タイトル抽出は変更しない（連載・短編とも現行経路が有効）

連載は `span[itemprop="name"]`、短編は見出しの自己リンク `<a href=./>` がいずれも健在で、`_extractTitle` は現行のまま正しく動作する。

調査の途中で「短編の自己リンクが消えた」と誤認した経緯を残しておく。実マークアップは**属性値に引用符が無い**形（`<a href=./>異世界転生？他所でやれ！！</a>`）なので、`grep 'href="./"'` では0件になる。HTMLパーサは属性値を `./` として解釈するため、`querySelector('a[href="./"]')` は問題なく一致する。既存テスト `parseIndex - single-part title from heading` が `<a href=./>` の非引用形を使って、この経路が機能することを既に固定している。

したがってタイトル抽出は**コードも spec も変更しない**。短編フィクスチャでは自己リンク経路が引き続き機能することを回帰テストとして押さえる。

### 決定5: ファイル名移行の同一エピソード判定を「前回タイトル」も許容するよう一般化する

決定2でタイトルが変わるため、既存ファイルが取り残される。

```
移行前に保存済み : 0004_運ぶための力.txt
新しい期待ファイル: 0004_3　運ぶための力.txt   ← 両方残り、同じ話が2件に見える
```

現行 `migrateEpisodeFileNamePadding` は `(parsedIndex == i) AND (restName == safeName(現在のタイトル))` を同一エピソードの条件にしているため、タイトル変更ケースは対象外（spec に「Title-changed file is not migrated」と明記されている）。`saveEpisode` は旧名を消さずに書くだけなので、旧ファイルはゴミとして残る。

**素朴な一般化（`parsedIndex` だけで一致とみなす）は採らない。** それだと話が途中に挿入されてインデックスがずれた場合に、別エピソードの本文を現在のインデックスのファイル名にリネームしてしまい、URLキーのキャッシュ判定と組み合わさって**誤った本文を正しい話として温存**しうる。現行の restName 一致条件は、偶然この事故を防ぐ役割を果たしている。

代わりに、**エピソードキャッシュが記録している「前回そのURLで保存したタイトル」**を同一性の根拠に使う。キャッシュは URL をキーに `episodeIndex` と `title` を保持しているので、前回書いたファイル名の restName は `safeName(cache[url].title)` として厳密に再現できる。

```
同一エピソード判定（拡張後）:
  parsedIndex == i かつ
  ( restName == safeName(現在のタイトル)          ← 従来（パッド幅違い）
    OR
    restName == safeName(cache[url].title) )      ← 追加（タイトル変更）
```

ハーメルンのケースでは URL も index も変わらないため後者が必ず成立し、旧ファイルは正しくリネーム／削除される。インデックスがずれた場合はキャッシュの前回タイトルと一致しないので**何も触らない**（今日と同じ挙動＝旧ファイルは残るがデータ喪失は無い）。安全側に倒れる。

リネーム／削除の分岐、冪等性、no-abort 契約（個別失敗は WARNING ログのみで全体を止めない）は既存のままとする。

- **代替案A**: `saveEpisode` で同 index の旧ファイルを削除する → 保存経路が全サイトで毎回削除を走らせることになり影響範囲が広い。また移行処理と役割が二重化する。
- **代替案B**: 何もせずユーザにフォルダ削除を促す → 更新のたびにゴミが増える運用になるため不採用。

### 決定6: フィクスチャは実サイト取得HTMLのサニタイズ版にする

`hameln_index_valid.html` は手書き620バイトの旧マークアップ模造で、実サイトが変わってもテストは緑のままだった。実HTMLを取得してサニタイズ（広告・トラッキングスクリプト・不要なヘッダフッタの除去、本文の短縮）したものに差し替える。

必要な検体（`https://syosetu.org` から取得。UAは `NovelViewer (Flutter desktop app)`、Cookie は `over18=off` が必要）:

| 用途 | 取得元 | 特徴 |
| --- | --- | --- |
| 連載の目次 | `/novel/402955/` | 章見出し4件・39話・改稿マーカーあり／なしが混在 |
| 短編（インライン本文） | `/novel/123475/` | `episode-list` セクション無し・`#honbun` あり・`<title>` 重複形式 |
| 各話本文 | `/novel/402955/1.html` | `#maegaki` / `#honbun` / `#atogaki` が揃っている |
| ドリフト検体 | 既存 `hameln_index_drifted.html` | そのまま流用（空目次ガードの前提条件テスト用） |

既存の `hameln_index_valid.html`（旧マークアップ）は、**新実装で0件になること**を確認する回帰検体として `hameln_index_legacy_table.html` にリネームして残すか、`drifted` に統合するかを実装時に判断してよい。

## Risks / Trade-offs

- **全話再取得**: `updatedAt` の形式が変わるため、ダウンロード済みのハーメルン作品は初回更新時に全話を再取得する。ユーザ判断で受容済み。レート制限に従うため大作では時間がかかる。
- **ファイル名移行の一般化は全サイト共通コードに触れる**: 既存の同一タイトル経路の条件は変えず、OR 条件を追加するだけに留める。他サイトのテストが回帰しないことを確認する。
- **エピソードキャッシュが無い／古い場合、旧ファイルは残る**: 決定5は `episode_cache.db` の前回タイトルを同一性の根拠にするため、キャッシュDBが失われている環境（既存コードも「missing/stale `episode_cache.db`」を想定済みの状態として扱っている）では判定が成立せず、旧タイトルのファイルが残ったまま新ファイルが追加される。データ喪失は起きないが重複表示は起きうる。安全側（触らない）に倒す設計上の割り切りであり、既知の制限として受容する。実サイト確認 (5.2) でも、キャッシュが健在な通常経路を対象とする。
- **例中のファイル名のパッド幅**: 本ドキュメントの例では `0004_…` と4桁で表記しているが、パッド幅は総話数の桁数に依存する（39話の作品なら `04_…`）。実機確認時の実際のファイル名は総話数に応じて読み替えること。
- **サイトが再び変わるリスク**: 今回の根本問題は「テストが旧マークアップを固定していたこと」。実HTML由来のフィクスチャにしても、サイト変更を自動検知はできない。空目次ガード (F118) が実行時に確実にエラーを出す設計は維持されているので、少なくとも静かな失敗にはならない。

## Migration Plan

コード側の移行処理のみで完結し、ユーザ操作は不要。

1. 更新実行時、`migrateEpisodeFileNamePadding` が旧タイトルのファイルを新ファイル名にリネームする。
2. `updatedAt` の形式差によりキャッシュ判定が不一致となり、全話が再取得されてリネーム済みファイルを上書きする。
3. エピソードキャッシュDBは移行処理では変更せず、再取得時に新しい `updatedAt` で上書きされる。

ロールバック時（旧バージョンに戻した場合）は、ファイル名・`updatedAt` がともに旧形式へ戻る方向で再度全話再取得が走る。データ破壊は発生しない。
